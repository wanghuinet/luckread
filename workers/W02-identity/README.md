# W02 — Identity / Account

Canonical Worker role: **Identity / Account**.

Project authority has selected this repository path as the physical source location for canonical W02:
`workers/W02-identity`

The directory name `W02-identity` is the canonical physical path for W02; Worker authority remains defined by the Worker Master. Canonical W02 owns T01/T02 and the D1-01 logical identity/account persistence domain under the amended Worker Master; the physical production database is Neon PostgreSQL. Production deploys the D1-free `wrangler.neon.jsonc` against the existing D1-01 Neon Hyperdrive. The original `wrangler.jsonc` and `migrations/**` are retained as historical SQLite/D1 schema lineage, reviewed migration-source evidence and limited legacy test fixtures; they are not a production runtime provider.

Deployment and inter-Worker transport are governed by:
`docs/change-control/CC-MAPPING-0-E6-W02-DEPLOYMENT-TRANSPORT-DECISION-2026-09-22.md`

W02 remains the sole account-system core:
- Better Auth owns authentication, sessions and email-verification flow.
- W02 owns account creation/lifecycle and authoritative account state.
- Payload Core and Better Auth implementation are not replaced or modified by the W08 CASL change.
- W02 continues to host the existing RoleAssignment materialization and layer-projection code during this incremental closeout because account lifecycle and authentication response paths currently depend on it. That compatibility code does not make W02 the shared business-permission policy engine; CASL policy evaluation belongs to W08.
- Existing internal session endpoints remain Service-Binding transports only. No public W02 auth endpoint is introduced by the W08 authorization change.
- D1-01 remains the logical database-domain label only. Production W02 identity, account, RoleAssignment, session, MFA and audit persistence runs through the existing Neon PostgreSQL Hyperdrive; PostgreSQL-native artifacts in `src/neon-postgres-migrations/**` are the schema applied to Neon. Original D1 migrations are retained solely as source lineage and are never executed against PostgreSQL.

W08 authorization contract:
`workers/W08-creator/src/authz/casl-policy.ts` and `POST /internal/authz/check-permission`.

No Worker deployment is implied by source changes. Remote D1 mutation and controlled Worker deployment still require their own evidence and authorization.


## Staged Neon D1-01 PostgreSQL schema

- Better Auth core tables are generated by the pinned Better Auth 1.7.27 CLI from the canonical \`buildLuckReadAuth\` configuration using the schema-only PostgreSQL config. The config is used only by the pinned Better Auth schema CLI; the production Worker uses the D1-free `wrangler.neon.jsonc` and the D1-01 Neon Hyperdrive.
- Existing W02 PostgreSQL-native custom migration artifacts \`0001\`–\`0010\` are generated from the W02 D1 source migrations and canonical contracts. A combined disposable PostgreSQL 18.6 rehearsal applies the Better Auth core and custom artifacts in dependency order, then runs the existing per-feature PostgreSQL verifiers.
- The W02 rehearsal is schema-only. It does not execute the SQLite/D1 source migrations on PostgreSQL, connect to Neon, touch Cloudflare D1, import users/sessions/credentials, or deploy/change the Worker runtime.
- \`0007_l8_genesis_bootstrap_audit.sql\` is intentionally excluded from this staged Neon schema because its referenced genesis change-control record still declares PR #1299 proposed/unmerged/undeployed. It requires separate admission after the out-of-band approval and MFA readiness conditions are met.
- The historical \`0002_auth_013_account_state.sql\` alters the W01 Payload \`users\` projection; it is not executed as a W02 Better Auth migration. W02 Better Auth account state is represented by the canonical custom fields in the generated \`user\` schema, while W01 remains the owner of Payload tables.
