## 0. 本契约的目标

本契约是 GPT/工程执行者开展 LuckRead 三端产品体验工程的统一准绳。目标不是做三套相似的页面，而是把 LuckRead 打造成拥有 X 与 Threads 级成熟度的统一社交产品：

- **体验目标**：快速、自然、完整、可靠、可恢复、可访问，尽可能贴近 X / Threads 用户已熟悉的交互模型、信息密度、页面结构、导航、反馈和内容发现体验。
- **产品目标**：三端共享同一账号、内容、关系、权限、通知、搜索语义、业务规则与链接；不同设备只按平台能力适配呈现。
- **工程目标**：优先复用 LuckRead 已有代码、API、组件和获准开源参考；发现真实缺陷后一次推进完整功能闭环，不重复评审文档，不做无证据的“完成率”。
- **验收目标**：逐功能以需求、设计/行为、API/权限、测试、运行和设备证据验收。体验达到高标准是目标，不把“完美”或“100%”当未经证据证明的声明。

参考 X / Threads 的公开产品行为和交互惯例，不复制商标、专有素材、私有算法、私有接口、受限代码或未经授权的资产。

## 2. 三端统一定义

### 2.1 业务一致
三端的账号、内容、帖子状态、回复、关注、互动、隐私、屏蔽/静音、通知、搜索、订阅权益及服务端判定必须一致。端侧不得创造业务事实或改变授权语义。

### 2.2 体验一致
- 同一功能在三端应有相同的命名、意图、状态、操作结果、失败原因、权限边界和数据含义。
- 交互可以根据平台原生习惯变化：App 使用原生导航、触控、手势、系统键盘、相机/媒体权限；H5 与 PC 使用浏览器、鼠标、键盘、响应式布局及可分享 URL。
- 一致不等于强制把手机布局拉伸成桌面，也不等于三端逐像素相同。

### 2.3 端级职责
- **App**：触控优先、快速启动、底部导航、原生分享/相机/媒体选择、系统通知、深链、离线和恢复体验。
- **H5**：移动浏览器优先，响应式和触控行为完善；轻量加载，支持浏览器历史、深链、分享、登录状态恢复。
- **PC**：桌面多栏布局、键盘导航、鼠标/滚轮操作、快捷键（可选且可发现）、窗口宽度适配，保持可读和可操作。
- 不得将第三端含混为任意页面；在本契约中 H5/移动 Web 与 PC Web 分别验收。若项目目录或发布渠道将两者合并，仍需在测试矩阵分别覆盖移动和桌面 viewport。

## 3. 对标标准与评估方法

评估 X / Threads 公开可见行为作为参考基准，而非不变的功能清单。每一功能需记录：参考行为、LuckRead 目标、当前实现、差距、技术依赖、风险、测试与证据。

### 3.1 评分级别
每个功能使用以下级别，不使用模糊“差不多”：
- **L0 未审查**：尚无可靠源码/运行证据。
- **L1 源码存在**：实现可定位，尚未证明完整运行。
- **L2 自动验证**：针对性测试/静态检查通过。
- **L3 集成验证**：真实 API、权限、状态和端到端流程通过（记录环境）。
- **L4 设备验收**：真实目标设备/浏览器的操作、可访问性、性能和故障恢复验收通过。

同时用状态分类：VERIFIED_COMPLETE、CODE_PRESENT、PARTIAL、MISSING、BLOCKED、BROKEN、DEFERRED。百分比仅在明确分母、权重、证据等级和未覆盖项后计算；不得将源码存在、CI通过或PR合并单独称为上线完成。

### 3.2 优先级
- **P0 Beta 核心闭环**：登录与账户切换、导航、Feed、帖子详情/回复、互动、发布和媒体、搜索基本能力、个人主页、通知、隐私/安全、错误恢复、性能、可访问性。
- **P1 社交完整度**：高级搜索/过滤、主题、引用帖子、列表/自定义Feed、收藏分类、Creator Studio、更多通知/创作者体验、视频创作完善。
- **P2 扩展**：Communities、Live/Spaces、AI功能等；先完成产品批准、API/权限/成本与治理评估，不默认纳入 Beta。

## 4. 全产品页面与功能清单

GPT 必须持续维护此清单，检查现有页面/模块并修复真实缺陷，不应只写报告。按阶段实施，避免并行触碰相互依赖的领域。

- 弹层/菜单/确认框/键盘避让/手势关闭/滚动锁定/焦点恢复。
- 安全区、状态栏、系统栏、横竖屏、动态字体、reduce motion、屏幕阅读器。
- 端侧 loading skeleton、错误恢复、无网络、慢网络、重试、刷新、取消和超时行为。

### B. Feed 与内容发现（P0/P1）
- For You、Following、Latest（若服务/API支持）；清晰切换与滚动状态恢复。
- Feed 卡片：头像、显示名、用户名、验证/状态（真实权威）、时间、正文、链接、图片/视频/多媒体、内容警告、编辑状态、互动计数、菜单。
- Feed 加载、分页、pull-to-refresh、空态、失败重试、无效/已删除内容、屏蔽用户、重复项和排序。
- Feed 内媒体预加载、播放控制、自动播放偏好/节流、占位与失败状态。
- Topics、搜索趋势、主题关联、兴趣发现及个性化 Feed（按现有 API/权限）。
- 推荐与Following之间切换，不意外丢失用户上下文。

### C. 帖子详情与讨论（P0）
- 独立帖子详情、回复层级、回复加载/分页、引用关系、原帖/转帖关系、回复折叠和上下文。
- 回复/评论撰写、编辑/删除（权威允许时）、回复限制、引用限制、举报、屏蔽。
- 线程阅读体验：清晰层级、父回复上下文、长回复、媒体、加载更多、回到原帖。
- 回复计数和互动状态一致；更新失败回滚/提示/重试，不重复提交。

### D. 内容发布 / Composer（P0）
- 文本输入、长度/字符限制、草稿自动保存、草稿恢复、清空确认。
- 图片、视频、相机、媒体权限、选择、预览、移除、上传进度、失败重试、取消。
- 多媒体排序、封面/预览、视频播放预览、尺寸/格式/网络处理（按既有 API）。
- 投票创建与选项验证、发布、结果和投票权限。
- 帖子线程/多段发布（API支持时）、引用帖子、内容编辑、发布后跳转/Feed更新。

### E. 用户 Profile / 关系（P0）
- Profile 头部、头像/封面、简介、链接、真实资料字段、关系状态、关注/取消关注。
- Posts、Replies、Media、Likes（受隐私/API授权限制）、置顶内容、用户信息编辑。
- Followers/Following列表、加载/搜索、关系操作、屏蔽/静音/举报入口。

### F. 搜索（P0基础/P1完整）

## 5. 视觉设计与交互要求

### 5.1 视觉基线
- 采用 X / Threads 常见社交产品信息层次：简洁顶部区域、清晰正文、头像与身份、媒体占位/呈现、互动行、列表分隔、导航和弹层。
- 建立并复用项目现有 token/组件，不出现页面自建颜色、字体、间距、按钮、图标和阴影体系。
- 字体大小、行高、内容宽度、卡片边界、媒体比例、点击目标、按钮状态、焦点和视觉反馈一致。
- 不直接使用 X/Threads品牌图标/Logo/专有插画，采用 LuckRead品牌与合法的通用交互符号。
- 深色/浅色模式完整一致；图片、视频、弹层、输入框、系统栏和错误状态均适配。

### 5.2 动作与反馈
每个可操作控件必须具备：
- 明确可发现的 affordance；
- 触控/鼠标/键盘可操作性；
- loading/disabled/pressed/focus状态；
- 成功反馈（基于真实操作结果）；
- 错误说明、恢复或重试路径；
- 防重复提交、合理节流；
- 可访问名称、状态和焦点顺序。
禁止按钮仅视觉可点却无行为；未开放功能应诚实呈现且不作为默认核心导航。

### 5.3 不要求机械像素复制
参考产品会迭代且有地区/账号差异。以公开、可观察、稳定的产品模式为基准。针对 LuckRead 的业务、品牌、架构、内容治理和平台差异，允许必要偏差并记录理由。

## 6. 性能契约与可观测性

目标不是无条件承诺具体毫秒数，而是对每个关键页面测量并逐步达到目标。先记录设备/浏览器、网络、构建版本、数据规模、指标和测试步骤，再优化。

关键指标至少包括：
- 启动/恢复：冷启动、热启动、Session恢复、首次可交互时间。
- Feed：首屏呈现、TTFC/TTNC（适用时）、滚动帧率、图片加载、预取、分页。
- Composer：打开/输入响应、媒体准备、上传耗时、发布成功率、恢复率。
- Search：输入响应、结果延迟、取消与错误率。
- Profile/通知/消息：首屏、分页、刷新、实时连接/重连。
- Web：LCP、INP、CLS、资源大小、缓存命中、导航和路由加载。
- App：内存、崩溃、卡顿、ANR（Android）、启动与媒体播放稳定性。

### 6.1 优化原则
- 首屏先呈现可用内容；非关键请求延迟加载，避免同步阻塞。
- 复用现有查询缓存、分页和请求取消机制；缓存键必须包含必要身份/权限上下文。
- 防止账户切换后旧请求、旧缓存、草稿、上传和媒体状态污染新账号。
- 媒体优先缩略图、合理预加载窗口、取消不可见请求、播放状态与屏幕/可见性同步。
- 优化应有基线与结果，不通过牺牲正确性、隐私或权限换速度。
- 不在文档中虚报性能数据；没有设备实测标记为 NOT_MEASURED。

## 7. 安全、身份隔离与权限

- 三端仅使用既有统一对外 API 和 transport，遵守 `THREE-CLIENT-DEVELOPMENT-CONTRACT.v1.0.md`。
- 客户端永远不连接 Neon/D1/数据库，不访问内部 Worker/Service Binding，不调用私有 API。
- 每个 query/cache、mutation、草稿、上传、临时媒体和本地数据都审查 viewer/account scope。
- 账户切换/注销必须清除或隔离旧账户缓存、请求、实时连接、草稿、上传队列和敏感内容，遵循当前会话/数据契约。
- 服务端权限不可由隐藏按钮、客户端角色或缓存代替。
- 私有/会员/被屏蔽/敏感/已删除内容不能因共享缓存或深链绕过权限。
- API写操作遵守现有幂等和状态语义，拒绝重复提交、权限过期、旧账户token和非法payload。

## 8. 开发执行协议：GPT 每轮工作必须遵循

每次用户指令“继续”：

1. **实时核查**：确认 main 最新 SHA、现有开放 PR、最近合并、当前契约/功能 tracker、目标代码和相关测试。
2. **去重**：不重复已合并功能、不覆盖他人PR、不把已封存模块重新审计；仅对新证据提出解封。
3. **确定完整大阶段**：选择一个明确且规模合理的垂直工程阶段，避免拆成无意义小任务或重复只写评审文档。阶段必须能产生可验证的功能改进。
4. **确认依赖**：检查 API、权限、领域契约、源代码、许可和架构；缺失时停止受阻部分并记录证据。
5. **实施**：在独立分支完成该阶段代码、针对性测试、必要文档与验证；不得直接写 main。
6. **测试**：运行能运行的测试、静态检查、构建/CI。记录命令、结果和限制。不得把未运行的测试描述为通过。
7. **安全与回归**：检查身份隔离、权限、缓存、错误恢复、跨端一致性和可能影响范围。
8. **交付**：创建一个聚焦该阶段的 PR，说明范围、改动、测试、未验证项、风险、验收步骤。默认 draft PR，除非已满足审查标准。
9. **PR管理**：除用户明确授权外，不合并 PR；不合并其他工程师PR、不关闭或改写其他工程师PR、不更改主分支保护。
10. **阶段结束**：完成一个大的可验证阶段后总结证据与下一阶段方向，等待“继续”。不要为了反复出文档而循环审计；如果没有新证据或可执行差距，应停止重复工作。

### 8.1 GPT必须主动执行而不是仅提出建议
- 检查实际源码并定位缺陷；
- 在授权范围内修改代码；
- 新增/更新测试；
- 运行测试与必要检查；
- 以PR交付；
- 记录明确阻塞与证据；
- 对实际完成项更新tracker/验收记录（如允许且不造成重复文档）。

GPT不得仅通过新建大量评审文件替代产品工程实施。

## 9. 大阶段计划与出口标准

### Stage 0 — Baseline / Contract Alignment
**出口**：最新主分支、开放PR、契约和功能tracker对齐；目标分母、阶段范围和证据等级清晰；无重复审查。

### Stage 1 — P0 App Core UX Closure
范围：App Shell、身份隔离、Feed、Search基础、通知、Profile、核心导航/加载/错误状态。
**出口**：源码、测试、API行为、账户隔离和核心旅程证据；明确哪些设备验收未完成。

### Stage 2 — Publishing & Media Reliability
范围：Composer、草稿、图片/视频、投票、线程、上传、恢复、发布状态。
**出口**：独立测试环境下的真实 API E2E、失败/重试/进程恢复、账户切换、幂等与权限证据。

### Stage 3 — Social Interactions & Thread Quality
范围：帖子详情、回复树、点赞、关注、转帖/引用、收藏、分享、限制、举报、屏蔽/静音。
**出口**：各互动状态/权限/回滚、深链、跨端数据一致性验证。

### Stage 4 — H5 / PC parity & Responsive Experience
范围：移动Web、桌面Web、统一功能语义、布局、路由、键盘/鼠标/触控、性能。
**出口**：移动/桌面浏览器分别验收，关键核心旅程无端间业务语义差异。

### Stage 5 — Settings, Privacy, Notification & Account
范围：设置完整闭环、隐私、安全、通知偏好、账户数据/删除等现有合同支持项。
**出口**：设置状态来自权威 API、保存和恢复、失败路径、跨端一致性。

### Stage 6 — P1 Discovery & Creator Features
范围：高级搜索、主题、列表、自定义Feed、Creator Studio、书签分类、视频创作扩展。
**出口**：API合同/权限、完整端到端、无占位假功能。

### Stage 7 — Performance, Accessibility & Release Readiness
范围：关键性能基线/优化、屏幕阅读器、动态字体、减动效、真实设备/browser测试、Beta blockers。
**出口**：指标数据、设备/版本/测试步骤、残留风险、发布门禁与回归清单。

阶段顺序允许根据真实依赖调整，但必须记录调整依据。不能通过不断新增“审计阶段”拖延可执行工程。

## 10. PR模板最低要求

每个三端功能 PR 必须包含：

- **Stage / Feature / Scope**
- **Reference behavior**：对标公开参考模式及观察日期
- **LuckRead current state**：已有实现和去重来源
- **Changed paths**
- **Authority/API**：W01公开API、Worker authority、权限契约
- **Cross-client impact**：App / H5 / PC
- **Tests run**：命令、结果、CI状态
- **Evidence level**：L0-L4各项及未验证项
- **Accessibility**：触控目标、键盘、屏幕阅读器、动态字体、减动效
- **Performance**：基线/结果或 NOT_MEASURED
- **Security / isolation**：账户隔离、缓存、权限、媒体
- **Risks / blockers / follow-up**
- **Manual acceptance steps**

## 11. 完成判定

本契约目标是高质量、可持续的三端产品，不接受：
- 页面堆砌、假入口、假数据、无操作的控件；
- 只改视觉但破坏业务权限、状态或API；
- 三端各自做不同业务逻辑；
- 反复新建评审文档却不修真实缺陷；
- 无测试、无设备证据却宣布“完美”“100%”“已上线”；
- 为对标而擅自新增数据源、Worker、数据库、API或绕过现有边界。

**最终产品验收**必须以 P0 核心旅程和必要P1功能的真实证据、跨端一致性、权限与隔离、性能、可访问性、故障恢复及 Beta 发布门禁为依据。X / Threads 是体验参考，LuckRead 必须形成自己的品牌与产品。
