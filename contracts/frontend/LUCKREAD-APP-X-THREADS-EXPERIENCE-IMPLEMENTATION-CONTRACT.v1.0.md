## 0. 契约目的与效力

本契约规定 LuckRead 原生 APP 以 X 和 Threads 的成熟用户体验为目标，如何审计现有实现、筛选已验证的 GitHub 开源代码、复用已有组件、拆分模块、实施、测试、发布和验收。

本契约不是要求把 X 或 Threads 的所有功能一次性复制到 LuckRead，也不是重新设计 LuckRead 后端。目标是吸收两类产品的有效体验：

- **X：** 快速公共信息流、实时互动、帖子与回复线程、引用转发、内容传播、私信、通知、搜索和创作者订阅。
- **Threads：** 主题驱动的发现、话题标签、可管理的回复、兴趣信息流、自定义 Feed、社群氛围、创作者洞察和更好的对话质量。

最终目标是让 LuckRead 形成自己的统一产品体验，而不是复制 X / Threads 的商标、专有素材、内部接口、私有算法或未经授权的代码。

### 0.1 契约执行规则

1. 本契约提交并经审阅后，作为 APP 对标项目的分阶段执行依据。
2. **一次只开发一个独立模块或一个完整垂直功能切片。**
3. 当前模块完成代码、测试和 PR 交付后，立即停止，不自行开始下一个模块；等待产品负责人明确发出“继续”。
4. 不把多个无关模块合并到一个 PR，不以批量提交掩盖缺陷。
5. 未经明确指示，不自行合并 PR、不关闭 PR、不改变主分支保护策略。
6. 每轮首先检查 main、开放 PR、已有代码、现有 API、成熟上游项目和测试证据，完成去重后才允许修改。
7. 任何模块如果缺少必要的权威 API、权限、数据契约或可验证复用来源，必须报告阻塞和最小缺口；不得制造假 UI、假数据或仅靠本地状态模拟成功。
8. 合并、部署和生产验收是不同状态。PR 合并不等于生产功能完成。

## 1. 不可违反的架构约束

### 1.1 Worker 与数据边界

1. 保持 LuckRead 当前既定的 **12 Workers、5 D1、现有 Queue 和 Service Bindings**；不得因本项目新增 Worker、D1、Queue、Service Binding 或第二套领域服务。
2. 保持 W11 独立分析数据边界及其现有 allLuck / allluck 约定，不把分析事件回写成业务权威事实。
3. W01 是 APP、H5、PC 对外 API / Payload / CMS 边界；前端不得直接访问 D1、R2、Worker 内部绑定或数据库。
4. W02 继续承担 Better Auth 账号、凭证、Session 和账号状态权威；不得在 APP 内另建账号体系。
5. W03 是内容权威；帖子、文章、视频、草稿、发布状态、编辑版本和内容所有权必须服从 W03 当前契约。
6. W05 是社交关系和互动权威；关注、点赞、评论、转发、收藏等操作必须复用现有 W05 / W01 暴露的权威路径。
7. W06 按当前治理与审核边界执行；举报、内容限制、审核结果、风险策略和申诉不能由客户端自行决定。
8. W07 是订阅、支付、订单、退款和商业权益权威；APP 不自行判定付款成功或会员权限。
9. W08 按现行授权契约执行；客户端不能自行提升角色、层级或权限。
10. W10 按现有异步执行边界处理需要异步化的工作；不把通知 fan-out、统计或外部投递变成 APP 同步写入依赖。
11. W11 负责按现行约定接收分析事件与派生指标；浏览、播放、互动、订阅和收入指标必须定义各自的权威来源与口径。

以上角色是本项目必须遵守的现有边界摘要，不构成对 Worker 职责的重新定义。具体接口和读写归属以对应 Worker 的当前契约为准。

### 1.2 严禁事项

- 不修改 Payload Core。
- 不修改 Better Auth 核心实现来满足 APP 视觉需求。
- 不引入 Firebase / Firestore 作为新的账号、帖子、消息、关注或内容数据源。
- 不把开源项目自己的登录、支付、存储、权限、数据库和后端接口迁入 LuckRead。
- 不在 React Native 页面内写数据库访问逻辑。
- 不通过客户端拼接或猜测 R2、S3、私有媒体地址。
- 不复制帖子正文来实现转发或引用转发；转发应引用原始内容 ID。
- 不在 APP 本地保存付款、订阅、关注、点赞、审核或权限的最终权威状态。
- 不为一个 UI 模块创建新的业务表、Worker 或平行 API。
- 不以关闭鉴权、扩大权限、绕过审核或放宽数据校验来达到“页面能用”。
- 不把上游 Demo、截图、静态 HTML、无测试代码标记为生产级已验证实现。

## 2. 产品目标与体验原则

### 2.1 X 体验目标

LuckRead 应优先学习 X 的以下交互特征：

1. 打开 APP 后快速显示可用内容，不因非关键资料请求阻塞首屏。
2. For You / Following / Latest 等信息流切换清晰，滚动位置和刷新状态可预测。
3. 帖子卡片信息密度合理，作者、正文、媒体、时间、互动数和操作入口完整。
4. 回复、回复树、引用转发、普通转发和原帖之间的关系明确。
5. 发布窗口支持文字、媒体、投票、引用、线程等内容生产路径。
6. 点赞、关注、收藏等操作反馈即时；失败时能恢复，不产生重复记录。
7. 用户主页能清晰呈现帖子、回复、媒体、文章、视频和关系。
8. 通知、私信、搜索和创作者订阅形成完整的回访路径。
9. 原生菜单、底部弹层、手势、键盘和导航符合 Android / iOS 使用习惯。
10. 内容链接、用户链接和深链在 APP、H5、PC 之间保持一致。

### 2.2 Threads 体验目标

LuckRead 应学习 Threads 的以下交互特征：

1. 以话题和兴趣组织内容发现，不只依赖单一推荐流。
2. 允许用户关注感兴趣的主题，并从主题进入相关讨论。
3. 支持可管理的信息流、用户自选 Feed 和 Feed 固定入口。
4. 发帖时帮助作者选择相关主题，但不强制添加无关标签。
5. 作者可以控制谁能回复、谁能引用或互动；实际权限必须由服务端执行。
6. 对高质量讨论提供回复排序、回复筛选、回复审核或批准等能力；只有在领域 API 和治理契约支持后才开放。
7. 个人资料可以展示兴趣和主题，帮助其他用户理解账号定位。
8. 创作者洞察不仅展示浏览量，也应展示回复、粉丝增长、内容表现和周期变化。
9. 社群围绕共同兴趣形成轻量身份、讨论和内容发现。
10. 体验重点是对话质量、兴趣关系和可控性，而不是单纯复制按钮。

### 2.3 统一设计原则

- 快速：先呈现必要内容，非关键资料延迟加载。
- 连贯：页面、底部弹层、键盘、返回手势和导航行为保持一致。
- 可恢复：加载失败、上传失败、断网、登录过期均有明确恢复操作。
- 可信：所有状态来自 LuckRead 权威 API，禁止假成功。
- 可控：通知、回复、隐私、屏蔽、静音和内容可见性设置清楚。
- 可访问：支持屏幕阅读器、动态字体、足够的点击区域、颜色对比和系统安全区域。
- 多端一致：APP、H5、PC 共享相同身份、内容、权限和业务事实。
- 最小自研：已有能力不重写；成熟组件优先；仅编写必要的 LuckRead API adapter 和集成代码。

## 5. 功能详细要求

### 5.1 APP Shell 与统一交互

**目标：** 让整个 APP 的基础导航和控件表现一致，不再出现个别页面白屏、主题不一致、弹层无法关闭、返回错乱或点击无响应。

必须覆盖：

1. 启动恢复：Session 校验、登录过期、冷启动和热启动。
2. 导航：底部 Tab、Drawer、详情页、深链和系统返回。
3. 原生弹层：底部弹层、上下文菜单、确认框、键盘避让和手势关闭。
4. 夜间模式：全局页面、状态栏、Tab、弹层、输入框、图片背景和系统栏一致。
5. 无数据状态：空列表、首次使用、无关注内容、无搜索结果。
6. 失败状态：离线、超时、401、403、404、422、429、5xx。
7. 页面恢复：从详情返回信息流时尽可能恢复原滚动位置和筛选状态。
8. 触控：所有核心按钮有可访问名称、点击区域和禁用状态。
9. 多语言：中文和英文文案不混乱，时间、数字、金额按地区格式化。
10. 版本兼容：升级 Expo / React Native 后所有原生模块重新执行构建和设备验收。

不得为了统一 UI 而引入第二套导航或第二套主题系统。

### 5.2 信息流 Feed

**目标：** 形成稳定、快速、可控制的多类型时间线。

必须覆盖：

- For You：基于当前已有推荐候选和权限结果展示内容。
- Following：关注关系时间线。
- Latest：按时间排序的内容入口；缺少权威 API 时先报告 API 缺口。
- Topic Feed：从话题标签、专题或主题进入内容流。
- Custom Feed：按用户选择的主题、作者或列表组合。
- Profile Feed：从用户主页查看其内容。
- Saved Feed：查看已收藏内容。
- Video Feed：保留当前独立视频流。

交互要求：

1. 首屏立即出现骨架或缓存内容，不等待头像、计数、所有媒体详情全部完成。
2. 分页使用 cursor，不使用无界 offset。
3. 刷新、加载更多、请求取消和重复请求去重。
4. 页面切换能恢复滚动位置。
5. 新内容提示不强制打断正在阅读的用户。
6. 帖子卡片统一呈现作者、时间、正文、媒体、话题、互动数量和菜单。
7. 隐藏、不感兴趣、屏蔽和静音应真实影响后续分发。
8. 删除、下线、不可见或会员专属内容必须按权威权限过滤。
9. 不允许通过前端重复请求大量作者详情或互动数据造成瀑布流。
10. 缓存只能存派生读模型；不得成为业务最终事实。

### 5.3 发帖 Composer 与内容生命周期

**目标：** 让用户能够在一个统一发布入口完成普通动态、媒体动态、投票、引用转发和线程等创作任务。

内容类型：

- 普通文字动态。
- 图片动态。
- 短视频动态。
- 投票动态。
- 引用转发。
- 多条连续线程。
- 回复 / 评论。
- 文章和长内容（复用现有文章体系，不重复建立文章模型）。

发布窗口要求：

1. 文字计数、媒体数量和媒体类型限制必须从现行产品/API 契约读取，不在多个页面硬编码不同规则。
2. 图片多选、预览、删除、顺序调整和封面设置。
3. 视频选择、上传进度、封面预览、失败重试和播放授权。
4. GIF 搜索、选择和插入；先验证授权来源、媒体服务和版权边界。
5. 原生拍摄入口；必须正确申请相机、麦克风和媒体权限。
6. 投票创建、选项管理、有效期、投票和结果显示。
7. 线程编辑器可增加、移除和重排子帖；部分失败能够恢复，不重复生成已成功内容。
8. 引用转发包含原帖预览和附加评论；原帖始终引用 W03 内容 ID，不复制正文。
9. 草稿自动保存和手动保存；草稿列表可恢复、删除和继续编辑。
10. 定时发布必须使用明确时区，服务端任务执行，APP 展示真实状态。
11. 编辑已发布内容应优先原地更新并保留原内容 ID、URL 和互动关系；不得默认通过下线后重新发布来伪装编辑。
12. 发布成功必须由服务端确认，并能从详情或 Feed 重新读取。
13. 超时后使用同一幂等请求恢复，不创建重复帖子。
14. 发布失败、上传失败、审核中、待发布和部分成功状态必须区分。

**验收重点：** 从打开发布窗口到媒体上传、提交、服务端确认、返回 Feed、重新打开详情，每一步均需验证。

### 5.4 互动、回复与引用转发

必须覆盖：

- Like / Unlike。
- Repost / Undo Repost。
- Quote Post。
- Reply / Nested Reply。
- Bookmark / Remove Bookmark。
- Share Link / Native Share Sheet。
- Pin / Unpin。
- Edit / Delete。
- Report / Block / Mute。

体验要求：

1. 交互立即反馈，避免按钮点击后等待整页刷新。
2. 网络失败后回滚到权威状态，并提供重试。
3. 连续点击或网络重放不得重复计数。
4. 数量更新使用明确的权威响应或派生计数，不自行推算最终总数。
5. 回复树支持父子关系、跳转原帖和返回上下文。
6. 回复排序提供已被 API 支持的选项；UI 不得显示无法实现的筛选。
7. 允许内容作者控制回复和引用范围，但实际授权必须由服务端验证。
8. 对引用、回复和转发保持原内容身份、作者和链接关系。
9. 举报、屏蔽和静音立即反馈，但必须确认服务端完成。
10. 已删除、被屏蔽或无权访问内容必须正确显示受限状态。

### 5.5 用户主页与社交关系

目标主页结构：

- Posts。
- Replies。
- Media。
- Articles。
- Videos。
- Likes（依据隐私策略显示）。
- Followers。
- Following。
- 置顶内容。
- 话题 / 兴趣信息。
- 会员或订阅身份（只有真实权益生效后才能显示）。

要求：

1. 主页资料、封面、头像、用户名、简介和链接使用现有身份 / 内容 API。
2. 用户名修改不得改变用户 ID 或内容 ID。
3. @Mention 点击必须解析到稳定 user_id / canonical identity。
4. 关注、取消关注、粉丝数和关注数不得只更新本地 UI。
5. 屏蔽、私密账号和账号限制策略在主页及所有内容列表中一致生效。
6. 分页和刷新不重复内容，不丢失置顶内容。
7. 空状态、隐私限制和账号不存在必须区分。

### 5.6 通知中心与系统推送

**目标：** 将站内通知和手机系统推送形成可靠闭环。

通知至少覆盖：

- 社交：关注、点赞、评论、回复、提及、转发、引用转发。
- 消息：私信、消息请求、群聊邀请。
- 创作者：新订阅者、订阅变化、会员互动。
- 商业：付款成功、付款失败、退款和账单状态。
- 内容：审核、发布、定时发布结果。
- 实时：直播 / Spaces 开始和活动提醒。
- 安全：新设备登录、密码和安全设置变更。

要求：

1. 站内通知 cursor 分页、单条已读、全部已读、未读总数。
2. Android 和 iOS 分别完成设备 token 注册、刷新、注销。
3. 推送权限拒绝时仍可正常使用站内通知。
4. 推送点击通过 App Link / Universal Link 打开正确内容或会话。
5. 用户可以管理通知类型、渠道和频率。
6. 屏蔽、静音、私密账号和通知偏好在投递前生效。
7. 高频通知聚合或折叠，不能对每个点赞都无界推送。
8. Push fan-out 异步进行；失败可重试、去重和清理失效 token。
9. 未读数和投递状态属于派生状态，遵循现有通知权威契约。
10. 不把“通知写入数据库”误认为“手机已收到推送”。

### 5.7 私信与实时消息

**目标：** 将当前占位私信页升级为可靠消息产品。

基础能力：

- 一对一会话。
- 群聊和成员管理。
- 消息请求及陌生人接收规则。
- 文字消息。
- 图片、视频和链接附件。
- 回复、引用、转发。
- 已发送、已送达、已读状态。
- 未读计数和会话置顶。
- 免打扰、归档、删除和举报。
- 会话搜索、消息历史 cursor 分页。
- 在线状态和正在输入（仅在服务端能力支持时）。
- 断线重连、发送重试和重复消息去重。
- 跨设备消息一致性。

安全要求：

1. 会话参与者、消息读取和附件访问每次都进行服务端授权。
2. Block / Mute / 私密账号 / 陌生人请求规则必须一致。
3. 管理员不能默认读取私人消息内容。
4. 消息顺序、sequence、幂等键和离线恢复必须有清晰语义。
5. 不依赖 exactly-once 投递假设。
6. 未送达、失败和发送中状态必须区别显示。
7. 会话删除、消息删除和保留策略必须符合当前隐私及数据生命周期契约。
8. 不创建新的 Messaging Worker / D1 / Queue；如果 docs/56 中的 Messaging Domain 尚未映射到当前 Worker 的真实权威代码和 API，先做最小合同对齐，停止 UI 假实现。
9. WebSocket / Durable Object / Queue 仅在现有架构允许并且已有资源边界可承载时使用；不得把新实时基础设施直接塞进 APP。

### 5.8 创作者工作室与订阅经营

**目标：** 用户在 APP 内可以完成创作者经营，而不仅是购买会员。

创作者首页：

- 浏览量、互动量、粉丝数、订阅人数。
- 内容表现趋势。
- 收入总览、待结算、可结算和已支付状态。
- 订阅增长、续费和流失趋势。
- 快速发布、管理内容和查看评论。

内容管理：

- 动态、文章、短视频分类。
- 草稿、已发布、审核中、定时发布、已下线。
- 编辑、删除、归档和恢复（按领域契约）。
- 文章系列、合集、专题和内容关联（复用已有内容结构）。

订阅管理：

- 创建和管理会员套餐。
- 订阅者列表和状态。
- 会员专属内容。
- 会员标识与会员互动权益。
- 续费、取消、到期、付款失败和恢复。
- 付款历史、退款、账单和支付方式。
- 创作者收入和结算状态。

数据来源规则：

- 内容事实来自 W03。
- 社交关系来自 W05。
- 订阅、订单、付款、退款和商业权益来自 W07。
- 分析和聚合指标来自 W11 或现行被认可的派生分析接口。
- 不通过客户端把浏览量或支付回调推算成收入。
- 不重复开发 W07 支付、订阅、退款和会员权限。

### 5.9 搜索、话题与发现

**目标：** 同时具有 X 的搜索精准度和 Threads 的兴趣发现体验。

基础搜索类型：

- Top / 综合。
- Latest / 最新。
- People / 用户。
- Posts / 内容。
- Photos / 图片。
- Videos / 视频。
- Topics / 话题。
- Creators / 创作者。
- Communities / 社群（模块上线后）。

高级筛选：

- 精确短语。
- 包含词 / 排除词。
- 指定作者。
- 指定提及对象。
- 指定回复对象。
- 时间范围。
- 内容类型。
- 主题标签。
- 语言和可见性（受权限约束）。

发现体验：

- 搜索建议。
- 搜索历史与清除。
- 热门搜索。
- 推荐话题。
- 主题详情和主题 Feed。
- 用户兴趣标签。
- 主题相关创作者。
- 从搜索结果返回时恢复关键词和筛选状态。

搜索索引仅为派生索引，不能绕过原始内容、账号和会员权限。复用现有 Meilisearch / 搜索适配器时必须遵守 docs/53。

### 5.10 自定义 Feed 与 Lists

自定义 Feed：

1. 用户可以选择主题、用户或现有列表组成 Feed。
2. 可以创建、编辑、排序、置顶和删除自定义 Feed。
3. 只有具备公开分享契约时，才显示公开分享和分享链接。
4. Feed 切换应保持各自滚动位置和刷新状态。
5. 不在 APP 内保存独立于服务端的权威 Feed 关系。

Lists：

- 创建公开或私有列表。
- 添加和移除用户。
- 查看列表成员。
- 关注 / 取消关注其他公开列表（若当前领域支持）。
- 列表独立时间线。
- 列表置顶、排序和分享。
- 私有列表成员与内容必须执行资源授权。

Lists 与自定义 Feed 是不同产品概念；不得仅用一个本地数组冒充两个服务端功能。

### 5.11 Communities 社群

目标：围绕主题或兴趣建立公开讨论空间。

基础能力：

- 社群发现、加入、退出。
- 社群主页、规则和成员。
- 社群内容 Feed。
- 社群帖子和讨论。
- 管理员 / 版主 / 成员角色。
- 加入审核（如产品规则要求）。
- 社群举报、内容治理和成员处罚。
- 社群通知、静音和退出。
- 主题徽章或身份标签（只有真实服务端权益时）。

治理要求：

1. 社群管理员权限由服务端授权。
2. 社群规则、审核和处罚必须与 W06 治理系统对齐。
3. 不能以客户端隐藏按钮代替服务端权限。
4. 不得为社群建立平行的 User、Content 或 Moderation 数据源。
5. 社群 API 未就绪时只登记阻塞项，不生成假社群页面。

### 5.12 视频生产与播放

当前视频 Feed 已有代码，不重新开发视频 Feed。重点是完善端到端生产和播放：

- 原生拍摄和相册选择。
- 上传进度、断网恢复和单文件重试。
- 视频封面选择。
- 裁剪和时长限制。
- 字幕和字幕轨道。
- 视频播放进度、继续播放和全屏。
- 画质选择或自适应播放（依现有媒体能力）。
- 弱网和播放错误恢复。
- 评论、点赞、关注、转发、收藏和分享。
- 付费内容播放授权。
- 创作者视频管理和播放分析。

媒体只通过现有媒体服务和授权播放 API 获取，不能从 storage key 推断公开 URL。视频处理能力必须先检查当前媒体服务契约和基础设施。

### 5.13 Spaces / Live

作为 P2 单独规划，不得混入普通 IM 或普通视频 Feed。

目标能力：

- 创建音频房间或直播活动。
- 主持人、联合主持人、听众。
- 申请发言、批准发言、静音和移除成员。
- 房间分享和活动通知。
- 实时状态和参与者列表。
- 结束、回放和内容关联。
- 主持人权限、举报、风险和审核。
- 网络中断和 RTC 故障降级。

必须遵守 docs/56 中 Live 与 IM 的边界。LiveKit 只能作为实时音视频传输基础设施，不能成为 LuckRead 用户、内容、订阅或消息的业务权威。若当前生产部署没有经过验证的 RTC 服务和授权流程，先做可行性审计，不做假直播入口。

### 5.14 AI 辅助能力

AI 属于 P2 差异化增强，不是核心社交功能上线的阻塞条件。

可评估：

- 搜索结果摘要。
- 长线程摘要。
- 文章和视频摘要。
- 写作建议和标题建议。
- 内容多语言翻译。
- 创作者数据解释。
- 用户明确触发的内容理解。

要求：

1. 必须由获准的 AI 服务或现有 API 提供。
2. 尊重内容权限、私密账号、会员内容、私信隐私和版权边界。
3. 不将私人消息或未公开草稿发送给未授权服务。
4. AI 输出必须标明生成属性，不可伪造事实或数据。
5. 不新增 Worker 或数据库来制造第二套 AI 数据源。
6. 费用、速率、模型、隐私和失败降级单独审查。

## 6. 分阶段交付路线图

路线图是建议执行顺序。每个子模块必须单独审计、单独 PR、单独验收。不得因为路线图写在同一文档，就一次性批量开发。

### Phase 0 — 基线冻结与复用审计

**目的：** 确定真实缺口，避免重做。

工作项：

1. 获取最新 main SHA 和所有开放 PR。
2. 对 APP 路由、组件、API adapters、测试和当前依赖做模块映射。
3. 对照现有 W01 / W02 / W03 / W05 / W06 / W07 / W10 / W11 契约。
4. 检查 H5 / PC 对应能力，复用现有页面和接口。
5. 对四个已授权 GitHub 项目做源文件、许可证、依赖、测试和兼容性审计。
6. 为每个功能标记 VERIFIED_COMPLETE / CODE_PRESENT / PARTIAL / MISSING / BLOCKED / BROKEN / DEFERRED。
7. 输出去重后的模块顺序和每个模块的最小交付范围。

**退出条件：** 有可追溯的功能矩阵、API/权限映射、复用来源审查和待办模块清单。不得因 Phase 0 尚未完成而声称全功能已经审计完毕。

### 7.2 上游代码必须通过的验证门槛

任一新增复用源，必须同时完成以下检查：

1. **许可证：** 明确 SPDX / LICENSE 文件及适用范围。无许可证、许可证缺失或授权不清楚时不得复制。
2. **维护情况：** 检查最近提交、维护者活动、开放 Issue、归档状态和依赖更新。
3. **可运行性：** 本地按上游文档安装并运行，不能只看 README 和截图。
4. **测试证据：** 检查单元测试、集成测试、E2E 和 CI；关键流程必须实际执行。
5. **构建证据：** 确认目标平台构建成功；React Web 构建成功不代表 React Native 构建成功。
6. **安全：** 检查依赖风险、硬编码密钥、上游 API、鉴权和数据泄露风险。
7. **兼容性：** 核验 LuckRead 当前 Expo / React Native / Android / iOS 目标版本。
8. **数据边界：** 只允许复制呈现层、状态交互组件或被批准的通用工具；不得迁入上游业务数据库和权限逻辑。
9. **移植范围：** 明确源路径、目标路径、依赖、样式、许可文件和最小改动。
10. **回归：** 在 LuckRead API 和真实权限下验证，而非使用上游 Demo 数据。
11. **性能：** 检查列表虚拟化、图片加载、渲染次数和内存。
12. **可访问性：** 检查键盘、屏幕阅读器、点击区域、动态字体和系统主题。

只有以上证据齐全，才允许把代码标记为 VERIFIED_REUSE。否则标记 REFERENCE_ONLY 或 BLOCKED。

## 8. 前端与 API 约束

### 8.1 单一 API 边界

- APP 只调用 W01 暴露并通过契约的公开 API。
- H5 / PC 继续调用相同权威业务 API。
- 不从 APP 直连 D1、R2、W05、W07 等内部绑定。
- 不根据 Worker 内部实现自行拼接 URL。
- 不复制上游 Firebase / Express / Supabase API。
- 不在多个页面复制相同的请求、DTO 解析和状态规则。

### 8.2 API 交互标准

每个写接口必须核对：

- 身份验证和 Session。
- 资源所有权和权限。
- 输入校验和稳定错误码。
- 幂等键。
- 版本控制 / If-Match（若当前 API 契约要求）。
- 请求 ID。
- 超时、取消和重试策略。
- cursor 分页。
- 速率限制和反滥用策略。
- 成功后的权威重新读取。
- 错误状态是否可以安全重试。

不得因上游组件要求而改变 LuckRead API DTO。使用 adapter 把 LuckRead DTO 转成组件需要的展示模型。

### 8.3 API 缺口处理流程

如果前端要实现某能力而当前 API 缺失：

1. 搜索当前 W01 路由、Worker client、OpenAPI、测试和线上运行证据。
2. 检查是否已有同义 API 或可以复用的领域能力。
3. 确认谁是领域权威及权限归属。
4. 评估最小 API 增量和向后兼容。
5. 提交 API / 权限 / 数据契约变更提案，注明所需 Worker 和 D1，但不得新增资源。
6. 在合同和 API 通过后再开发前端。

禁止创建只有 APP 使用的私有写接口，禁止通过本地数据库补齐服务端缺失能力。

## 10. 性能与可靠性目标

性能以真实设备、真实 API 和可重复的测试场景为准。以下为本项目初始目标，Phase 0 必须记录基线，若某设备或网络条件不适用，需在模块 PR 说明原因和实际结果。

| 项目 | 初始目标 / 要求 |
|---|---|
| 用户点击反馈 | 本地按钮状态和触摸反馈不等待网络；目标在 100ms 内可感知 |
| 页面加载 | 立即呈现骨架或缓存状态，禁止长时间纯白屏 |
| 首屏 Feed | 优先显示首批内容，不等待所有头像、计数和媒体详情 |
| 信息流滚动 | 支持稳定虚拟列表，避免大量图片同时解码和无界列表渲染 |
| 图片 | 渐进加载、尺寸约束、缓存策略和失败占位 |
| 视频 | 首帧、缓冲、错误重试和后台暂停策略有明确行为 |
| API | 记录 requestId、页面耗时和失败率；慢请求可定位到 API / 图片 / 媒体阶段 |
| 内存 | 页面切换后取消无用请求、释放播放器和大媒体资源 |
| 弱网 | 保留可恢复输入和重试路径；不能重复提交 |
| 离线 | 明确只读缓存边界；不得把本地缓存当作已成功的业务写入 |

上线前必须基于真实设备测量首屏、列表滚动、图片、视频、内存和 API 的 P50 / P95。不能仅用开发模拟器或一次成功演示宣称达到大厂性能标准。

## 11. 安全、隐私和治理

每个模块必须验证：

- 登录态和 Session 失效。
- 未登录、已登录、不同权限层级。
- 内容所有者与非所有者。
- 公开、私密、会员专属和已限制内容。
- Block / Mute / 举报 / 审核限制。
- 附件签名 URL 和访问过期。
- 防止未授权的用户、消息、内容和账单读取。
- 不把 token、密码、支付数据或私信正文写入日志。
- 本地凭证仅使用已有安全存储方案。
- 用户注销后清理本地敏感 Session 和相关缓存。
- 删除、撤回、归档和保留策略遵守现有领域契约。
- Android / iOS 权限仅在需要时请求，并提供明确用途说明。

不得为提高互动率而减少用户对隐私、通知、内容可见性和屏蔽的控制。

## 12. 测试与真实验收

- 首次进入。
- 加载中。
- 有数据。
- 无数据。
- 服务端错误。
- 网络超时。
- 离线。
- 登录过期。
- 权限不足。
- 连续点击。
- 同一请求重试。
- 页面退出和重新进入。
- 系统深色模式。
- 弱网和媒体加载失败。

## 14. 每轮开发与 PR 工作流

每个模块严格遵循：

1. 读取 main 最新提交和开放 PR。

4. 明确本轮只处理一个模块。
5. 写出本轮目标、非目标、文件范围和验收条件。
6. 建立独立分支。
7. 实现最小必要变更，优先复用现有组件和依赖。
8. 执行模块相关测试、构建和 API / 设备验收。
9. 由 PR 展示源文件复用、许可证、测试证据和差异。

12. 合并后验证 main 和部署状态；如需要部署，提供准确 Worker / APP 构建及工作流参数。
13. 模块交付后立即停止，提交简明报告：本轮完成什么、PR、测试、部署情况、仍缺少什么、剩余模块数量。
14. 等待负责人明确发出“继续”，不得自动推进下一模块。

### 14.1 PR 范围

- 一个 PR 对应一个模块或一个完整垂直功能闭环。
- 纯重构必须有明确功能收益或测试必要性。
- 不把文档、依赖升级、样式翻新和业务 API 变更无关地混在同一个 PR。
- 不因为多个模块共享组件就把多个产品功能捆绑交付。
- 不绕过 main 分支保护和必要的工程审核。

## 17. 本项目首批模块的建议顺序

基于当前 main 的静态代码审计，建议的首批执行顺序如下：

| 顺序 | 模块 ID | 模块 | 为什么优先 |
|---:|---|---|---|
| 1 | APP-UX-001 | APP 核心信息流和互动真机验收 | 复用已有功能，先消除基础体验缺陷 |
| 2 | APP-PUBLISH-001 | 引用转发、线程、草稿与安全编辑差距收口 | 提升日常内容生产能力；先去重 PR #1510 |
| 3 | APP-NOTIFY-001 | 系统推送闭环 | 让用户能及时回访 |
| 4 | APP-IM-001 | 私信基础链路 | 当前 APP 明确不可用，是最大核心社交空白 |
| 5 | APP-CREATOR-001 | 原生创作者工作室入口和总览 | 将订阅、内容和收入经营带入 APP |
| 6 | APP-DISCOVERY-001 | 搜索筛选与主题发现 | 补齐 Threads 风格兴趣发现 |
| 7 | APP-FEED-001 | 自定义 Feed | 形成可控的信息流体验 |
| 8 | APP-LISTS-001 | Lists | 扩展关系组织和信息流 |
| 9 | APP-COMMUNITY-001 | Communities | 建立主题社群 |
| 10 | APP-VIDEO-CREATOR-001 | 视频生产体验 | 完成从创作到播放的数据闭环 |
| 11 | APP-LIVE-001 | Spaces / Live | 独立实时系统，技术和治理成本较高 |
| 12 | APP-AI-001 | AI 辅助体验 | 差异化增强，不阻塞核心社交产品 |

此顺序是建议基线。Phase 0 发现某项已被新 PR 或生产能力完成时，应将其标记为 VERIFIED_COMPLETE 并从实施队列剔除，不要重新开发。

## 19. 契约生效后的最终原则

LuckRead 的目标不是“把 X 的页面换一个 Logo”，而是建设一个同时具备 X 的高效公共互动能力和 Threads 的主题、兴趣、社群与对话质量的社交产品。

工程执行必须遵循：

**先查已有实现，后确认缺口；先找成熟代码，后写最小集成；先通过许可证和质量验证，后复制；先确认 API 和权限，后开发页面；一个模块一个 PR；完成马上停止；真实验收后再宣布完成。**

任何人不得仅因为本契约列出某个功能，就认定该功能已经存在、可以立即部署或可以绕过现有架构实现。

**当前结论：本文件只建立目标体验、工程边界和分阶段执行规则。它本身不代表私信、推送、社群、Lists、Spaces、AI 或创作者中心已经开发完成。**
