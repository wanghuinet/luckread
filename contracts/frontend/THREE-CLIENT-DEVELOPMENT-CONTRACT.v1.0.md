# LuckRead APP / H5 / PC 三端开发契约 v1.0

**状态：ACTIVE / 强制执行 / 开发准入契约**  
**适用范围：** React Native APP、H5、PC Web 的全部页面、组件、状态管理、API 调用和相关服务端实现。  
**权威依据：** 现有 Blueprint、领域契约、Worker Binding / Service Binding 契约、API 契约及已批准的 Change Control。本文只收紧三端开发边界，不替换上位契约、不创建新架构。

> **开发原则：任何功能先符合本契约，再允许编码、合并和发布。代码已经存在、页面可显示或接口返回成功，都不能代替契约符合性证据。**

## 0. 契约优先级与冲突处理

遵循：

`Blueprint → 领域/API/传输契约 → 已批准的 Change Control → 本三端契约 → 实现与测试`

如果本契约与更高优先级的现有契约冲突，必须暂停该功能开发并提交冲突证据；禁止自行选择一种实现、绕过契约或先上线再补手续。任何架构边界例外必须先取得明确批准并完成 Change Control。

## 1. API-001：统一入口——APP、H5、PC 只使用 W01 对外 API

### 强制规则

1. APP、H5、PC 的业务请求统一经过 **W01 暴露的公开 API**。W01 是三端对外入口和路由边界，不因为入口身份自动取得其他领域的数据写权限。
2. 锁定的公开 API 地址形式为 `https://api.luckread.com/v1/...`。三端不得各自引入另一套公开 API 主机、路径版本或平行请求层；W01 内部路由路径可按现有实现映射，但内部路径不是对外契约。
3. 每端必须复用该端已有的统一 API client / transport。业务页面、组件和状态管理不得自行创建平行网络客户端、绕开公共 transport 或复制一套认证、错误处理、重试和写请求幂等逻辑。
4. 前端不得直接连接任何 D1、其他数据库、数据库代理或数据库管理端点；不得持有数据库凭证、D1 binding、SQL client、私有服务凭证或用于绕过 W01 的 Worker 内部地址。
5. 前端不得绕过 W01 直接调用 W02–W12 的内部 Service Binding、内部 Worker 服务 URL 或领域私有接口。跨 Worker 调用仅由已授权的服务端入口按现有契约完成。
6. 上传/下载媒体二进制是受控的数据传输例外，不是业务 API 入口例外：客户端必须先通过 W01 现有 API 获取契约允许的上传授权、对象引用或播放地址；不得由客户端创建媒体权威记录、推断权限或绕过现有 `img.luckread.com` / `video.luckread.com` 交付与访问策略。
7. 三端对同一业务动作遵守同一 API 契约、DTO、权限判定、状态机、分页/排序语义和错误语义。不得为单一页面私自改变业务规则、伪造后端成功态或用 UI 状态代替服务端权威事实。

### 禁止事项

- 页面/组件直接读写 D1 或其他数据库。
- APP、H5、PC 各自维护不同的业务 API 地址规则。
- 为绕开权限或缺少的 API 而直接访问领域 Worker、Payload 内部模型或数据库。
- 以隐藏按钮、前端路由保护、客户端角色字段或本地缓存代替服务端鉴权。
- 在缺少 API 契约时猜测 endpoint、DTO 字段、权限或业务结果。

## 2. AUTHORITY-001：统一数据权威——数据由既有职责 Worker 负责

### 强制规则

1. 每一类业务事实只有一个权威写入方。APP、H5、PC、W01 网关、缓存、事件、分析投影和搜索索引都不得成为第二个事实来源。
2. W01 负责公开 API 入口、网关编排和现有 Payload/CMS/API 边界；W01 通过**已经批准并部署的 Service Bindings 与传输契约**调用有权威职责的 Worker。W01 的公开入口身份不能改变领域归属。
3. 按当前 Worker 职责路由，不得按页面方便与否选择数据库或写入方：

   | Worker | 权威职责边界 |
   |---|---|
   | W02 | 身份、账号、会话、凭证与授权事实 |
   | W03 | 内容、文章、媒体、翻译等内容域事实 |
   | W04 | 信息流、推荐、搜索及其获准的派生结果 |
   | W05 | 社交、社区、私信/消息、通知等社交域事实 |
   | W06 | 权利、信任与安全、治理及处置事实 |
   | W07 | 订阅、交易、支付、商业化事实 |
   | W08 | 创作者、组织及对应资格/关系事实 |
   | W09 | 平台、存储与可靠性能力边界 |
   | W10 | 既有 Queue / Job 异步执行能力，不拥有业务事实 |
   | W11 | 增长、活动、分析与运营派生数据；不得取代源领域事实 |
   | W12 | 外部开发者与集成执行边界 |

4. 写入必须进入对应权威 Worker 的已批准 API/传输接口；读取也必须遵循现有权威、访问权限和投影契约。禁止跨 Worker 直接查库、越权写表、复制业务表或用影子表形成第二权威。
5. Payload 内部模型、缓存、统计表、事件记录和读模型只能按既有契约作为实现或派生投影；不得被三端作为绕过 W01 的公开业务接口。Payload 不得取代 W02 的平台身份/授权权威，也不得取代 W03 的内容域权威。
6. 不新增 Worker、D1、Queue、Service Binding 或另一套数据访问层来规避当前契约。确需拓扑变更时，必须先经过 Change Control 并完成对应映射、权限、迁移和验证门槛。

## 3. ASYNC-001：异步化与缓存——同步返回、派生处理分界清晰

### 异步处理

1. 用户当前请求必须立即获得结果的核心校验、鉴权、权威状态变更及其必要响应保持同步；不能把必要的业务提交伪装成“已成功”后再异步补写。
2. 不要求当前请求等待完成的统计聚合、分析计数、通知扇出、搜索/推荐投影、缓存预热与派生视图更新，使用**现有且已批准的 Queue / 异步执行路径**。
3. 异步消息和消费者必须遵守现有事件契约，具备幂等/去重、重试、重复和乱序投递容忍、失败可观测与既有死信/恢复流程。消费事件不等于获得业务事实写权限。
4. 不得新增 Queue 或自建并行异步系统。若既有契约尚未覆盖该任务，先补齐并批准契约，再编码。

### 缓存与查询

1. 热门公开内容、公开资料、热门搜索词及其他适合缓存的公开读数据，应优先使用现有 Cloudflare 缓存/缓存机制，减少重复 D1 查询与不必要的源服务扇出。
2. 缓存是可重建的性能层，不是数据权威。缓存键、TTL、失效/更新路径必须与相应领域和访问策略一致；权威数据更新后，使用现有同步失效或 Queue 派生更新路径。
3. 私有、敏感或依赖当前用户权限/订阅/封禁/可见性/版权状态的响应，不得进入不区分用户和权限上下文的共享公共缓存。缓存命中不能覆盖当前权威鉴权结果。
4. 缓存未命中时必须回到获准的 API/权威读路径，并遵守现有查询预算；不得为填充缓存而让三端直接查询 D1。
5. 热门搜索词统计、内容统计和通知计数等派生更新不得在每次页面读取时重复写 D1；按现有异步与投影约定聚合处理。

## 4. REVIEW-001：每个功能的开发准入与验收

每一个涉及 APP、H5、PC 或其 API 的功能 PR，必须在描述和测试证据中回答：

- **统一入口：** 三端调用的 W01 API、公开路径和 API 契约是什么？使用哪个已有的统一 transport？
- **数据权威：** 写入/读取由哪个 Worker 拥有？W01 到权威 Worker 使用哪个现有 Service Binding / 传输契约？是否产生了第二数据源？
- **同步/异步：** 哪些结果必须同步返回，哪些派生工作走现有 Queue？如何保证幂等、重试和失败恢复？
- **缓存：** 是否需要缓存？公开/私有类别、缓存键、TTL、失效路径与权限检查是什么？
- **三端一致性：** APP、H5、PC 是否遵循相同业务语义、权限和错误处理？各自相关测试是否通过？
- **证据：** 至少包含目标测试与代码检查结果；涉及线上行为时补充真实 API/运行时验收，不得把“代码已合并”写成“线上已验证”。

### 合并阻断规则

只要出现以下任一情况，该功能即为 **BLOCKED / 不得合并或发布**：

- 违反 API-001、AUTHORITY-001 或 ASYNC-001；
- 所需 API、权限、领域写入方或事件语义未确认，却靠猜测继续实现；
- 引入绕过 W01 的数据库访问、另一套业务 API、未经批准的 Worker 调用或重复事实来源；
- 使用缓存覆盖权威事实/当前鉴权，或用异步投影冒充已完成的权威操作；
- 缺少必要的测试或验收证据。

**本契约是开发准入规则，不是建议清单。** 例外必须在实现前获得明确批准并完成必要的 Change Control；PR 说明、临时开关、注释或事后补文档不能自行豁免。
