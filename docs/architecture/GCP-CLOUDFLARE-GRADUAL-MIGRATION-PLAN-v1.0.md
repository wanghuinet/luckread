# LuckRead Cloudflare + GCP 渐进式迁移执行方案 v1.0

**状态：PROPOSED FOR REVIEW（评审通过前仅是执行方案，不授权生产切流）**  
**目标：内容权威与媒体分发继续留在 Cloudflare；非内容域中高 CPU、数据库密集型的业务逐步迁移到 GCP。**  
**适用仓库：** `wanghuinet/luckread`  
**运行时影响：** 本文档提交不修改 Worker、API、数据库绑定或生产基础设施。

## 1. 目标与迁移原则

LuckRead 采用“Cloudflare 内容与边缘层 + GCP 非内容业务计算与数据库”的长期混合架构：

- **Cloudflare 保留**：W03 内容权威、现有内容数据、R2 原始媒体和派生媒体、全球 CDN、边缘缓存，以及维持既有公开 API 兼容性的轻量入口。
- **GCP 承载**：非内容域的高 CPU 计算、主要关系型数据库读写、社交关系、治理运行状态、订阅与交易、身份域（在最后阶段迁移）、推荐/搜索/信息流服务、分析及批处理。
- **跨云边界**：通过有认证的服务 API 和可靠事件契约通信。GCP 不直接绕过 W03 写入内容数据库，也不把内容正文或原始媒体复制为新的权威副本。
- **对外兼容**：H5、Android、iOS、PC 仍使用现有 LuckRead 公共 API、DTO、错误格式、游标和身份语义。迁移计算位置不等于公开 API 改版。
- **渐进切流**：先盘点和影子验证，再按业务域切换；每个域同一时刻只有一个权威写入源。不得用无事务保障的应用层“双写”假装零停机。
- **成本优先**：先使用 Cloud Run + Cloud SQL for PostgreSQL 的最小可行组合；只有负载、查询形态或隔离要求有证据证明需要时，才加入 Memorystore、BigQuery、独立计算实例或其他托管服务。

该方案明确的是长期目标及切换控制。它不表示当前所有 Worker 已具备可迁移的完整业务实现，也不代表 GCP 资源已经创建、压测或获准接管生产流量。

## 2. 从当前主分支确认的事实与迁移前置门

以下事实来自当前仓库代码/配置；配置文件存在不等于生产资源已验证可用。

1. 仓库维护 12 个逻辑 Worker，目录包括 W01–W12。
2. W03 的职责是内容权威；内容正文、内容状态与媒体对象继续遵循既有 W03 / D1 / R2 边界。
3. W04 的目录为 `workers/W04-feed-search`。其 README 明确说明当前切片没有 D1 绑定、只存派生账户状态投影，并且 Feed / Recommendation / Search 业务 API 尚未完整实现；因此必须先满足其功能准入和运行时验收，再切换到 GCP，不能把迁移当作功能已经完成的证据。
4. W05 的目录为 `workers/W05-social`，其社交关系与互动数据属于 W05 领域；交易、变现权威属于 W07。
5. W11 的目录为 `workers/W11-growth-campaign-analytics-operations`，README 将 D1-05（`allluck`）定义为分析派生数据域，禁止用它成为 W03 内容或 W05 社交实体的权威源。W11 Wrangler 文件中存在 `D1_05` / `allluck` 绑定与数据库 ID，且已有分析事件、聚合、重建和迟到事件相关迁移。
6. `docs/00-CURRENT-GATE-STATUS.md` 与 GCP 兼容性变更控制记录中仍把 D1-05 的物理准入/运行时证据或 GCP 迁移准入标记为待完成/受门禁控制。**在继续之前必须对照当前 HEAD、真实 Cloudflare 资源、CI 证据和部署状态解决该记录与 Wrangler 配置之间的差异。不得仅凭绑定文本宣称线上数据库已经就绪。**
7. `contracts/database/cloudflare-d1-pg-portability.v1.json` 是 D1 → PostgreSQL 的数据便携性合同；`contracts/capability/reconciliation-batches/AK-postgresql-gcp-portability.v1.json` 当前状态为 `NOT_GREEN`。PG-001 至 PG-009 的能力门禁必须按现有合同和当前状态处理，不能通过本方案直接标绿。

### 2.1 迁移前必须生成的代码证据

在任何生产数据复制或流量切换之前，由实际实现分支生成并评审以下证据：

- 每个 Worker 的当前入口、调用方、服务绑定、队列消费者、D1/KV/R2 绑定。
- 每张待迁移表的 owner、权威写入 API、所有读写调用方、数据量、索引、约束、保留期、删除规则、敏感级别及 ID 格式。
- 每个业务域的事件生产者、事件 schema/version、幂等键、重试 / DLQ / replay 路径。
- API 级基线：成功率、错误率、p50/p95/p99、QPS、CPU、数据库读写/锁等待、缓存命中率、跨云流量成本。
- 实际主分支、现存 PR、工作流、当前绑定和部署状态。文档中的目录/角色说明不得替代代码证据。

## 3. 目标部署形态

```text
H5 / Android / iOS / PC
          |
          v
Cloudflare Edge / W01 兼容 API 层
   |                          |
   | 内容请求                 | 非内容域请求
   v                          v
W03 Content + D1 + R2     GCP Cloud Run 服务
(内容权威仍在 CF)         - Feed / Search / Recommendation
                         - Social / Governance / Operations
                         - Subscription / Commerce
                         - Identity（最后阶段）
                         - Analytics / Batch
                                   |
                                   v
                         Cloud SQL for PostgreSQL
                         - 按领域隔离 schema / DB role
                         - 事务业务数据与在线投影
                                   |
                         +---------+---------+
                         |                   |
                         v                   v
                    可靠事件处理         可选分析仓库
                    Pub/Sub 等            BigQuery
                    （获准后使用）         （按量引入）
```

### 3.1 GCP 服务选择

| 能力 | 首选落点 | 边界 |
|---|---|---|
| 在线业务 API、CPU 密集逻辑 | Cloud Run | 按现有领域契约分组部署，不要求一个 Worker ID 对应一个独立服务 |
| 非内容在线关系型数据 | Cloud SQL for PostgreSQL | 私网优先；独立数据库角色、最小权限、备份与恢复测试 |
| 事件传输/异步消费者 | 当前已批准传输链路先保留；后续可评估 Pub/Sub | 新增 GCP 基础设施必须单独通过安全、可靠性、成本及部署门禁 |
| 批处理/重建/回填 | Cloud Run Jobs 或受控任务执行 | 必须可暂停、恢复、重试、限速和审计 |
| 热点缓存 | 先复用 Cloudflare Cache；有实测依据时再评估 Memorystore | 缓存不是授权边界，也不是唯一事实源 |
| 长期行为分析 | 先通过 W11 在线投影验证；历史分析负载需要时再评估 BigQuery | 不用分析仓库处理高频在线事务 |
| 日志、指标、追踪、密钥 | Cloud Logging / Monitoring / Trace / Secret Manager | 密钥不入代码、日志、客户端或公开配置 |
| 媒体对象 | Cloudflare R2 | 本方案不迁移原始图片、视频、附件和内容正文对象 |

Cloud Run 应通过受控连接访问 Cloud SQL；连接池、并发上限、最大实例数、连接数上限和迁移作业限速必须一起设计，避免扩容导致数据库连接耗尽。Cloudflare 侧不保存长期数据库账号，也不在每个边缘请求中直接创建 PostgreSQL 连接。

### 3.2 网络与服务身份

- Cloudflare → GCP 的所有服务请求使用专用服务身份、短时凭据或经过评审的签名请求；每个调用需要 request/correlation ID、超时、限流与可审计身份。
- GCP → Cloud SQL 走受控网络和 Cloud SQL 支持的连接方式；数据库不因跨云迁移而暴露给任意公网客户端。
- 如采用 Cloudflare 到 GCP 私有网络的连接方式，必须先验证区域、路由、连接限制、故障模式与费用；没有通过验证前使用受认证的 HTTPS 服务边界，不在 Worker 中直接放入数据库连接串。
- 秘密在 Secret Manager 或受支持的密钥管理系统中保存，并制定轮换、泄露和回收流程。

## 4. 数据所有权与目标归属

“非内容数据搬到 GCP”按**领域和表所有权**实施，而不是直接把一个混合 D1 整库迁走。尤其不能把同时包含内容和社交数据的 D1-02 整体迁移后破坏 W03 内容权威。

| 领域 / Worker | 目标计算位置 | 目标数据策略 | 迁移顺序 |
|---|---|---|---|
| W01 API / BFF | Cloudflare 保留轻量入口；重计算交给目标服务 | 不成为新的业务事实源；公共 DTO 不变 | 全程保留兼容性 |
| W02 Identity / Better Auth | 入口与身份流程先保持稳定，后期将获准的计算/持久化迁入 GCP | 保留账号 ID、验证状态、会话/凭据安全、角色授权语义；不得复制出两个账号权威源 | 最后阶段 |
| W03 Content | Cloudflare | 内容正文、发布状态、版本与内容权威留在 Cloudflare；R2 继续保存媒体 | 不迁移内容权威 |
| W04 Feed / Search / Recommendation | GCP Cloud Run | 在 GCP 构建可重建的排序、候选、搜索和用户兴趣投影；内容详情通过 W03 既有/获准 API 获取 | 先完成当前缺失的 serving 准入，再迁计算 |
| W05 Social | GCP Cloud Run | 仅迁移明确由 W05 拥有的关注、点赞、转推、评论等社交数据；内容 ID 保持为跨域引用 | W04 之后 |
| W06 Governance / Risk | GCP 为主要非内容计算目标 | 治理案例、风控/审计运行数据按表所有权和留存规则迁移；内容审查结果仍经 W03 权威状态流转 | 按风险及合规门禁 |
| W07 Subscription / Commerce | GCP Cloud Run + PostgreSQL | 订单、订阅、权益、账务/结算按各自权威合同迁移；不可把分析指标当财务事实 | 高风险专项波次 |
| W08 Creator | GCP 处理非内容业务和读写；W03 仍保存内容实体 | 创作者资料/运营投影与文章、媒体正文分开，保留关联 ID | 中后期 |
| W09 Platform | GCP | 非内容运维状态、配置、任务运行信息按域拆分迁移 | 中后期 |
| W10 Async | GCP 运行非内容重计算与批量任务；过渡期间使用当前可靠传输链路 | 重放、幂等、DLQ、补偿与任务状态可审计 | 分阶段迁移 |
| W11 Analytics | GCP | 在线派生表进入 PostgreSQL；历史大规模聚合再决定是否进入 BigQuery；保持可重建 | 第一阶段试迁域 |
| W12 Developer Integration | GCP 处理 CPU/DB 密集型服务 | 应用注册、配额、调用审计按合同迁移，API credential 与密钥重新托管 | 中后期 |

这张表规定目标，不授权跨领域改表。每次迁移都必须通过表级 mapping 与 domain owner review。

## 5. 数据划分：权威事实、派生投影和内容引用

### 5.1 继续留在 Cloudflare 的数据

- 文章/动态/视频等内容正文、修订、发布及下架状态。
- 作为 W03 权威内容模型一部分的内容元数据和发布工作流。
- R2 对象以及必要的媒体元数据、对象生命周期和签名访问边界。
- 内容访问必须经过既有权限与可见性判断；缓存命中不能代替授权。

### 5.2 可迁移至 GCP 的非内容数据

- W05 所有的社交关系、互动和可变状态。
- W02 所有的身份数据（安排在后期，单独做身份/会话安全验收）。
- W06/W07/W08/W09/W10/W12 各自拥有的非内容业务数据及运行状态。
- W04 的排序特征、候选集、用户兴趣、索引及其他可重建投影。
- W11 的已验证事件、聚合、watermark、重建状态和分析 read model。

### 5.3 GCP 可保留的内容投影（非权威）

为了搜索/推荐性能，可以在 GCP 保留最小、可重建的内容索引/候选特征，例如 content ID、owner ID、类型、时间、主题、可检索文本索引及 R2 对象引用（仅在必要时）。这些数据必须：

- 标记 source authority、版本和最后更新时间；
- 通过既有/获准事件或接口更新，能从 W03 权威数据重建；
- 不允许直接写回或覆盖 W03 内容；
- 在删除、私密化、封禁、版权限制时及时下线，在线请求仍按当前授权/可见性规则作最终检查；
- 遵守删除、隐私、同意、保留期和跨区域数据策略。

严禁在 GCP 数据库中偷偷建立第二份可独立发布/修改的文章正文权威。R2 URL/对象 key 只是引用，并不转移对象存储归属。

## 6. 迁移分波次

### Wave 0 — 现状证据与数据域分界（不切流）

1. 对齐 `docs/00-CURRENT-GATE-STATUS.md`、实际主分支、Worker Wrangler 配置、D1 resource registry、真实 Cloudflare 资源和 CI 证据。
2. 生成 Worker × 数据库 × 表 × API × 事件的所有权矩阵，尤其拆清 D1-02 中 W03 内容表与 W05 社交表。
3. 逐表归档 D1 schema、索引、约束、当前数据量、增长速率、读取/写入 QPS、隐私分级和删除要求。
4. 为 PG-001..PG-009 逐项补充测试和可审计证据；保持未通过的项为 BLOCKED/NOT_GREEN。
5. 从生产样本测出当前性能与成本基线；建立独立的 Cloud Run / Cloud SQL 测试环境，禁止连入生产源。

**通过标准：** 无未归属数据表、无未知写入方、所有跨域引用可识别、当前 D1-05 物理准入状态已核实、恢复演练方案已评审。

### Wave 1 — GCP 基础设施与发布通道（不接生产流量）

1. 用基础设施即代码定义区域、网络、Cloud Run 服务、Cloud SQL、备份、日志、监控、告警和密钥绑定。
2. 定义 PostgreSQL schema 与独立角色；每个服务仅拥有自己的 schema/table 所需权限。
3. 建立 schema migration 命令、CI 检查、测试数据装载、连接池及连接上限。
4. 验证从 Cloudflare 边缘到 GCP 服务的认证、超时、重试、限流、取消和故障回退。
5. 完成备份恢复、故障演练、滚动部署、数据库扩容/连接耗尽告警和费用告警。

**通过标准：** 测试环境中恢复成功；凭据轮换演练通过；数据库无任意公网访问；监控可区分 Cloudflare、Cloud Run、数据库和跨云延迟。

### Wave 2 — W11 分析先行（派生数据试迁）

W11 是首个候选试迁域，因为它已具有事件去重、质量分类、小时聚合、watermark、重建和迟到事件相关实现；这不意味着其所有全局准入门已关闭。

1. 把当前有效事件契约和 schema/version 作为输入；建立 PostgreSQL 对应 schema，逐一对照 D1 字段、唯一约束、检查约束、索引与 UTC 时间语义。
2. 从可重放事件源回放历史数据，按批导入并限速；每个事件使用稳定 `event_id` 和 `dedupe_key` 幂等去重。
3. 让 GCP 影子消费者独立计算，不服务用户请求、不改变在线指标，不与旧消费者竞争同一消费游标。
4. 对同一时间窗口比较去重事件数、有效/迟到/重复事件数、小时级内容/创作者聚合、watermark 和重建结果；保留差异证据。
5. 先影子读取，再小比例读取；最后把 W11 的唯一权威写入与读取切换到 GCP。旧 D1 保留为有版本标记的回滚快照/可重建副本，不继续进行无约束的双权威写入。
6. 如事件历史无法完整重放，必须在切换前实现并验证受控增量传输；不能以“最近总量相等”替代明细和聚合对账。

**通过标准：** 事件不丢失、重复投递不重复计数、迟到事件及重建语义一致、对账差异为 0 或每项差异有批准的解释和修复结果，且在线业务请求不因分析写入而等待。

### Wave 3 — W04 Feed / Search / Recommendation 计算迁移

1. 先完成现有 W04 serving-runtime 的功能与权限准入。当前代码状态不足以把本阶段描述为“把成熟推荐服务直接搬迁”。
2. 先把召回、排序、搜索和用户兴趣的领域逻辑封装在可测的服务接口后；GCP 版本使用 PostgreSQL 访问适当的派生数据/非内容信号。
3. W03 内容读取继续走内容权威 API 或经批准的只读接口；GCP 不直连内容 D1，也不获得 W03 写权限。
4. 推荐候选必须经过账户状态、可见性、屏蔽/静音、治理、版权和内容删除规则；GCP 缓存和排名分数均不能成为授权依据。
5. 使用固定样本做结果差异比较，再按功能开关从 1% → 5% → 25% → 50% → 100%（比例仅为建议起点，需结合流量和风险调整）逐步切流。
6. 监控 p50/p95/p99、候选数量、空 Feed 比例、重复率、缓存命中率、信号新鲜度、内容删除下线延迟和成本/千次请求。

**通过标准：** API/DTO 与游标兼容、权限负例全部通过、删除/封禁内容及时消失、推荐结果可重建、切流可快速停止，无明显性能或成本回退。

### Wave 4 — W05 社交读写迁移

1. 以 W05 权威写入路径建立表级清单，先覆盖经过确认的关注、点赞、转推、评论、收藏及相关计数；具体表名必须从当前 migration/SQL/Repository 证据生成，不从本文档猜测。
2. 不迁移整个混合的 D1-02。只迁移 W05 拥有的实体；W03 内容记录留在 Cloudflare。
3. 对跨域关系采用稳定 ID 与可验证的逻辑引用；不能期待 Cloudflare D1 与 PostgreSQL 之间存在 JOIN 或跨库事务。
4. 通过已批准的 outbox/事件传输进行增量同步，或者安排经评审的短写入栅栏 + 最终增量导入。如果现有事件没有覆盖某表的全部变更，不得直接切流。
5. 迁移关注图和高频互动时，采用批量写、索引按查询形态优化、计数可重建及热门键保护；不允许分析聚合覆盖 W05 的权威计数/事实。
6. 对每张表检查主键、唯一性、冲突、软删除/硬删除、并发更新和幂等行为。

**通过标准：** 社交操作在跨设备刷新后保持一致；不丢失、不重复的权威状态变更；计数可以从源数据重算；W03 内容操作仍在 Cloudflare 完成。

### Wave 5 — 其余非内容业务域

按领域独立切片，禁止把 W06/W07/W08/W09/W10/W12 当成一次性整体搬迁。每个域重复执行 Wave 0 的表格盘点、Wave 1 的服务准备、影子验证、切流及恢复测试。

- **W06 治理/风险/审计**：先迁移非内容处理计算和非内容运行状态；封禁、下架、内容状态转换必须通过其已批准的权威接口。
- **W07 订阅/交易/财务**：单独验证订单幂等、权益授予/撤销、退款、账本和结算；任何情况下都不能丢账、重复扣款或由 Analytics 生成资金事实。
- **W08 创作者运营**：把创作者业务资料和运营 read model 与 W03 内容、R2 媒体引用分开处理。
- **W09/W10 运维与异步任务**：每种任务验证重试、顺序、DLQ、回放、补偿、可暂停/恢复和任务状态迁移。
- **W12 开放平台/开发者集成**：独立验证凭据、配额、签名、审计和 webhook 重试。
- **W02 身份与 Better Auth**：放在后期独立切片，包含账号 ID、邮箱验证、会话、刷新/撤销、凭据、角色赋权和登录安全的端到端验证。身份切换前不得让 Cloudflare D1 与 PostgreSQL 同时成为账号/会话的权威写入方。

### Wave 6 — 关闭旧非内容写入路径

所有目标领域通过切流门槛后：

1. 停止旧非内容数据源的写入，保留必要的只读审计/恢复窗口。
2. 证明旧数据不再收到有效写入，所有消费者已迁至新事件端点或已安全停止。
3. 执行最终对账、备份、保留期和删除规则核查。
4. 清理旧绑定/Secrets/权限前，先跑 Worker × 数据库访问边界 CI，确保不再需要的服务不能访问该库。
5. 只在保留期限、审计及恢复规则满足后，提交单独变更停用/删除旧资源的申请。

## 7. 数据复制、一致性与零数据丢失规则

### 7.1 迁移数据步骤

每张表必须走相同流程：

1. **冻结 schema 版本**：源表结构、迁移版本、ID 规则、时间和状态字段先固定。
2. **初次快照**：导出可校验快照，保存导出时间、行数、校验摘要和脱敏规则。
3. **目标导入**：批量导入 PostgreSQL，保留 ID、时间、唯一性与空值语义。
4. **增量追平**：用经批准、可重放的 outbox/事件/变更日志追平；不假设 D1 自动提供与 PostgreSQL 相同的 CDC 语义。
5. **影子读取**：目标读结果仅用于比较，尚不决定用户请求。
6. **写入栅栏**：切换时阻止旧写入、等待在途请求/队列排空，记录最终水位。
7. **原子路由切换**：启用新权威写路径，然后恢复写入；所有应用只认一个权威源。
8. **切后对账**：按 ID、版本、行数、状态汇总、业务不变量、事件水位逐项验证。

### 7.2 禁止模式

- 禁止一次请求分别向 D1 和 PostgreSQL 写数据而没有可靠的一致性协议。
- 禁止在尚未对账时同时向两个库提供权威读取。
- 禁止依赖数据库自增 ID、SQLite rowid、数据库特定时间/JSON 函数或隐式排序来维持业务语义。
- 禁止使用 Analytics 的计数去覆盖 W03/W05/W07 的权威状态。
- 禁止跨云请求无限重试、无超时或不设并发上限。
- 禁止从 Cloudflare 缓存直接返回未经适用的当前授权检查的私有内容。

### 7.3 PostgreSQL 兼容性

遵守 `contracts/database/cloudflare-d1-pg-portability.v1.json`：

- ID 使用稳定、不可变的业务 ID；迁移不因为 PostgreSQL 类型而改变公开标识符。
- 时间语义使用 UTC；源端毫秒精度映射与目标端 `timestamptz` 转换须显式测试。
- 业务枚举与状态机由应用合同约束；JSON/JSONB 只作为内部实现选项。
- 索引按真实查询模式设计，不能机械地把 SQLite 索引复制为最终 PG 索引。
- 约束、排序规则、唯一性、空值、并发事务、隔离级别和重试必须由跨数据库测试验证。
- Payload 自有表迁移必须遵守官方 Payload adapter 边界；不得依赖未文档化的内部表或修改 Payload Core。

## 8. 灰度、监控与切流门槛

每个域必须建立独立 feature flag / 路由开关，包含开关所有者、默认值、回滚操作、配置版本和审计记录。

建议的初始切流护栏（需在实际基线采集后经 owner 批准，不是当前已测 SLO）：

- 数据丢失或重复权威业务变更：**0 容忍**。
- 安全、权限、账务和内容权威越界：**0 容忍**。
- 错误率较切换前基线增加不得超过 **0.1 个百分点**；若基线或样本量不足则不得自动放宽。
- API p95 延迟不得比基线恶化超过 **10%**，并单独检查 p99、跨云 RTT 与数据库锁等待。
- 观察窗口至少覆盖代表性的高峰、低峰、作业执行及一个完整业务周期；具体长度由该领域风险决定。
- 任何差异没有明确 owner、修复证据和批准前，不扩大灰度比例。

必须统一关联 request ID、correlation ID、event ID、migration run ID 和 schema/pipeline version，让一次操作可以从 Cloudflare 入口追踪到 Cloud Run、PostgreSQL 和事件消费者。

## 9. 回滚与灾难恢复

### 9.1 读取/计算层回滚

如果 GCP 目标只在影子模式或只处理派生数据，停止影子消费者/切回旧路由即可；切换前必须确认旧系统的事件水位和缓存失效情况。

### 9.2 权威写入切换后的回滚

权威写入切至 PostgreSQL 后，旧 D1 可能已经落后，**不能直接把路由切回旧 D1 并宣称完成回滚**。每个事务域必须在切流前选定并演练以下一种机制：

- 有验证证据的反向增量复制/重放，可以把新权威写入追平回旧数据源；或
- 经批准的短暂停写、导出增量、恢复旧库并切回的恢复流程；或
- 当反向迁移风险太高时，采用经过演练的 PostgreSQL 前滚恢复策略，不声称可无损回切。

对 W11 这类可重建派生数据，优先依靠有保留期限的可信事件源进行重放和重建。对于身份、社交和财务权威数据，必须逐域定义明确的恢复点目标（RPO）和恢复时间目标（RTO），并在演练中证明。

### 9.3 数据库与区域恢复

- Cloud SQL 自动备份、时间点恢复、保留策略和恢复权限需要按环境设置并演练。
- 备份必须加密、限制访问并执行恢复验证；“备份成功”不是“可恢复”的证据。
- R2 对象生命周期和内容恢复仍由 Cloudflare 的既有备份/保留规则管理，不因 GCP 数据库备份而视为已保护。

## 10. 性能与费用控制

- Cloud Run 通过最大实例数、每实例并发、最小实例（按冷启动要求）、CPU/内存档位控制成本和尾延迟。
- Cloud SQL 依据查询计划、锁等待、连接池、索引命中、CPU、存储增长和备份窗口配置规模；不要仅依据注册用户数购买配置。
- 写密集工作先做批量写与受控异步处理，分析聚合与在线事务分开限流。
- 根据证据决定是否使用 Redis/Memorystore、BigQuery、独立 PostgreSQL 实例或专用搜索引擎；首版不因“未来可能需要”而全部启用。
- Cloudflare ↔ GCP 跨云数据量和 RTT 是常态成本/延迟项。优先传输事件、ID、必要投影和结果，不传输媒体二进制及可避免的完整内容副本。
- 每个域切流前进行可重复压测，记录固定请求集、数据规模、并发、暖/冷缓存、p95/p99、错误率、数据库成本和 Cloud Run 成本。
