# LuckRead Article/Video Snowflake ID Decision v1.0

- Status: **DECISION RECORDED / IMPLEMENTATION PENDING**
- Date: 2026-10-23
- Scope: IDs for article and video content only
- Selected reference implementation: [dustinrouillard/snowflake-id](https://github.com/dustinrouillard/snowflake-id)
- Related content authority: W03 Content; public API boundary: W01
- This record documents the technical decision and implementation gates. It does not claim that Snowflake IDs are implemented or that database savings have been measured.

## 1. Decision

LuckRead will use the `dustinrouillard/snowflake-id` project as the selected implementation/reference for a Snowflake-style content ID generator, subject to the production-safety gates in this document.

The scope is limited to:
- articles;
- videos, including short-form and long-form video content where those are represented as W03 article/video content.

The scope explicitly excludes:
- user and authentication IDs;
- comments, likes, reposts, follows, subscriptions, orders, and other business IDs;
- social posts whose identity is not part of the article/video content scope;
- changing the Worker/D1 topology or data-authority boundaries.

The intent is to apply the new scheme to newly created in-scope content after implementation and compatibility tests pass. Existing content IDs will not be bulk-rewritten as part of the initial rollout.

## 2. Why this project

The project's README says it is inspired by Twitter's Snowflake ID and describes this bit layout:

| Component | Bits | Purpose |
|---|---:|---|
| Timestamp | 42 | Time-based ordering |
| Machine/node ID (`mid`) | 10 | Distinguishes ID producers |
| Sequence | 12 | Distinguishes IDs generated by one producer in one millisecond |
| Total | 64 | Compact time-based identifier |

The project emits decimal strings because JavaScript numbers cannot exactly represent every 64-bit integer. Its README also warns that a distributed deployment must provide a unique `mid` for each producer.

Reference:
- Project: https://github.com/dustinrouillard/snowflake-id
- Historical Twitter archive: https://github.com/twitter-archive/snowflake

This is an implementation inspired by Twitter's Snowflake design, not evidence that it is the exact implementation currently used inside X.

## 3. API and storage rules

1. **External representation:** W01 APIs return and accept content IDs as decimal strings. APP, H5, and PC must not convert them to JavaScript `Number`.
2. **Content authority:** W03 remains authoritative for article/video identity and lifecycle. W01 remains the public API boundary. Do not let clients generate authoritative IDs.
3. **Database representation:** Before changing a primary-key column to SQLite `INTEGER`, inspect the existing W03/D1-02 schema, Payload assumptions, relations, migrations, and all cross-Worker contracts. SQLite integers are signed 64-bit. If changing the storage type would break existing compatibility, keep the decimal representation compatible with the current schema and measure the actual benefit before making a schema change.
4. **Relations:** Every article/video reference in detail routes, lists, media associations, author/content relations, and any permitted social or analytics references must preserve the same canonical ID string on the wire.
5. **No global ID migration:** Do not alter W02 identity IDs or unrelated business identifiers. Do not rewrite historical article/video IDs without a separately approved migration plan.

## 4. Mandatory production-safety gates

The package must not be treated as production-safe merely because it generates decimal strings. Before enabling it in W03 production, verify:

- **Cloudflare Workers compatibility:** module format, runtime APIs, bundling, and tests work in the repository's actual Worker toolchain.
- **Global uniqueness:** all concurrently active generators receive distinct producer IDs, or an alternative collision-safe mechanism is proven. A fixed default `mid: 1` shared by multiple isolates is not acceptable.
- **Ephemeral/scaled runtime:** Cloudflare Worker isolates can be created and scaled independently. Do not assume an isolate is a stable physical machine or that an in-memory counter coordinates other isolates.
- **Clock and sequence behavior:** test clock rollback, multiple calls in one millisecond, sequence exhaustion, restart/isolate recreation, and timestamp boundaries. Fail safely rather than silently emit duplicate IDs.
- **Signed 64-bit range:** generated IDs fit the selected database representation and remain safe through migrations, query parameters, logs, and API serialization.
- **Collision tests:** test parallel generation across simulated producers and across repeated initialization; test that every ID is unique and decimal-string round-trips exactly.
- **Dependency review:** inspect package maintenance, dependency tree, license, security advisories, and source before adding it to production dependencies.

If the package cannot meet these gates within the existing architecture, pause the rollout and document the smallest compatible adaptation. Do not add a Worker, D1 database, or Queue just to host ID generation.

## 5. Rollout plan

1. Inventory W03 content ID generation, actual D1-02 column types, Payload assumptions, API schemas, and all consumers of article/video IDs.
2. Add isolated generator tests and prove uniqueness under the production execution model.
3. Confirm decimal-string IDs survive W01 API validation, APP/H5/PC parsing, routing, pagination, and all relevant foreign-key/reference paths.
4. Decide the database storage type based on measured compatibility and index/storage benchmarks; do not assume that numeric-looking strings save space by themselves.
5. Enable the generator only for new in-scope article/video content behind a controlled rollout.
6. Keep existing IDs valid and monitor duplicate-key failures, invalid-ID responses, and content-reference integrity.

No code, schema, API contract, or existing data is changed by this decision record.

## 6. Success criteria

Implementation is considered complete only when evidence demonstrates:

- no duplicate IDs under tested concurrent production-like conditions;
- no JavaScript precision loss on any client;
- no regression to existing content, creator, media, and cross-Worker references;
- database/index size and relevant query performance are measured against the current baseline;
- existing IDs and all out-of-scope ID domains remain unchanged;
- required tests and CI pass on the implementation commit.

A smaller ID field or improved performance must be reported as a measured result, not assumed from the use of Snowflake.
