# LuckRead 1.0 Public URL Decision v1.0

**Status: LOCKED**

## 1. Canonical domain

LuckRead 1.0 public URLs use:

`https://luckread.com`

`luckread.cn` is a legacy alias and redirects to `luckread.com`.

## 2. Public identity URL

A registered user's `username` is the public handle and is required during account registration.

Canonical profile:

`https://luckread.com/@{username}`

The platform must never auto-generate a public username after registration when the registration boundary requires the field.

Username rules:

- unique;
- public;
- normalized/validated by the existing account-identity rules;
- historical usernames must not be silently reassigned when that would create ownership ambiguity.

## 3. Public content URLs

Content URLs are bound to the author's public username and use an immutable content identifier.

| Content | Canonical URL |
|---|---|
| Article | `/@{username}/article/{contentId}` |
| Dynamic post | `/@{username}/post/{contentId}` |
| Video | `/@{username}/video/{contentId}` |
| Short video | `/@{username}/short/{contentId}` |

The readable slug may be introduced later, but `contentId` remains the stable identity and must not depend on a mutable title.

## 4. Public author collections

`/@{username}/articles`

`/@{username}/posts`

`/@{username}/videos`

`/@{username}/shorts`

Relationship pages:

`/@{username}/followers`

`/@{username}/following`

## 5. Global public entry points

These remain type-level entry points only:

`/articles`

`/posts`

`/videos`

`/shorts`

They do not introduce the 2.0 Feed / Recommendation / Search system.

## 6. Share URLs

Existing share-token URLs remain:

`/s/{shareId}`

They are share aliases, not canonical author/content URLs.

## 7. API and management domains

API:

`https://api.luckread.com/v1/...`

Administrator backend:

`https://mp.luckread.com/admin`

Creator Center:

`https://mp.luckread.com/creator-center`

`/admin` remains Payload administrator scope; Creator Center is not placed under Payload Admin.

## 8. Legacy compatibility

The current ID-based routes:

`/content/{contentId}`

`/users/{userId}`

remain compatibility routes during migration so existing links do not break.

New frontend navigation must prefer the canonical username-based URLs. A later migration step can resolve the immutable content/user ID to the canonical username URL and issue permanent redirects without changing the underlying entity IDs.

## 9. URL ownership rule

Public URL identity does not become a new database authority.

- User identity authority remains the existing User/Identity contracts.
- Content authority remains the Content domain.
- `username` is the public routing key.
- `contentId` remains the immutable content identity.
- No additional D1 is created only for public URL routing.
- Cache/projection layers must remain derived and rebuildable.

## 10. 1.0 boundary

This decision freezes the public URL shape for the 1.0 foundation.

Not included in this decision:

- long-form video;
- Live;
- Feed;
- recommendation;
- search;
- other 2.0 discovery systems.
