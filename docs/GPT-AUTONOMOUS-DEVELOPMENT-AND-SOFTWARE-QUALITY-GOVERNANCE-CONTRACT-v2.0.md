# LuckRead GPT 自主开发与软件质量治理总契约 v2.0

**状态：PROPOSED / REVIEW REQUIRED**  
**版本：2.0.0**  
**适用范围：LuckRead 仓库内由 GPT 参与的需求分析、代码开发、缺陷修复、测试、PR 审查、合并协助与发布验证**  
**仓库：`wanghuinet/luckread`**  
**基线分支：`main`**

> 本文件是 GPT 的操作与质量治理契约，不是新的产品、架构、API、数据、权限或发布权威。它把 GPT 的工作方式约束到 LuckRead 已存在的治理体系中，防止跨对话上下文漂移、重复开发、错误合并、证据失真和回归缺陷。

---

## 0. 核心目标与不可作出的承诺

目标不是让 GPT 生成更多代码，而是让每一次变更都能回答：

1. 为什么要改，以及由哪个已批准的 Feature / Issue / Contract 授权？
2. 当前仓库里是否已经存在相同能力、实现、PR 或可复用依赖？
3. 修改了哪些边界，可能影响哪些调用方、数据、权限、事件和平台？
4. 用什么测试证明行为正确，怎样证明旧功能没有被破坏？
5. 哪些证据绑定到哪个精确 Commit SHA，当前结果是否仍然有效？
6. 当前工作究竟是代码完成、测试通过、PR 合并、部署完成，还是生产验证完成？

**不得承诺“零 Bug”或“绝对无漏洞”。** 软件质量目标是持续降低缺陷概率、影响范围和修复成本；用可复现测试、静态分析、安全检查、运行观测和回归机制不断发现与消除风险。

## 1. 权威体系：单一事实来源，禁止平行造权威

GPT 必须遵守仓库当前 `main` 中的权威文档和现有准入流程。至少按以下入口核对：

| 领域 | 权威来源 / 用途 |
|---|---|
| 功能完整性 | `docs/00-LUCKREAD-ULTIMATE-FEATURE-BLUEPRINT-v2.0.md` |
| 当前架构 | `docs/00-PROJECT-BLUEPRINT-v1.4.md` |
| 通用工程执行 | `docs/DEVELOPMENT-EXECUTION-STANDARD-LUCKREAD-1.0-v1.0.md` |
| 跨合同冲突与准入 | `docs/74-FINAL-CONTRACT-RECONCILIATION-AND-ADMISSION-GATE-v1.0.md` |
| L5 工程执行规格 | `docs/179-L5-EXECUTION-SPECIFICATION-CONTRACT-v1.0.md` |
| L6 验证原子单元 | `docs/180-L6-VERIFICATION-AND-EVIDENCE-ATOMIC-UNIT-CONTRACT-v1.0.md` |
| 证据与验收追踪 | `docs/176-EVIDENCE-REGISTRY-ACCEPTANCE-TRACEABILITY-CONTRACT-v1.0.md` |
| 具体领域 | 对应当前有效的 Worker、API、Data、Event、Permission、Security、Runtime、UX 合同 |

上表是 GPT 的最小核查入口，不代表文件清单完整，也不改变 `docs/74` 定义的权威优先级。开始具体工作时，必须继续读取该模块当前有效的合同、L5、L6、Evidence 和 Change Control。

**禁止：**

- 新建第二份 Feature Inventory、第二套架构蓝图、第二份 API 清单或第二套 Evidence Registry。
- 在本文件中重新定义业务字段、operationId、实体归属、权限、状态机、Worker 职责、D1 归属或运行时拓扑。
- 用旧文档、聊天摘要、搜索片段、历史 PR 或未合并分支覆盖当前 `main`。
- 因为文档内容看起来过时就自行选用另一个版本；必须先按 Change Control / Reconciliation 处理冲突。
- 把本文件的操作约束解释为绕过现有领域合同或准入门禁的授权。

若权威文件缺失、互相矛盾或无法确认适用版本，立即标记 **BLOCKED**，列出冲突文件和最小需要解决的问题；不得用代码猜测业务规则。

## 2. 每轮开始：从 GitHub 恢复真实上下文

每次新对话、收到“继续”、准备开发或准备合并时，按顺序核实：

1. 仓库是否为 `wanghuinet/luckread`，默认分支是否仍为 `main`。
2. `main` 最新 Commit SHA、提交时间和提交说明。
3. 所有相关开放 PR：编号、标题、创建/更新时间、base/head、head SHA、草稿状态、变更文件、Review、未解决线程。
4. 当前 PR 的必要 CI / Workflow / Job 结果；区分成功、失败、跳过、取消、未运行和无结果。
5. 最新实现、关联测试、Contracts、L5/L6、Evidence、部署与运行证据。
6. 当前模块在 Feature Blueprint / Stage / Slice 中的真实状态，以及是否被其他 PR 或 Commit 改动。

核查结果必须注明**核查时的精确 SHA**。若工具只能返回部分数据，明确说明覆盖范围，不得声称已经检查全部 PR、Review 或工作流。

### 2.1 事实来源优先级

`main` 当前内容与 GitHub 实际状态 > 当前 PR 的实际差异和 CI 结果 > 与当前 SHA 绑定的有效测试/运行证据 > 仍然有效的项目文档 > 历史记录 > 对话记忆。

聊天记录只帮助恢复用户意图，不作为仓库现状的证明。不得把旧对话中“已完成”“已通过”“可以合并”的结论直接沿用到新 SHA。

### 2.2 “继续”命令语义

- **“继续”**：恢复当前任务和最近一次交接状态，从当前未完成步骤继续；不得重启已 GREEN 的工作，不得擅自扩大范围。
- **“继续推进 / 继续批量推进”**：仍然遵守模块边界；只有在用户明确允许批量处理且各项互不依赖、可分别审查时，才可连续处理多个独立 Slice。每个 Slice 仍需独立验证和交接。
- **“合并 PR 后继续”**：先重新读取 PR diff、Review、未解决线程、必要 CI 和合并条件；满足条件才合并，之后重新读取最新 `main` 再继续。
- **“先合并 PR”**：只处理已明确授权范围内的 PR；按依赖关系和用户指定顺序执行，不把“继续”解释为合并授权。
- **“跳过某门禁”**：仅适用于用户明确点名的门禁、PR 和范围；必须记录授权依据和影响，不能推广到其他 PR 或未来任务。

若当前上下文没有明确的活动 Slice，以仓库中的当前执行指针、开放 PR 和未关闭阻塞恢复，不得自行挑选一个看起来容易的任务替代。

## 3. 任务选择与范围控制：一次一个可验收 Slice

每个开发周期只设定一个当前主目标。它必须具备：

- 可追踪的 Feature ID / Issue / 合同依据；
- 明确的用户或系统结果；
- 明确的修改边界和不在本轮范围内的内容；
- 明确的依赖和影响面；
- 对应 L5 执行规格、L6 验证单元与 Evidence 计划；
- 可独立审查、测试、提交和回滚的边界。

先做去重：检查当前代码、组件、API adapter、测试、已合并 Commit、所有相关开放 PR、已引入依赖和历史实现。已存在且证据仍有效的能力直接复用；只修真正缺失或失效的部分。

**完成一个模块后必须停止。** 报告本轮完成内容、证据、未完成项和下一模块，等待用户明确“继续”。不能因为路线图中存在下一个任务，就自动开始下一个模块。若用户明确授权批量推进，也不能把互不相关的模块揉进一个 PR 或跳过独立验收。

本规则与既有工程执行标准的“一次开发对话处理一个 Vertical Slice”保持一致：当前 Slice 达到 GREEN 后，结束本轮对话；下一个 Slice 原则上在新对话启动并从 GitHub 重新恢复状态。若用户明确要求在同一对话继续，也必须把它视为新的上下文边界，重新核实 main、PR、合同和证据，不得沿用未验证的旧状态。

## 4. 设计与实现：最小自研、最小差异、先查后改

每次修改前必须完成：

1. 阅读当前调用链和现有实现，不只看目标文件。
2. 确认功能归属、数据 authority、API owner、权限 owner、事件生产/消费方和运行边界。
3. 搜索仓库现有实现和已引入依赖。
4. 对候选 OSS / 第三方组件检查许可证、维护状态、源代码、测试、依赖安全、目标平台兼容性和真实运行证据。
5. 记录复用的上游仓库、精确 Commit、源路径、许可证、目标路径、删去的上游后端/认证/存储逻辑及 LuckRead 回归结果。
6. 选择满足合同的最小实现，不进行与 Slice 无关的重构或格式化全仓。

优先级：

1. LuckRead 当前 `main` 已有实现；
2. 已引入且适配当前运行版本的成熟依赖；
3. 许可证明确、维护健康、经过真实验证的成熟开源实现；
4. 仅为连接 LuckRead API、权限和既有系统编写薄适配层；
5. 确有必要且无法复用时才自研业务代码。

**禁止仅凭 Stars、README、截图或 Demo 宣称项目成熟。** 无许可证或授权不明确的代码只可参考设计，不得复制。不得迁入上游的数据库、认证、支付、权限或业务权威。

## 5. 变更前影响分析：避免修 A 坏 B

每个 Slice 开发前，列明：

- 直接修改文件和模块；
- 上游调用方与下游消费者；
- API / DTO / OpenAPI / 客户端兼容影响；
- 数据结构、迁移、索引、唯一约束和历史数据影响；
- 权限、身份、Session、资源所有权和隐私影响；
- 事件、Queue、幂等、重试、乱序、重复投递和补偿影响；
- 缓存失效、派生状态重建与数据一致性影响；
- Android / iOS / H5 / PC 受影响入口；
- 可观测性、成本、性能、发布、回滚和恢复影响。

只修改目标 Slice 所需范围。若发现相邻问题，记录为独立 Issue / Slice，不顺手扩大本轮实现，除非该问题是当前变更的安全或正确性阻塞。

数据库迁移必须确认迁移编号、执行顺序、兼容窗口、重复执行行为、回滚/前向修复策略和目标环境；不得仅凭文件存在认定生产迁移已执行。

## 6. 验证策略：按风险选测试，不以“跑过一个测试”代替质量

所有验证以当前 L5/L6、对应领域合同及现有 CI 配置为准。GPT 应选择与变更风险匹配的验证集，并在 PR 中写明执行命令、目标 SHA 和真实结果。

最低检查维度：

| 变更类型 | 必须考虑的验证 |
|---|---|
| 纯函数 / 业务逻辑 | 类型检查、Lint、单元测试、边界与异常输入 |
| API / DTO / OpenAPI | 合同一致性、请求响应、稳定错误码、权限、兼容性、分页与幂等 |
| 数据库 / 迁移 | Schema、约束、索引、旧数据、重复执行、并发、迁移前后行为 |
| Worker / Service Binding / Queue | 调用边界、认证授权、失败隔离、重复/乱序投递、重试、死信或恢复策略 |
| 身份 / 支付 / 权限 / 隐私 | 默认拒绝、越权负向测试、主体/资源边界、重放/重复请求、审计和敏感信息处理 |
| APP / H5 / PC UI | 组件测试、加载/空/错误/离线/权限状态、导航、主题、无障碍和真实 API E2E |
| 性能 / 高流量路径 | 真实基线、P50/P95、资源消耗、并发、限流和降级 |
| 部署 / 配置 / 依赖升级 | 目标环境构建、配置校验、兼容性、回滚或前向恢复、部署后 Smoke Test |

每个可变更行为至少覆盖适用的成功路径和失败路径。状态型操作还要检查非法状态、并发冲突和重复提交；跨域和异步流程还要检查一致性、事件副作用及恢复行为。

测试应尽可能可重复、隔离、确定。不得用假数据、Mock 成功响应或本地状态冒充真实 API / 生产能力。Mock 可以用于隔离单元测试，但必须另有真实边界的契约或集成验证。

**不允许为了让 CI 变绿而：** 删除测试、放宽断言、吞异常、跳过鉴权、降低类型严格度、把失败改成软警告、修改测试输入来绕开缺陷，或把未运行写成通过。

## 7. 缺陷闭环：每次修复都要降低复发概率

每个 Bug 按以下顺序处理：

1. 收集可验证的症状、请求/追踪 ID、环境、版本和复现步骤；不记录密码、令牌或隐私正文。
2. 在当前 SHA 或明确的测试环境复现；不能复现时标记 UNREPRODUCED，不假定根因。
3. 定位根因，不把表面错误信息当作根因。
4. 添加或完善能够在旧代码上失败、在修复后通过的回归测试。
5. 实施最小修复，并检查同一调用路径、相同 helper 和相邻状态是否存在同类缺陷。
6. 运行目标测试及受影响模块的回归测试。
7. 检查错误日志、监控、审计和用户可见错误是否恰当。
8. 把修复、测试、证据和 Commit SHA 绑定，关闭缺陷前确认其验收条件。

若某缺陷重复出现，必须分析为何原测试未发现、覆盖的是不是错误层、是否存在多个实现或状态来源，并修正测试策略，而不是重复追加相似的脆弱断言。

## 8. 安全与隐私：安全门禁默认不可跳过

每个变更按风险检查适用项：

- 身份认证、Session 生命周期、令牌撤销和会话过期；
- 资源级授权、所有权、角色、Scope 和服务间调用授权；
- 输入验证、输出编码、注入、路径穿越、SSRF、开放重定向等适用风险；
- CSRF、CORS、Origin、Cookie、重放、速率限制和暴力尝试；
- IDOR / BOLA、越权读取、越权修改和批量数据泄露；
- webhook 签名、事件真实性、幂等和重放保护；
- 敏感字段最小化、日志脱敏、凭证安全存储；
- 第三方依赖漏洞、许可证和供应链风险；
- 文件上传、媒体访问授权、签名 URL 和对象所有权；
- 备份、数据删除、保留期限、审计和恢复。

遵守默认拒绝和最小权限原则。安全检查必须针对实际服务端边界；隐藏按钮、客户端校验和 UI 状态不构成授权。

任何发现的高危/严重漏洞、未授权数据暴露、跨用户越权或身份绕过均为阻塞项。不得以“先合并后修”处理。

## 9. CI、门禁和例外授权

门禁结果必须逐项分类为：

- **PASS**：该检查真实执行并成功；
- **FAIL**：真实执行且失败；
- **SKIPPED**：被条件或人工跳过；
- **NOT RUN**：没有执行；
- **UNKNOWN**：无法取得可靠结果；
- **BLOCKED**：因前置条件或外部依赖无法执行。

SKIPPED、NOT RUN、UNKNOWN 不等于 PASS。若一个 PR 的目标变更相关检查已成功，不得无故重跑已经成功的工作流；只有证据失效、代码 SHA 变化、失败任务需重试或用户明确要求时才重跑，并优先只重跑失败任务。

### 9.1 全局门禁与专项门禁

- 安全、身份/授权、数据迁移正确性、架构边界、目标代码测试、必要构建和发布安全检查默认不可跳过。
- Five-Way、R4、Evidence、R5 等全局对齐/准入门禁必须按仓库当前治理文件判断其适用范围和实际状态。
- 任何例外都必须有用户对**具体 PR + 具体门禁 + 具体范围**的明确授权，并在 PR/交接记录中写明；不得把一次例外变成长期默认规则。
- 例外只改变获准门禁的本次处理方式，不会把 SKIPPED/NOT GREEN 伪装成 GREEN，也不能替代本 Slice 的安全、架构和必要测试证据。
- 如门禁失败涉及当前改动、安全、架构、数据、授权或必要测试，不得借用与当前 Slice 无关的历史授权跳过。
- 若门禁的失败属于既存全局阻塞，应区分“本 Slice 的局部验证结果”和“全局发布/准入状态”，准确报告，不得隐瞒或夸大。

## 10. Git 分支、Commit 与 PR 工作方式

1. 先核实最新 `main` 和已有工作，确认没有重复 PR / 重复实现。
2. 在最新 `main` SHA 上建立专用分支；未经授权不直接向 `main` 写入。
3. 保持一个 Slice 的变更集中、可审查，不在 PR 混入无关格式化、依赖升级或其他模块。
4. Commit message 清楚描述变更性质与领域。
5. PR 描述必须包含：目标与 Feature/Issue、背景与根因、变更范围、不做事项、架构/API/Data/Permission 影响、复用来源、迁移风险、测试命令和结果、CI 链接、证据、未完成项及回滚/恢复说明。
6. 审查实际 Diff，而不仅是 PR 标题或提交说明；检查敏感文件、生成文件、意外依赖、删除测试、遗漏迁移和越界改动。
7. 对 Review comment 逐项处理；未解决线程必须显式报告，不得假设已解决。
8. 仅在用户明确授权合并且适用门禁满足或有该 PR 的明确专项例外时合并。
9. 合并后重新读取 `main` 最新 SHA 和合并结果；再确认测试与证据是否仍绑定到最终合并 SHA。
10. PR 合并不等于部署成功；部署成功不等于生产功能已验收。

不允许强推覆盖他人提交、删除未知分支、关闭未审查 PR 或擅自改变分支保护与仓库安全设置。

## 11. 状态机：不同完成阶段不得混写

每项功能和每个 Slice 的状态分开记录：

| 状态 | 含义 |
|---|---|
| DISCOVERED | 已发现需求/缺陷，尚未完成范围和权限确认 |
| CONTRACTED | 适用 Feature / Contract / L5 / L6 已明确 |
| IMPLEMENTING | 正在修改代码 |
| CODE_COMPLETE | 目标代码已实现，但不代表测试通过 |
| TESTS_GREEN | 要求的测试已通过，注明测试 SHA 与范围 |
| PR_OPEN | PR 已创建，等待 Review / CI / 合并 |
| PR_MERGED | PR 已合并到 main，注明 merge SHA |
| DEPLOYED | 已部署到指定环境，注明部署版本 |
| DEVICE_ACCEPTED | 目标设备/平台的真实验收已通过 |
| PRODUCTION_VERIFIED | 生产环境完整流程和观测证据已通过 |
| BLOCKED | 有明确阻塞项，注明责任边界和解除条件 |
| DEFERRED | 经批准推迟，注明所属版本/范围和重新进入条件 |
| NOT_VERIFIED | 尚无足够证据，不得称完成 |

**GREEN 只能由对应权威准入流程确认。** 代码存在、文档更新、某个单测通过、PR 合并或某次人工演示，都不能单独证明整个功能 GREEN。

Evidence 应明确：声明、验证方法、预期、实际结果、精确 Commit SHA、CI Run/Job 或运行产物、执行时间、适用环境、有效性/失效条件。代码发生影响该证据的变化时，必须重新评估证据是否仍有效。

## 12. 发布后反馈与持续改进

上线后按现有监控和运维边界观察：

- API 错误率、延迟和超时；
- 客户端崩溃率、白屏和关键旅程失败；
- Queue 积压、重试、死信和消费延迟；
- 数据库错误、慢查询、读写消耗和迁移状态；
- 登录、授权拒绝、可疑访问和安全事件；
- 支付、订阅、权益和退款的一致性；
- 媒体上传、处理和播放失败；
- 通知投递率、无效令牌和深链失败；
- 资源成本、性能分位数和容量余量。

只采集完成运维所需的最小数据，遵守现有隐私和保留规则。线上问题进入缺陷流程：事件 → 影响评估 → 根因 → 回归测试 → 修复 → 证据 → 监控确认。没有监控数据时必须明确说明，不得声称“线上稳定”。

## 13. 强制 STOP 条件

出现以下任一情况，停止当前 Slice 的实现或合并动作：

1. Feature ID / 产品范围 / 合同授权缺失；
2. 权威文档冲突、数据 owner 不明确或出现第二事实来源；
3. 需要改变 Worker、D1、Queue、Service Binding、Payload Core 或其他冻结边界；
4. API、权限、状态机、并发、幂等、事件或迁移语义不清；
5. 涉及高危安全问题或越权风险；
6. OSS 许可证不清、目标 SDK 不兼容或关键依赖来源不可信；
7. 测试不能复现关键业务行为，或必要验证环境/证据缺失；
8. 当前 main 已发生变化，分支与基线冲突且未完成重新核对；
9. PR 有未解决的阻塞性 Review 或必要 CI 失败；
10. 变更已超出当前 Slice，无法安全审查或回滚。

STOP 不是放弃任务。GPT 必须报告：阻塞事实、证据位置、影响、最小可执行解法、需要谁作出的决策。不得以猜测或降级质量门禁继续推进。

## 15. Definition of Done

一个 Slice 只有同时满足下列适用条件，才可交付：

- 范围有明确 Feature / Contract 依据，无未批准的新能力；
- 与当前 main、PR、现有代码和依赖完成去重；
- 修改未突破架构、数据、API、权限和安全边界；
- 变更及失败路径有适当自动化测试；
- 新修复的 Bug 有可复现回归测试；
- 必要测试、CI、Review 与门禁状态真实且可追溯；
- Evidence 绑定精确 SHA，内容新鲜且与声明一致；
- 迁移、重试、回滚/恢复和副作用已按适用合同核实；
- 第三方许可证、来源和归属完整；
- 未完成、未运行、跳过和延期项目已明确列出；
- 当前 Slice 的 PR/Commit/交付状态报告准确；
- 完成本 Slice 后停止，等待下一条明确指令。

项目整体 1.0 发布仍由现有产品范围、架构 Blueprint、合同准入、Evidence、生产部署和发布审批共同决定；不得由 GPT 根据局部 Slice 成功自行宣布整个产品“完全完成”。
