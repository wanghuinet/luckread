# LuckRead 1.1 → 1.2 内容平台增强边界与实施参考 v1.0

> 性质：研发参考文档，不是新的 Blueprint、Contract、Mapping 或 Evidence Registry。
>
> 目标：明确 1.1 与 1.2 的技术边界，避免为了追求“更先进”而反复推倒已经稳定的内容基础设施。

## 1. 总原则

LuckRead 1.1 的优先目标不是一次性做完所有内容产品能力，而是把**成熟自媒体平台所依赖的基础设施、主链路和工程质量**做扎实。

1.1 完成后，LuckRead 应当具备稳定的：

**账号 → Creator → 创作 → 草稿 → 编辑 → 媒体 → 审核 → 发布 → 内容展示 → 社交互动 → Creator Center**

主闭环，并能够在现有 12 Worker / 4 D1 / 现有 Queue、Service Binding、Payload Core 边界内继续扩展。

1.2 原则上采用**加法增强**：

- 在 1.1 已稳定的能力上增加新的节点、插件、派生能力和体验。
- 不因为新增编辑器功能、Topic、Mention、视频高级处理等能力而推倒 1.1 内容核心。
- 不新增 Worker、D1、Queue 或改变既定权责边界，除非未来经过单独架构变更。
- 不为了“像某个平台”而直接复制完整第三方项目。

## 2. 1.1 应先收口的基础设施

### 2.1 内容核心

1. 内容创建、读取、列表、更新、删除。
2. Draft / Review / Publish / Unpublish / Archive / Delete / Restore 生命周期。
3. 定时发布。
4. If-Match 乐观并发控制。
5. Idempotency mutation 保护。
6. Revision history 与 rollback。
7. Stable slug / canonical content identity。
8. Article / Post / Short Video 的内容引用边界。
9. W03 作为 Content 权威，W01 只承担入口与适配。

### 2.2 Creator Studio / 创作工作流

1. Creator 内容列表与状态操作。
2. 草稿恢复。
3. 自动保存。
4. 发布前校验与错误反馈。
5. 内容详情、预览和发布后的展示闭环。
6. 内容、媒体、状态之间保持一致，不通过前端自行推断业务状态。

### 2.3 文章编辑基础设施

1. 结构化 ArticleDocument。
2. 基础 block 编辑。
3. 图片 / 图库。
4. Undo / Redo。
5. Block duplicate / split / merge / reorder。
6. Clipboard 基础能力。
7. Word 导入。
8. Markdown / Outline / Find & Replace 等当前插件能力。
9. 编辑器插件上下文保持类型化，插件不直接修改业务持久化模型。

1.1 的目标是**稳定、可扩展、可继续增加插件**，而不是现在一次性做成完整桌面级文字处理器。

### 2.4 Media / Short Video 基础设施

1. Media asset 上传。
2. Short Video 主视频 + 可选封面。
3. 视频元数据采集与编辑。
4. 视频发布 / 下架 / 恢复与内容生命周期联动。
5. 播放地址 / delivery metadata。
6. TikTok 风格沉浸式连续浏览的基础体验。
7. 播放、静音、进度、预加载、手势和互动等基础体验。
8. 明确区分“上传成功”“可播放”和“真实转码完成”。

1.1 **不伪造真实转码状态**。当前实现没有独立媒体处理执行链时，不能把对象存在直接解释为 PROCESSING 完成或 transcoding READY。

### 2.5 Social 基础设施

1. Follow / Unfollow。
2. Followers / Following 列表。
3. Like / Unlike。
4. Comment / Reply。
5. Bookmark / Favorite。
6. Share 边界。
7. Block / Mute / Report 等已存在的社交安全边界。
8. Creator Center Audience 基础数据。
9. 高频交互保持幂等、缓存和 D1 保护。

### 2.6 平台工程质量

1. `fetchJson` 等共享客户端 API 能力优先复用。
2. 统一错误处理、加载状态、请求取消、竞态保护。
3. 公共读优先 cache-first。
4. 私有响应不得进入共享缓存。
5. 正常公开读尽量不直接产生 D1 读取放大。
6. Mutation 使用 If-Match / Idempotency 时保持一致。
7. 前端不得直接访问 D1。
8. 不为了局部页面优化而重新创建第二套 API / Authority。

## 3. 1.1 “成熟自媒体平台基础”定义

这里的“成熟”不是功能数量无限增加，而是以下条件同时成立：

### 产品闭环

Creator 能够从注册、完善身份、进入 Creator Center，到创建文章 / 短视频、保存草稿、编辑、提交审核、发布、查看作品、管理状态，再回到创作。

### 工程闭环

内容操作具备：

**认证 → 权限 → 校验 → 并发保护 → 幂等 → 持久化 → 状态转换 → revision → 可恢复**

### 体验闭环

用户可以正常完成：

**上传 → 编辑 → 预览 → 发布 → 阅读 / 播放 → 点赞 / 评论 / 收藏 / 关注 / 分享**

### 成本闭环

公开读取具备：

**缓存 → single-flight → D1 traffic guard → bounded read**

避免随着访问量增长而把 D1 当成无限容量的同步查询层。

## 4. 1.2 再做的增强方向

1. **高级编辑器**
   - inline marks
   - links
   - code / code block
   - tables
   - embeds / cards
   - richer paste / HTML conversion
   - 更完整的 keyboard / selection / accessibility
   - 更强的插件生态

2. **媒体生产管线**
   - resumable upload
   - ingest / validation
   - processing state
   - retry / recovery
   - poster / thumbnail
   - transcoding / renditions
   - adaptive delivery
   - 更完整的媒体生命周期

3. **Mention / Topic / Hashtag**
   - @mention resolution
   - canonical topic
   - hashtag normalization
   - anti-spam
   - notification fan-out

4. **内容国际化**
   - content language
   - translation variants
   - localized metadata
   - content version / review relationship

5. **SEO / Distribution**
   - canonical URL
   - structured metadata
   - OpenGraph
   - RSS / Atom
   - sitemap
   - indexing controls

6. **Creator Analytics**
   - content views
   - engagement
   - watch / completion related signals
   - creator dashboards
   - async derived metrics

7. **更高级的内容组织**
   - series / collection UX 增强
   - richer content relationships
   - reference / derivative / translation provenance

以上属于 1.2 的**候选增强池**，不是要求 1.1 立即全部实现。

## 5. GitHub / 开源项目借鉴策略

1. **优先研究成熟项目解决问题的方式，而不是寻找一个项目整体替换 LuckRead。**
2. 对编辑器能力，重点参考：
   - Lexical
   - Payload + Lexical
   - Gutenberg
   - Ghost
3. 对视频媒体能力，重点参考：
   - PeerTube
   - FFmpeg 生态
4. 对 Mention / Hashtag / Social 语义，重点参考：
   - Mastodon
5. 对文档版本与编辑体验，重点参考：
   - Outline
6. 代码级复用前必须检查许可证、依赖、运行环境和 LuckRead 的 Worker / D1 约束。
7. 不能因为第三方项目更先进，就把新的数据库模型、运行时、Worker 或请求链直接搬进 LuckRead。
8. 第三方项目的产品范式、数据建模思想、算法思路可以研究；具体代码应以许可证允许范围和 LuckRead 自身架构为边界。

## 6. 1.1 → 1.2 的技术策略

### 1.1

**先把地基做稳。**

重点是可靠性、边界、性能、成本、Creator 主链路和基础内容体验。

### 1.2

**在稳定地基上做加法。**

重点是编辑器高级能力、真实 Media Pipeline、Mention / Topic / Notification、SEO / Distribution、Analytics，以及更成熟的内容生态能力。

### 1.2 禁止的做法

- 为了引入 Lexical 新能力而整体推翻现有内容 API。
- 为了视频转码而擅自增加 Worker / D1 / Queue。
- 为了 Topic / Mention 再创建第二个 Social / Content authority。
- 为了搜索 / 推荐提前建设完整 Feed / Recommendation / Search 平台。
- 为了“像 TikTok”复制第三方私有实现、源码或资源。

## 7. 当前执行结论

截至本参考文档建立时：

- LuckRead 1.1 内容核心已经进入**基础能力收口阶段**。
- Creator Center audience 读取放大问题已通过 PR #968 收口。
- Short Video MVP 已形成完整的上传、元数据、发布、沉浸式播放和基础社交体验。
- 文章编辑器已经具备结构化文档和插件化基础。
- 后续优先级应从“继续反复修基础 CRUD”转向“把 1.1 的基础设施、性能和稳定性收干净”。

**当前策略：先完成 1.1 的成熟自媒体平台基础，再进入 1.2 的能力加法。**
