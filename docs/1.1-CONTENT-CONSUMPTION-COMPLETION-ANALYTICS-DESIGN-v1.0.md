# LuckRead 1.1 海量内容消费与完播统计系统设计

**版本：v1.0**  
**状态：DESIGN / IMPLEMENTATION PENDING**  
**适用范围：文章（Article）/ 动态（Post）/ 小视频（Video）**  
**Analytics Authority：W11**  
**Async Processing：W10**  
**Analytics D1：D1-03**

> 本文是 1.1 技术设计文档，不改变 LuckRead 已锁定的 12 Worker / 4 D1 / Queue / Service Binding 拓扑。
> 目标是在百万级内容、千万级日常阅读/点赞/评论、数亿级视频播放场景下，避免把用户行为直接转换成 D1 写入或高频 CPU 计算。

## 1. 目标

1. 统计文章阅读完成率、阅读深度、阅读时长。
2. 统计动态浏览、停留、互动。
3. 统计视频播放、3 秒率、25/50/75/90/100% 完成漏斗、完播率、观看时长、复播率、流失点。
4. 统一统计点赞、评论、收藏、分享、关注转化。
5. 支持 Creator Center 查询内容级、创作者级统计。
6. 支持迟到事件、重复事件、异常流量、Bot、回放和指标重建。
7. 海量行为不直接写 D1；D1 主要保存聚合 Projection。
8. 热门内容不能因为单点流量造成 D1 热点争用或 CPU 峰值。
9. 不引入新的 Worker、D1、Queue 或拓扑。

## 2. 非目标

- 1.1 不实现复杂推荐算法。
- 1.1 不实现完整实时数据仓库。
- 1.1 不要求永久保存每一次客户端 heartbeat。
- Creator Analytics 不成为内容、社交、账号等领域的业务事实源。
- Creator Dashboard 不通过同步 COUNT/GROUP BY 扫描海量原始行为。

## 3. 权责边界

W03 Content → 内容状态/内容元数据权威 → analytics events

W05 Social → Like / Comment / Follow / Favorite / Share 权威 → analytics events

W07 Commerce → 订阅/权益/交易业务事实 → analytics events

W10 Async → 批量事件运输、异步处理、重试、削峰

W11 Analytics → Analytics Event / Metric / Projection 权威

D1-03 → Analytics Projection / 查询数据

Cache → Dashboard / 热门统计读取加速

**硬规则：统计失败不能回滚已经成功的业务事实。**

例如点赞成功后 Analytics 暂时不可用，点赞仍然有效；后续通过重放/补算恢复统计。

## 4. 核心数据流

User
→ Article / Post / Video UI
→ Client Event Buffer
→ Batch Upload
→ Cloudflare Edge
→ Auth / Rate Limit / Validation / Abuse Filter
→ W10 Async
→ Dedup / Normalize / Aggregate
→ W11 Analytics
→ Hourly / Daily / Creator Projections
→ D1-03
→ Cache
→ Creator Center

**核心原则：业务请求路径 ≠ Analytics 聚合路径。**

禁止：
- 用户阅读 → D1 INSERT analytics_event
- 用户播放 → D1 UPDATE video
- 用户点赞 → 同步 UPDATE 十几个统计表

应该：
- 海量行为 → 批量事件 → 去重/压缩 → 异步聚合 → 少量 Projection 写入 D1

## 5. 统一 Analytics Event

建议统一事件模型：

| 字段 | 作用 |
|---|---|
| eventId | 全局事件 ID |
| schemaVersion | 事件 schema 版本 |
| eventName | 事件名称 |
| occurredAt | 用户行为发生时间 |
| receivedAt | 服务端收到时间 |
| source | web/app/h5 等 |
| sourceWorker | 来源 Worker |
| actorType | user/visitor/system |
| actorId | 登录用户 ID |
| visitorId | 匿名访客 ID |
| sessionId | 消费 session |
| visitId | 一次访问 |
| contentId | 内容 ID |
| contentType | article/post/video |
| creatorId | 创作者 ID |
| position | 阅读/播放进度 |
| durationMs | 停留/观看时长 |
| properties | 扩展属性 |
| dedupeKey | 幂等/去重键 |
| correlationId | 链路关联 |
| quality | valid/bot/duplicate/suspicious 等 |

事件必须允许乱序、重复、迟到和重试。

## 6. 客户端批量

禁止视频每 1 秒发送一个 heartbeat。

推荐：
- 客户端维护本地 session；
- 5～20 秒批量窗口；
- 页面隐藏/离开时 flush；
- 播放开始、播放成功、完成等关键生命周期事件优先；
- 同一 session 的重复进度只保留最大有效进度；
- 网络异常允许短暂本地缓冲和重试；
- 不保证每一个 heartbeat 永久落库。

客户端只负责减少传输量，最终指标由服务端校验。

## 10. 完播率

基础定义：

completion_rate = valid_completed_plays / valid_play_starts

示例：

valid plays = 10,000,000
25% = 8,200,000
50% = 7,000,000
75% = 5,900,000
90% = 5,100,000
100% = 4,800,000

completion_rate = 48%

Retention：
- 25% = 82%
- 50% = 70%
- 75% = 59%
- 90% = 51%
- 100% = 48%

### Session 压缩

一个播放 session 不需要永久保存几十个进度事件。

例如：
10% → 25% → 25% → 40% → 50% → 50% → 75%

最终保存：
- maxProgress = 75%
- watchMs
- replayed
- session metadata

## 11. 点赞 / 评论

Like / Comment 是业务事实，不能为了省成本而丢弃。

统计链路：

W05 authoritative mutation
→ idempotency
→ analytics event
→ W10
→ W11 aggregation

禁止一次点赞同步执行：
- creator total update
- content trend update
- hourly aggregation
- daily aggregation
- ranking update
- dashboard refresh
- notification fan-out

这些属于异步派生工作。

## 12. 去重

至少三层：

1. Event：eventId
2. Retry：dedupeKey
3. Session：contentId + sessionId

同一个 session 不能因网络重试重复计算播放。

进度使用：

max(previousProgress, incomingProgress)

只接受有效单调进度。

## 15. 热内容保护

真正容易造成数据库热点的是单个爆款，而不是百万篇普通内容。

内容流量等级：

NORMAL
HOT
EXTREME

EXTREME 内容必须：
- Edge 批量聚合；
- 延迟 flush；
- 避免每请求更新同一 D1 row；
- 使用时间窗口累计；
- 最终批量写入 Projection。

禁止把热点计数器设计成每次行为同步 UPDATE 的单行热点。

## 16. 热 / 温 / 冷数据

Hot：
minute/hour + daily

Warm：
hour/day

Cold：
day/week/month

历史细粒度数据按活跃度压缩。

目标：百万内容不会永久产生无限细粒度统计写入。

## 17. UV / 基数统计

不建议永久保存 user × content 作为 Creator Analytics 的唯一 UV 来源。

大规模 UV 可以使用 HyperLogLog 类基数估算结构。

需要绝对精确的业务场景另行使用权威业务数据。

## 18. Cache

Creator Center 查询：

Cache → Projection → D1

禁止：

Dashboard → COUNT(*) / GROUP BY / SUM() → 原始事件

建议：
- 内容统计短 TTL；
- Creator Dashboard 30～60 秒 TTL；
- 热门内容积极缓存；
- Cache miss 才读取 Projection；
- Dashboard 查询不触发重聚合。

## 19. 可重建指标

事件和 Projection 必须带：
- schemaVersion
- metricVersion
- aggregationWindow

如果 Bot 规则、完播定义、UV 算法或清洗规则改变，可以：

Event → Reprocess → Metric v2 → Projection v2

不能人工修改历史数字。

## 20. 容量目标

- 单个热门内容承受极高突发流量；
- 海量普通内容不会造成 D1 行数线性爆炸；
- 用户行为增长不等比例增加 D1 写入；
- Dashboard 查询复杂度与原始事件量解耦；
- Analytics CPU 主要用于批量处理，而不是逐请求统计；
- 热点内容不会产生 D1 hot-row contention；
- Analytics 故障不阻塞发布、阅读、点赞、评论。

## 22. 成本红线

禁止：
- 每次阅读 → D1 write
- 每次 scroll → D1 write
- 每秒 video heartbeat → D1 write
- 每个进度点 → synchronous D1 update
- 每次 like → 同步更新多个统计表
- Dashboard → raw COUNT/GROUP BY
- Hot content → synchronous hot-row counter
- Analytics failure → rollback business mutation

必须：
- Batch
- Async
- Dedup
- Aggregate
- Projection
- Cache
- Hot-key protection
- Rebuild
- Versioned metrics

## 23. 与现有架构的关系

只使用现有：
- 12 Workers
- 4 D1
- existing Queue
- existing Service Bindings

不新增：
- Worker
- D1
- Queue
- Topology

Canonical boundary：

W03 = Content Authority  
W05 = Social Authority  
W10 = Async Processing  
W11 = Analytics Authority  
D1-03 = Analytics Projection

后续实现不得为了方便把统计责任重新塞回 W03/W05，也不得把原始高频行为变成 D1 同步写路径。

## 24. 最终目标

建立完整闭环：

海量消费事件
→ 高效采集
→ 去重
→ 质量控制
→ 异步聚合
→ 可重建指标
→ D1 Projection
→ Cache
→ Creator Analytics

最终即使平台进入百万级文章、千万级日常互动、数亿级视频播放，系统也不能把行为一比一转换成 D1 写入。

**核心目标：行为量可以非常大，而 D1 / CPU 增长必须是受控的、分层的、可预测的。**
