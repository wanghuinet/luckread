# LuckRead 信息流与平台低成本高性能架构契约 v1.0

**状态：USER-REQUESTED / AUTHORITATIVE ARCHITECTURE ADDENDUM / IMPLEMENTATION AND EVIDENCE PENDING**  
**适用范围：LuckRead React Native CLI App、信息流 API、Cloudflare Workers、Durable Objects、Cache API、KV（仅在论证后）、Queues、Neon PostgreSQL、R2 及相关客户端缓存。**  
**优先级：本契约约束信息流读取、缓存、计数、推荐排序和平台成本优化。与当前已验证的数据模型及权限安全要求冲突时，以数据正确性、隐私和安全为先。**

## 1. 核心目标

LuckRead 应以尽可能少的 Neon 往返、Worker 内部调用和无效唤醒，提供接近本地应用的首屏体验、稳定分页、实时互动和可持续运营成本。

不可妥协原则：
1. 优先减少不必要的请求和重复计算，而不是牺牲数据正确性。
2. Neon 是用户、关注关系、帖子、互动权威记录的关系型持久化来源；缓存和 DO 状态均为可重建派生数据。
3. Worker 负责 API、鉴权和业务编排；DO 用于有明确协调/实时状态需求的场景，不作为所有功能的默认存储层。
4. App 本地缓存负责快速首屏与离线体验，服务端增量同步负责最终收敛。
5. 缓存必须尊重隐私、Block、屏蔽、删除、封禁、内容可见范围和授权变化。
6. 成本目标以真实 DAU、请求量、读写量、媒体流量和在线用户小时测量，不得以 DAU 单一数字承诺固定月账单。

## 2. 信息流分发策略：按需拉取为主，混合分发为目标

### 2.1 普通用户
- 默认采用 Fan-out on Read：发帖只写一份权威帖子记录，不为每个粉丝复制一份时间线记录。
- 读取时根据关注关系、内容可见性、Block/屏蔽规则和时间窗口构建候选帖子 ID 集合，再批量读取帖子内容。
- 查询必须有界，避免一次请求扫描无上限关注关系或帖子记录。
- 通过稳定游标翻页，不得使用深层 OFFSET 作为主要分页机制。

### 2.2 大 V 与高关注量账号
- 不强制所有账号采用同一种分发方式。
- 当某个作者的关注者规模导致 Fan-out on Read 成为明显瓶颈时，允许采用 Fan-out on Write 或混合模式。
- 分发策略必须由关注者规模、活跃度、读取频率、写放大和缓存命中数据驱动；设置可配置阈值并支持回退。
- 大 V 帖子可在读取时与预计算候选集合合并；必须去重并保证排序稳定。
- 禁止未经压测就给所有作者做全量粉丝扇出。

### 2.3 推荐流
- 初期采用可解释的候选集 + 时间衰减 + 互动热度 + 用户兴趣/安全过滤的简单排序。
- 热度/推荐分数可通过定时任务或事件驱动方式预计算，避免每次打开信息流执行昂贵计算。
- 预计算结果必须标记版本、计算时间和过期策略；源数据变化后允许短暂最终一致，但删除、封禁、隐私和 Block 过滤必须实时或在安全要求内立即生效。
- 推荐系统初期不要求引入独立复杂机器学习基础设施；只有指标证明必要时再演进。

## 3. 缓存分层与失效

### 3.1 帖子内容缓存
- 公开、可共享的帖子内容可按 post ID 缓存；缓存内容应有版本/更新时间或 ETag。
- 内容缓存 TTL 可根据内容热度、更新频率和成本测量设置，从短 TTL 到较长 TTL 动态调整；不得把“几分钟到几小时”作为不分场景的固定值。
- 帖子编辑、删除、作者封禁、可见性改变、审核状态改变必须触发缓存失效、版本校验或安全过滤。
- 用户私密内容、仅关注者可见内容及包含用户级授权结果的响应，不得进入公共共享缓存。

### 3.2 时间线 ID 列表缓存
- 时间线候选 ID 列表可使用短 TTL 缓存，以降低重复计算和 Neon 读取。
- 缓存 key 必须区分用户/时间线类型/必要的权限版本/语言或排序版本；不能因共享缓存而泄漏个性化结果。
- 列表缓存只保存候选 ID 与必要排序元数据，读取帖子详情时仍需执行可见性与授权过滤。
- 新帖、关注关系变化、Block、静音、取消关注、内容删除和封禁等事件必须有明确失效或过滤策略。
- 短 TTL 不能代替权限检查；安全撤销不得等待普通缓存 TTL 自然过期。

### 3.3 Cloudflare Cache API、KV 与客户端缓存
- Cloudflare Cache API 优先用于适合边缘共享的公开、可缓存 GET 内容；必须正确处理 Cache-Control、vary、版本和失效。
- KV 仅适合可容忍最终一致、读多写少、非事务性的派生数据；不得用于消息、权限或其他要求强一致的权威数据。
- RN 客户端使用本地持久化缓存，先展示上次成功数据，再在后台刷新；必须有缓存版本、账号隔离、过期策略和登出清理。
- 客户端缓存不作为权威数据；账号切换、登出、封禁或权限撤销后必须清理/隔离旧数据。
- 私密信息不得写入公共 Cache API；不得将包含授权内容的 API 响应设置为 public。

## 4. 分页、批量读取与 SQL

- 信息流必须采用稳定游标分页，排序键至少具备稳定唯一性，例如 (created_at, id)；若按热度排序，需定义稳定 tie-breaker 和游标版本。
- 禁止依赖深层 OFFSET；避免分页过程中因新帖插入造成重复或漏项。
- 先查询有界候选 ID，再批量加载详情；禁止每个帖子单独查询作者、互动数、媒体和权限信息造成 N+1。
- 通过批量查询/合理 JOIN/预计算摘要减少往返；避免无界 JOIN、超大 IN 列表和单请求过多结果。
- 索引依据实际 EXPLAIN (ANALYZE, BUFFERS) 和读写成本建立；不要仅凭字段名称盲目建索引。
- 对关注关系、帖子作者/创建时间、时间线游标、互动唯一约束和必要过滤字段建立匹配查询模式的索引。
- 帖子表按时间分区不是默认要求；只有当数据量、维护/归档策略、索引尺寸或查询计划证明收益时，才设计分区并完成迁移演练。
- 每次 API 响应必须有明确上限：候选数、返回帖子数、字段体积和关联摘要数量均需受控。

## 5. 点赞、浏览与互动计数

- 点赞事实必须具备用户/对象维度的唯一约束或等效幂等机制，防止重复点击和重试产生重复计数。
- 点赞/取消点赞的权威状态必须可恢复；不能只保存在 Worker/DO 内存。
- 高频浏览计数可按事件采样、去重、分片累计或批量聚合，最终再写入 Neon；需定义允许的统计延迟、去重窗口和丢失容忍度。
- 计数缓冲不能只存在 DO 内存；必须使用持久化缓冲、可重放队列或其他可恢复机制，并处理重试、重复投递和落库失败。
- DO 可用于热点计数协调或分片累加，但需压测热点对象、单对象吞吐、存储成本和故障恢复；不得默认所有点赞都进入一个 DO。
- 展示计数可短暂最终一致；用户自己的点赞状态、权限和关键业务事实必须准确。
- 对关键互动事实和聚合展示值分离建模；不得为了展示计数而让每次读取执行全表 COUNT。

## 6. App 首屏与本地体验

- App 首屏优先展示上次成功加载的信息流和本地缓存的必要媒体缩略图。
- 后台使用游标/版本请求增量刷新，不应每次打开都重新下载整页历史。
- 下拉刷新与后台刷新必须合并，避免重复请求；分页请求要防止并发重复加载。
- 网络错误时保留可用旧内容并明确提示数据更新时间；不得用空白页面覆盖本地缓存。
- 图片和视频采用尺寸适配、缩略图、渐进加载和可取消预取；不得预取超出屏幕/用户行为合理范围的大量媒体。
- 列表使用虚拟化和稳定 key，避免无关事件触发整列表重渲染。
- 客户端缓存按账号隔离；退出账号后清理敏感数据，避免多账号串数据。

## 7. 媒体存储与分发

- 图片、视频和文件原件放 R2，不进入 Neon；Neon 保存 object key、mime、大小、hash、尺寸、所有者、权限、扫描状态等必要元数据。
- 上传优先使用受控直传流程，避免大文件经 Worker 中转造成额外 CPU/带宽开销。
- 公开媒体可通过 Cloudflare CDN 缓存；私密媒体使用受控访问、短时签名 URL 或授权代理，不能公开缓存。
- 设计缩略图/转码/多分辨率策略，按实际使用生成，避免无用衍生文件。
- R2 存储与操作请求仍然计费；“出口流量免费”不等于整体媒体成本为零。应监控存储量、Class A/B 操作、转码和 CDN 请求。

## 8. Worker、DO、Queues 与后台任务边界

- Workers 负责鉴权、请求验证、业务编排和轻量数据访问；一次请求内复用已加载的用户/权限上下文，合并重复内部调用。
- DO 仅用于需要单对象协调、实时连接、短期状态或热点分片的工作；不得为了减少 Neon 访问把所有缓存、计数、会话数据都迁入 DO。
- DO 应优先使用 WebSocket Hibernation API 适配长连接；禁止固定高频心跳、无任务 Alarm 或轮询导致无意义唤醒。
- Queues 适合异步通知、可重试聚合、搜索索引、媒体处理和可恢复事件；消费者必须幂等、限速、可观测并支持失败重试/死信处理。
- 不得把 Queue 的至少一次投递误认为 exactly-once；所有消费副作用必须可去重。
- 不为简单批量写入而盲目增加 Queue/DO/KV 等组件；新增组件必须比较其调用费、存储费、维护成本和故障模式。

## 9. Neon 连接、计算与结构优化

- 先盘点当前 Worker 到 Neon 的连接路径，再决定使用 Neon pooled connection、Cloudflare Hyperdrive 或现有执行器；避免无依据叠加多层连接池。
- 若使用 Hyperdrive，按其连接管理模型配置适配的 Neon 连接串；不要机械地把 Pooler URL 与 Hyperdrive 叠加。
- 每次变更必须记录连接获取方式、连接复用、事务边界、池饱和、数据库唤醒和查询延迟。
- 事务保持短小；事务内不等待外部 HTTP、推送、R2 上传、Queue 消费或 WebSocket 广播。
- Neon CU 上限、自动伸缩、闲置行为和告警按实际套餐/项目配置核对；设置资源/账单告警与异常增长监控。
- 通过查询计划、慢查询和索引读写放大进行优化；不盲目分区、不盲目增加索引、不以牺牲数据一致性换取更低 CU。
- 对热数据、冷数据、保留周期和归档策略建立数据生命周期方案，实际分区/归档须单独压测和演练。

## 10. 成本与可观测性

必须按实际工作负载建立基线，至少记录：
- DAU/WAU、每用户每日打开次数、每次信息流请求数、分页深度、刷新率。
- 信息流候选集规模、帖子详情批量加载量、缓存命中率/未命中率、失效次数。
- Worker 请求数、CPU/耗时、内部 Service Binding/RPC 次数和错误率。
- Neon 活跃 CU/计算时长、查询/事务数、连接池等待、慢查询、锁等待、存储和索引体积。
- DO 请求数、WebSocket 消息数、Duration、唤醒/Alarm 次数、对象数和存储量。
- Queue 入队/出队/重试/死信量；R2 存储量、操作次数、媒体分发请求和流量。
- 每千次/每万次信息流刷新成本、每万条互动事件成本、每 GB 媒体成本，以及按 DAU 和活跃用户小时归一化的成本。
- 缓存命中率不能单独作为成功指标；同时看命中数据正确性、权限过滤、缓存失效延迟和源数据库负载。

禁止未经测量承诺“几万 DAU 每月几十美元”或“Neon 几乎零成本”。DAU 不等于请求量；成本由使用频率、消息/互动量、缓存命中、媒体流量、在线连接时长、计算配置和保留策略共同决定。

## 11. 安全、隐私与缓存隔离

- Block、静音、取消关注、私密账号、内容删除、封禁和年龄/地区等可见性规则必须在缓存读取后仍得到正确执行。
- 任何缓存命中都不能绕过当前授权；必要时以权限版本、用户版本或实时过滤保证撤权及时生效。
- 私密帖子、私人消息和用户级个性化响应禁止进入公共共享缓存。
- 不在日志中记录私人内容、令牌、签名 URL 或不必要的个人信息。
- 缓存 key 不得仅由 URL 组成而忽略身份、语言、权限或内容版本等必要维度。
- 缓存失效失败时必须优先保护隐私；宁可回源验证或暂时不展示，也不能泄露已撤销权限的内容。

## 12. 测试与验收

每个完整阶段必须包含：
1. 稳定游标分页测试：插入新帖、删除、编辑、重复时间戳和翻页期间数据变化。
2. 关注/取消关注、Block/解除 Block、私密账号、帖子可见性和封禁后的缓存权限测试。
3. 公共缓存与用户隔离缓存的命中/失效测试。
4. N+1 检测、SQL 查询计划、批量加载和高关注账号压力测试。
5. 点赞幂等、并发切换、计数缓冲故障、Queue 重试和重复投递测试。
6. 客户端冷启动、热启动、离线打开、后台刷新合并、账号切换和缓存清理测试。
7. R2 上传、缩略图、私密媒体授权、删除和孤儿对象清理测试。
8. Neon 连接池/Hyperdrive 真实配置验证、CU 峰值和故障恢复测试。
9. Worker/DO/Queue 的重试、休眠/唤醒、速率限制和成本测量。

验收报告必须包含 commit SHA、环境、数据规模、请求模型、缓存命中率、SQL/Neon 负载、p50/p95/p99、错误率、成本口径、对照基线和剩余风险。没有证据不得标记性能或成本目标完成。

## 13. 禁止事项（STOP）

- 正式帖子、关注关系、点赞事实只存在于缓存、DO 内存或客户端本地。
- 把公共缓存用于私密/个性化内容，或让缓存命中绕过权限检查。
- 所有用户一律 Fan-out on Write，或所有用户永远只能 Fan-out on Read，不按数据选择策略。
- 使用深层 OFFSET、无界候选集、N+1 或每次刷新全量拉取。
- 计数只写 DO 内存，或异步落库没有幂等、重试和恢复机制。
- 将分区、KV、Queue、Redis 或额外 DO 当成默认答案，未测量就增加架构复杂度。
- 假设 R2 免费、Neon 固定低价，或根据 DAU 单一数字承诺月成本。
- 以缓存 TTL 代替 Block、删除、封禁和权限撤销。
- 未经实际配置验证就断言 Neon Pooler 与 Hyperdrive 应当叠加使用。
- CI/压测/故障演练证据不足却宣称完成。

## 14. 实施顺序

1. **现状审计**：检查当前 Feed API、SQL、索引、关注关系读取、帖子详情加载、缓存、App 本地持久化和媒体链路。
2. **查询与客户端闭环**：稳定游标、批量详情加载、N+1 消除、本地优先首屏、增量刷新和账号缓存隔离。
3. **缓存闭环**：公开帖子内容缓存、短 TTL 时间线 ID 缓存、版本/失效机制、隐私与 Block 安全过滤。
4. **互动计数闭环**：点赞幂等、浏览采样/聚合、持久化缓冲、重试和对账。
5. **混合分发与推荐**：按作者规模启用混合分发，建立预计算排序和推荐候选集。
6. **成本压测**：基于真实请求/媒体/DAU 模型测量 Worker、DO、Neon、Queue、R2 成本，再决定分区、归档和额外基础设施。

**最终验收定义：** 信息流首屏本地优先、增量同步、稳定游标、查询有界、缓存安全、互动可恢复；Neon 只承担权威数据与必要查询；所有派生缓存均可重建；成本可按实际工作负载测量和持续优化。
