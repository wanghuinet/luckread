## 1. Purpose and decision

LuckRead 1.1 will build its creator analytics capability by reusing mature open-source analytics code wherever runtime, licensing, security, and ownership boundaries permit. The target is approximately **80% reuse of eligible generic analytics-engine and dashboard capability code**, with the remaining code focused on LuckRead-specific metrics, domain adapters, authorization integration, privacy rules, and operational contracts.

The 80% figure is an engineering target, not a claim that 80% of the entire LuckRead repository can be copied unchanged. It is not considered achieved until the source and license inventory, module-level reuse report, tests, and current-head evidence have been reviewed.

**Selected approach:** evaluate Facet first as the closest single-Worker + D1 functional base; use Traks as the permissive-license reference for selected reusable modules and for hot/cold analytics patterns; use HitsOnce as a reference for storage abstraction and batch writes; use PostHog and Umami primarily as product/analysis UX references, not as the Worker runtime to embed.

No source is copied until its exact file/package license and required notices are recorded. If Facet's AGPL-3.0-only server/dashboard core is not acceptable for LuckRead's distribution and hosted-service model, do not copy those covered files. Re-scope the reuse target around components whose licenses are acceptable and record the resulting variance rather than bypassing license obligations.

## 2. Scope

Within the existing 1.1 Analytics scope and its admitted Feature IDs, the system supports:

- Articles, dynamics/posts, and short videos as separate content types.
- Page/view counts, privacy-safe unique views, reading/view duration, video play duration and completion where reliable playback events exist.
- Likes, comments, shares, bookmarks/favorites, follow/follower changes, net follower growth, and engagement summaries.
- Creator-level and content-level trends, rankings, date ranges, and daily/time-series aggregation.
- Traffic source, campaign, device class, locale/region where available and privacy-approved, and basic paths/funnels/retention where event identity and consent rules permit.
- Subscription and revenue summary only from authoritative W07 commerce/payment/ledger records; analytical events may explain attribution but cannot create financial facts.
- Creator dashboard and authorized operations reporting with least-privilege data access.

Any analytics feature whose Feature ID is outside the already admitted 1.1 scope requires its own scope/contract admission. This addendum creates no new Feature IDs and does not mark any analytics Feature ID GREEN.

## 3. Code-reuse objective and measurement

### 3.1 Target

Target at least 80% reuse of the **eligible generic analytics capability surface** across these modules, subject to the audit gate:

- tracker / event ingestion request handling;
- event payload schema validation and normalization;
- time-window and period calculations;
- standard traffic dimensions and aggregation helpers;
- chart, date-range, filter, and dashboard presentation primitives;
- standard analytics query patterns and materialized-rollup helpers;
- generic retention, funnel, and trend primitives where they fit existing contracts.

LuckRead-specific code remains necessary for domain event adapters, article/dynamic/video semantics, W03/W05/W07 mappings, creator ownership filters, authorization, privacy/consent, event reconciliation, and business KPI formulas.

### 3.2 Required report

Before implementation, maintain a `reuse-inventory.md` or equivalent review record with, for each reused package/file:

- upstream repository and immutable commit/tag;
- exact path and package name;
- license and copyright/NOTICE obligations;
- direct copy, dependency, fork, or pattern-only classification;
- required changes and compatibility gaps;
- tests proving behavior was preserved;
- source-attribution and update/review owner.

Report both (a) reuse by generic module/capability and (b) source-line statistics for reused, modified, and new code. Exclude generated files and vendored build output; do not count configuration, LuckRead domain contracts, or tests as copied implementation. Never alter the denominator to make the target appear met. If the license/runtime audit makes the 80% target infeasible, document the exact blocker and submit a change-control decision before proceeding.

## 4. Upstream candidates and reuse boundaries

| Candidate | Reuse role | Fit and constraints |
|---|---|---|
| [Facet](https://github.com/writerslogic/facet) | First code-level candidate for tracker, event ingestion, D1 rollups, dashboard/API patterns | Designed around one Worker + D1 and includes page, session, channel, funnel, goal and experiment analytics. Its README marks the self-hosted core as AGPL-3.0-only and some packages as separately MIT/Apache licensed. Exact package/file license review is a blocking prerequisite before copying or embedding. |
| [Traks](https://github.com/shivamanupadi/traks) | Preferred MIT-licensed source for individually compatible schemas/helpers and hot/cold data patterns | MIT-licensed. Reuse only isolated modules that pass dependency/runtime review. |
| [HitsOnce](https://github.com/jtwebman/hitsonce) | Reference for Store abstraction, HTTP/app/data separation, batched writes, retention and deduplication | Cloudflare Worker + D1 and a pluggable store interface; repository is AGPL-3.0. No AGPL-covered code is copied until the license gate is passed. Do not add its optional Queue consumer or another Worker as a side effect. |
| [PostHog](https://github.com/PostHog/posthog) | Feature semantics and optional external product-analytics adapter reference | Useful reference for trends, funnels, retention, cohorts and behavioral analysis; its self-hosted backend is not treated as a Cloudflare Worker/D1 runtime. Existing optional-adapter boundary in the OSS integration addendum remains in force. |
| [Umami](https://github.com/umami-software/umami) | Dashboard UX, website metrics and PostgreSQL-backed reporting reference | Node.js/PostgreSQL application; do not claim the complete Umami backend can run natively inside a Cloudflare Worker. Reuse code only after auditing its actual package license and runtime compatibility. |

These projects are not merged wholesale. Facet is the first fit assessment, not pre-approved vendoring. Traks is the preferred permissive-license source for compatible individual code; HitsOnce and Facet core code remain license-gated. Avoid combining files from different projects without per-file provenance.

## 5. Target architecture

```text
W03 content / W05 social / W07 commerce
        │
        │ approved domain-event contracts only
        ▼
     W11 Analytics
  schema + quality checks
  dedupe + identity mapping
  aggregation + metric versions
        │
        ├── Analytics-only D1: hot counters, daily rollups, dashboard read models
        │
        └── Neon PostgreSQL (optional later phase): longer history and complex multidimensional queries
                  │
                  ▼
        LuckRead creator / operations dashboards
```

Rules:

1. W11 remains the only analytics execution and persistence owner. No new Worker is created.
2. W03, W05 and W07 remain authoritative for their own facts. They do not write directly into the analytics D1 or Neon.
3. Events enter through already authorized event/API delivery contracts. This document does not invent a new Worker-to-Worker binding, Queue, topic, or transport. If the existing contract does not supply an event, implementation is blocked until that surface is admitted.
4. One dedicated analytics-only D1 is an explicit 1.1 exception to the four existing business D1 domains. D1-01 through D1-04 keep their existing ownership and schema authority unchanged. Only W11 may access the analytics D1 after its physical binding and access contract are reconciled.
5. Neon is an optional second phase, not a prerequisite for the first dashboard release. It is an external analytics store, not one of the canonical D1 domains and not a source of truth for identity, content, social interactions, payments, entitlements, or ledger facts.
6. No additional Worker, Queue, Service Binding, or Payload Core modification is authorized by this analytics plan.
7. A document/PR does not create the D1 database or Neon project. Provisioning, binding, secrets, schema/migrations, data retention and runtime evidence must pass the current repository gates.

## 6. Storage responsibilities

### Analytics-only D1

Use D1 for bounded, fast dashboard reads and pre-aggregated derived data, for example:

- current/day/week/month counters and daily snapshots;
- content/creator metric rollups;
- deduplication/idempotency keys only where necessary and explicitly bounded by retention;
- metric version, rollup watermarks and reconciliation status;
- cached/materialized dashboard read models that can be rebuilt.

Do not make every dashboard request scan a raw event table. Avoid high-cardinality unbounded dimensions and synchronous per-action fan-out. Use indexed filters, bounded time windows, batch writes and rebuildable aggregates. Keep D1 derived; do not use it to overwrite authoritative business rows in D1-01..D1-04.

### Optional Neon PostgreSQL

Use Neon only when data volume or query needs justify it. Candidate responsibilities include longer-lived event history, ad hoc multi-dimensional queries, cohort analysis over extended windows and heavy report/export queries that should not compete with D1 hot counters.

Neon integration must use a Workers-compatible connectivity mode and connection management; do not assume a persistent TCP connection or copy a Node-only database driver into the Worker. Secrets, schema ownership, backup/retention/deletion, cost limits, retry/idempotency and failure handling require explicit review. Failure to write Neon must not fail the user's core content/social/commerce operation.

## 7. Event quality and metric contract

Each accepted event must carry, where applicable, a stable event ID, event name/version, actor/subject mapping, entity type/ID, occurred/received timestamps, source, correlation/request identifiers, and schema version. Properties must be allow-listed by event schema and privacy purpose; do not accept arbitrary client properties directly into trusted KPIs.

Processing order:

```text
Schema validation
→ identity/session mapping
→ timestamp validation
→ consent/purpose and privacy filter
→ risk/bot/suspicious-event classification
→ idempotent deduplication
→ validated event
→ aggregation / versioned metric
→ materialized dashboard read model
```

Event states must distinguish at least VALID, SUSPECT, INVALID, DUPLICATE, LATE and REJECTED. Delayed, replayed, corrected or reprocessed events must be handled deterministically and leave enough traceability to reconcile results. A browser-generated view/like event alone cannot override W03/W05/W07 authoritative state.

Metric definitions include metric ID/version, formula, authoritative source events or domain facts, exclusions, dimensions, window, timezone, freshness expectation and owner. Keep occurredAt, receivedAt and processedAt distinct. Derived results must be rebuildable from approved source events and authoritative facts.

## 8. Domain metrics and authority

| Domain | Analytics examples | Authority rule |
|---|---|---|
| Content / W03 | article and dynamic views, reading duration, short-video plays/completion, content ranking | Content identity and publish state are resolved by W03 contracts. Do not infer a valid content object from client input alone. |
| Social / W05 | likes, comments, shares, favorites, follows, net follower growth, engagement rate | Use valid W05 domain events or reconciled authoritative aggregates. Duplicate/replayed events must not inflate counts. |
| Commerce / W07 | subscription conversion, renewal/cancellation, order/revenue/refund summaries | Revenue and order facts must reconcile to W07/ledger sources. Analytics never mints financial facts or updates balances. |
| Traffic / behavior | source, device, page paths, funnels, retention and sessions | Collect only approved minimum attributes; honor consent/purpose and privacy policy. Raw IP and unnecessary credentials/secrets are forbidden in analytics payloads. |

## 9. Authorization and dashboard boundary

- Every dashboard query is scoped to the authenticated actor and the canonical ownership/organization/role/resource authorization contract.
- An analytics aggregate, dashboard UI state, cached response or upstream OSS admin token never grants permission.
- Creator reports are limited to the creator's authorized data and permitted aggregate dimensions. Platform-wide or restricted analytics require explicit permission and audit.
- Reuse existing LuckRead authorization and identity contracts; do not import an upstream project's user/session authority into LuckRead.
- Sensitive fields must be minimized, retention-limited and deletable according to the platform data lifecycle.

## 10. Implementation waves

### A. Source and license audit

Inspect pinned commits, package manifests, build commands, database migrations, authentication/access controls, runtime APIs, and every target file license. Produce the reuse inventory and choose either an approved Facet-core route or a license-compatible module route. No source copy/deployment before this gate passes.

### B. Contract and adapter closure

Map in-scope 1.1 analytics IDs to W11/T22/T23, approved source events, dimensions, metric versions, APIs/DTOs, access checks and test cases. Reuse existing analytics contracts; do not create competing metric definitions or event ownership.

### C. Native W11 + analytics D1 MVP

Integrate the approved event collector/validation/aggregation/dashboard modules into W11, bind the dedicated D1 only after the D1 access guard and canonical mapping artifacts are updated, and implement article/dynamic/video plus social growth summaries. No new Worker, Queue or service binding.

### D. Reconciliation and creator dashboard

Add date-range filters, content rankings, trend charts and creator-level summaries. Verify aggregate parity against authoritative W03/W05 data and restrict reports with the canonical permission contract. Record current-head CI/runtime evidence.

### E. Optional Neon history and advanced analysis

Only after the D1 MVP demonstrates a need, add Neon as a separate, optional analytics store under explicit secret, connectivity, cost, data lifecycle and failure-mode review. Start with a small set of read-heavy historical queries; do not dual-write every business mutation synchronously.

## 11. Acceptance criteria

The analytics reuse work is not GREEN until all applicable checks pass:

- [ ] Upstream revision, license and attribution inventory is complete for every copied/dependent component.
- [ ] The generic module reuse report measures the 80% target honestly and lists deviations/blockers.
- [ ] No third-party runtime, database schema or authorization authority is silently imported.
- [ ] W11 is the only Worker for this analytics capability; no new Worker, Queue, or Service Binding was added.
- [ ] The analytics-only D1 exception is reflected in the canonical mapping, binding/permission declaration, migration and verification artifacts before runtime binding/provisioning is considered complete.
- [ ] D1-01..D1-04 domain ownership and their current schemas remain unchanged.
- [ ] Duplicate, replay, late, invalid, bot/suspicious and corrected events have deterministic tests.
- [ ] Content metrics reconcile to W03 facts; social metrics reconcile to W05 facts; financial metrics reconcile to W07/ledger facts.
- [ ] Public dashboard queries are bounded/cached appropriately; private responses are not shared-cached; authorization and ownership-negative tests pass.
- [ ] User-facing content/social/commerce writes do not wait for analytics or Neon.
- [ ] Privacy, consent/purpose, retention, deletion, logging redaction and secret handling have tests/review evidence.
- [ ] Performance tests cover burst ingestion, aggregate query latency, bounded D1 reads/writes and cache behavior.
- [ ] CI, runtime evidence (where required), and current-head reconciliation are linked before marking the relevant feature GREEN.

Neon is optional for the first release; if it is not introduced, the Neon-specific checklist items are explicitly marked NOT APPLICABLE, not silently passed.

## 12. Stop conditions

Stop implementation if any of the following occurs:

- license obligations are unresolved or source provenance is unknown;
- meeting the 80% target would require importing incompatible or unapproved infrastructure;
- any business Worker writes directly to the analytics database outside an admitted event contract;
- analytics becomes the authoritative source for identity, content, social interaction, order, payment, entitlement or ledger facts;
- unvalidated events can directly alter trusted KPI counts;
- a new Worker/Queue/Service Binding is introduced implicitly;
- the extra D1 is bound before mapping/access contracts are reconciled;
- Neon outages can fail core product transactions;
- dashboard access bypasses canonical authorization or exposes restricted creator/platform data;
- the project represents planned, unrun or unverified work as GREEN.
