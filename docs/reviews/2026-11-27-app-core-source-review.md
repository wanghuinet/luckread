# Luckread App 核心页面源码评审（Feed / 发布 / 搜索 / 通知 / 私信 / Profile）

> 评审基准：X / Threads 的信息密度、操作反馈、稳定性、状态恢复、隐私边界与移动端响应。仅审查 main 当前源码，不代表真机运行、视觉测量或后端安全验证。任何未运行验证均标记为待验证。

## 范围和方法
- App Feed：首页时间线、分页/刷新/缓存/切换、媒体、tab/导航
- 发布：草稿、线程、媒体选择/上传、排序、轮询/定时、回复权限、失败恢复
- Search：历史、热门、话题、内容和用户搜索、请求取消与账户隔离
- Notifications：筛选、分页、读状态、深链、错误/重试
- Messages：会话、请求、群聊、实时消息、附件、编辑/撤回、读/typing、账号切换
- Profile：个人信息、内容/回复/点赞、关注、私信入口、滚动体验
- 不对源代码无法证明的真机动画、网络体验、视觉对齐及完整功能打分。

## 源码可见的正向基线
- Feed采用React Query无限查询、视图内容hydration、tab滚动可见性机制，并明确使用viewerId构造查询key，具备账户数据区分的基础。
- Search维护不同搜索请求的AbortController/requestId，包含历史/热门/话题/内容/用户名等独立状态，显示出防竞态设计。
- Notifications具有requestId/AbortController、viewer切换隔离状态、分页、读状态操作、深链通知ID处理。
- 发布页包含draft autosave、草稿指纹、待上传媒体恢复、幂等键、媒体预处理/上传、线程编辑、排期和回复受众控制等较完整的复杂流程。
- 私信页面有分页查询、实时连接、增量拉取、typing、发送幂等/缓存管理、编辑/撤回、附件上传、AppState/focus生命周期处理。
- Profile页面采用Animated/Reanimated滚动结构、RefreshControl相关机制、关注按钮和私信创建入口。

## X / Threads体验标准（验收而非空泛复刻）
1. 首屏：无需阻塞spinner；缓存内容先展示且刷新状态清晰；新数据到达不打断用户滚动。
2. 发布：点击后可反馈进度；避免重复提交；上传/排期/草稿可恢复；错误明确且可操作。
3. 搜索：输入/提交/切换分类即时响应；历史可编辑/清空；取消请求；分页不重复。
4. 通知：未读状态明确、筛选稳定、点击可直达、目标不可用时给合理提示。
5. 私信：消息即时但状态准确；断线重连/重复事件处理；请求、群聊、附件、编辑/撤回与账户安全。
6. Profile：头部折叠自然；关注状态一致；内容列表刷新/分页/空态/错误态完整。
7. 全局：每次操作可见反馈，错误可恢复，返回路径可预测，动态字体/屏幕适配/读屏可用。
8. 数据隔离：账户切换和登出即清理或封闭所有旧账户展示、请求、实时事件、搜索/草稿/媒体恢复记录。

## 本轮评估结论
当前源代码显示 App 核心流程已存在较多实现，不能再用“缺少页面”概括。真正缺口集中在**运行时证据、端到端状态覆盖、视觉基线对齐和指标体系**。因此不在源码层随意给出“整体复制百分比”；需建立各模块的源码覆盖率、自动化验证、真机验证、指标验证四栏证据，并逐项闭环。
