# LuckRead 1.1 Delivery Roadmap — OSS Reuse Plan

**Status:** PROPOSED / PLANNING ONLY  
**Scope:** Re-sequence the existing 1.1 plan to reuse selected open-source components and reduce custom implementation.  
**Architecture guard:** Keep the existing 12 Workers / 4 D1 / 25 Tasks, existing Queue and Service Bindings. No new Worker, D1, Queue, or Service Binding. Payload Core and Better Auth source remain unchanged. This plan does not amend canonical domain contracts by itself.

## 1. Decisions and reuse boundaries

| Area | Owner / placement | Decision | What it replaces or avoids |
|---|---|---|---|
| Account and sessions | W02 | Continue Better Auth; do not add a second account/session framework | Avoids parallel identity/session implementations |
| Authorization | W08 | Use CASL as the L0–L8 policy/decision engine in the existing W08 Worker | Avoids building a bespoke policy evaluator |
| CMS and content authoring | W01 Payload boundary; W03 remains content business authority | Reuse Payload and supported plugins/extension points; no Payload Core changes | Avoids building a second CMS and custom admin platform |
| Traffic analytics | W11 + configured Umami analytics target | Use Umami for aggregate web traffic/page analytics; use LuckRead-authoritative records for business metrics | Avoids building a custom page analytics collector/dashboard |
| Media upload UX | Existing content/media boundary | Evaluate Uppy only for upload UI/progress/retry where compatible with the existing storage contract | Avoids writing upload interaction primitives; does not assume resumable server support |
| Observability | Existing Cloudflare observability first | Reuse current logs/metrics; evaluate OpenTelemetry only for a specific tracing gap | Avoids adding a new monitoring stack before a demonstrated need |

**Important authority alignment gate:** the current canonical Worker documents still describe W02 as the identity/account/authorization authority and W08 as creator/organization. The new W08-CASL direction must be reconciled through the existing approved change-control/mapping process before authorization work is declared complete. This planning document does not silently override those contracts. W02 remains the account, credential, session, and account-state boundary; CASL policy evaluation is placed in W08 per the current implementation decision.

## 2. Status: reuse completed evidence instead of repeating work

The following work should not be reimplemented just for the new roadmap when its admitted evidence still matches the deployed/current source:

- Registration and verification email delivery, login persistence across refresh/navigation, and explicit logout behavior: reuse the already reported acceptance results; re-open only if the current source or deployment changes.
- Public content-list caching/invalidation and like aggregate cache behavior: reuse the successful checks already reported by the owner; do not reopen as fresh implementation tasks.
- Existing public cache safeguards (authenticated/private requests bypassing shared cache, bounded list cache, request-specific IDs): preserve and regression-test only when affected files change.

Open/pending implementation work is not counted as production-complete merely because code or a PR exists. The authorization path, CASL integration, and Umami runtime collection require their own merge/CI/deployment or real-runtime gates.

## 3. Delivery waves

### Wave 0 — Baseline and authorization contract alignment (first gate)

1. Review the L1–L4 creator-qualification work and its CI/runtime prerequisites.
2. Close the W02-account versus W08-permission authority conflict in the approved mapping/contracts. Do not change Better Auth internals or Payload Core.
3. Review the W08 CASL core for server-derived layer/account state, roles, scope, entitlement, resource ownership, fail-closed behavior, and caller authentication.
4. Merge/deploy only after the required CI gates pass, then verify a real account path rather than test-only role insertion.

**Exit checks:** canonical ownership docs and code agree; L1→L2→L3 and scoped L4 flows have positive and negative tests; a client cannot self-assign layer/role/scope; private endpoints deny unauthorized users; production behavior is checked on the intended source SHA.

### Wave 1 — Creator operating basics

- Complete creator profile/qualification, dashboard entry, ownership, and creator content list/actions using the existing W08/W03 contracts.
- Keep public profile identifiers stable and avoid leaking private account fields.
- Reuse existing UI/components where possible; do not build a parallel identity or authorization system in the Creator Center.

**Exit checks:** a normal user can reach the creator application path; approved creators can create/manage only their own content; revoked/suspended users lose protected capabilities according to the current contract.

### Wave 2 — Content/article/dynamic lifecycle and public API

- Close the user-visible vertical slice: draft, edit/autosave, revision/preview, review/preflight, publish/scheduled publish, update, unpublish, archive/restore, ownership and public detail/list.
- Ensure article and dynamic/post flows use the same admitted content API/error/cursor/cache conventions.
- Preserve W03 as content business authority. W01 remains the public API/CMS boundary and must not become a second content source of truth.
- Reuse Payload's supported extension points and evaluate only the plugins that fill a verified gap (first candidate: SEO metadata/structured-data support). No package is added without Cloudflare/Payload 3 compatibility checks.

**Exit checks:** each lifecycle transition has a test and authorization check; public list/detail reflect publish/unpublish changes within the agreed cache window; drafts/private content never leak through public cache; the real H5 flows work end to end.

### Wave 3 — Unified social layer

- Finish one consistent social contract across articles, dynamics, and short videos: follow/follower, like/unlike, comments/replies, bookmarks/favorites, shares, @mentions, hashtags/topics, notification preferences and inbox.
- Reuse existing like/follow/comment APIs and accepted cache evidence; focus only on missing cross-content consistency, replay/idempotency, negative authorization cases, and notification delivery.
- Keep W05 as social authority; moderation decisions remain W06-owned.

**Exit checks:** repeat requests are safe; counts and viewer-specific state agree after mutations; mentions point to stable user IDs; disabled/blocked or unauthorized interactions behave consistently; no extra D1 write is introduced on public reads.

### Wave 4 — Subscription, entitlement, and creator monetization minimum

- Deliver only the contracted baseline: subscribe/unsubscribe or membership lifecycle, access entitlement, paywall checks, subscription status, and creator summary based on authoritative records.
- W07 owns commerce/payment facts; account/access entitlement continues through its canonical authority and admitted cross-domain contract.
- Do not count client analytics events as purchase, entitlement, revenue, or payout evidence. Defer an advertising platform, marketplace, MCN settlement, and advanced billing features.

**Exit checks:** entitlement is checked server-side on each protected content path; failed/duplicate callbacks do not double-apply effects; subscription cancellation/revocation updates access; creator financial summaries match authoritative records.

### Wave 5 — Short-video MVP and media upload

- Implement the agreed simple short-video flow: upload, processing/ready/failure state, metadata editing, cover/poster, public detail/playback, and prefetch of the next and next-next item where practical.
- Evaluate Uppy for client upload UX only after confirming the existing storage endpoint, constraints, and allowed bindings. Do not assume a resumable-upload server exists just because the UI library supports it.
- Keep media bytes out of D1. Use only currently admitted storage and worker bindings; no new infrastructure.
- Do not expand into a recommendation engine, video/audio editor, long video, livestream, or podcast stack for 1.1.

**Exit checks:** upload and failure recovery work on supported devices; media processing status is truthful; unauthorized or unpublished video is not served; playback telemetry is best-effort and never blocks playback.

### Wave 6 — Analytics and SEO/distribution

**Umami (W11 web traffic):**
1. Inspect current page entry points, CSP/security headers, privacy/consent behavior, and existing deployment configuration.
2. Add the Umami client behind environment configuration, off by default when configuration is missing.
3. Allowlist page/event names and non-sensitive properties only; never send emails, credentials, auth tokens, raw private content, or arbitrary request payloads.
4. Verify that analytics outage/configuration errors cannot block login, reading, publishing, or social actions.
5. Mark production collection complete only after a real event appears in the configured Umami dashboard.

**Native LuckRead business analytics (W11):**
- Derive views/watch milestones, social engagement, creator growth and subscription summaries from server-validated domain records.
- Reuse the existing W10 async path and current D1-03 operational/analytics boundary only where already contracted. Avoid a browser-to-D1 write per interaction and avoid creating another authoritative copy of domain facts.

**SEO/distribution (W01/W03 boundary):**
- Close canonical URLs/slugs, sitemap/robots, OpenGraph, JSON-LD/schema.org, article/video/author metadata and redirect behavior.
- Reuse supported Payload features/plugins when compatible rather than replacing CMS behavior.

**Exit checks:** Umami is measured separately from native business truth; data collection is privacy-safe and non-blocking; key SEO routes render expected metadata and the sitemap contains only permitted published content.

### Wave 7 — Governance, performance, and release evidence

- Close the minimum 1.1 safety paths: report/block/mute, comment/content moderation boundary, rights/report evidence where in the locked scope, and appeal/status messaging.
- Re-run only tests affected by changed source. Reuse already accepted cache/API evidence when the source SHA and deployment provenance still match.
- Run integrated account→creator→content→social→subscription→analytics journeys, including cross-account negative cases and failure/retry behavior.
- Reconcile the release against current source SHA, deployed Worker version, API contracts, mapping and runtime evidence.

**Exit checks:** no known P0 security/business-flow blocker; no contract/implementation ownership mismatch; CI passes; required live runtime evidence is attached to the exact deployed source; 1.1 is not called GREEN merely because code exists.

## 4. Explicitly deferred to keep 1.1 small

- Full feed/recommendation engine and advanced search.
- Livestream, long video, podcast/audio platform, and media editing suite.
- PostHog-style cohorts, session replay, experimentation and advanced retention.
- New analytics infrastructure, a new database/queue/Worker, or a second CMS/account system.
- AI writing/rewrite assistants and large editor-plugin expansion until core authoring/publishing and the content/social API flows are closed.

## 5. Working method

- One issue at a time: implement → focused tests/CI → review → merge/deploy when authorized → runtime evidence → mark complete; then stop for the next instruction.
- Small, verifiable slices are preferred to parallel feature expansion.
- Existing accepted evidence is reused unless code, contracts, runtime configuration, or deployed source changes invalidate it.
- Any change to Worker/D1 ownership or external bindings requires the existing change-control path before implementation.
