## 3. 总体目标

完成全仓库剩余 D1 运行时依赖清理，使**已经迁移至 Neon 的业务模块彻底 Neon-only**，同时准确识别尚未迁移、仍需保留的 D1 依赖。

目标不是删除所有包含 `D1` 字样的文件，而是消除已迁移业务路径中的：
- D1 Adapter、Executor、Repository、Store；
- D1/PostgreSQL 双 dialect 或双实现；
- 自动识别数据库类型的 Resolver；
- Neon Store 缺失时回退到 `env.DB` 的逻辑；
- 仅为旧 D1 运行路径保留的依赖注入和兼容代码；
- 已迁移模块中仍然真实执行的 D1 查询与写入。

Neon Store 必须通过明确依赖注入。已迁移模块缺少 Store 时应 fail closed，返回明确的服务不可用错误（例如 503），不能自动回退 D1。写操作必须在业务写入之前完成依赖检查，避免部分写入后才报错。

## 4. 先审计，再并行清理

第一步必须检查：
1. 当前 main HEAD。
2. 所有开放 PR、分支、review、CI 和 changed files。
3. 各 Worker 的数据库依赖和跨 Worker 调用关系。
4. `wrangler.toml`、`wrangler.jsonc`、环境绑定、构建配置及部署脚本中的数据库引用。
5. 所有 D1 Adapter、`D1Database`、`env.DB`、`prepare()`、`batch()`、`exec()`、Resolver、fallback。
6. 测试、Fixture、Mock 中的 D1 使用，区分测试替身与生产执行路径。
7. 数据库文档、迁移记录、Schema、历史 Migration 和清理登记表。

输出并维护清单：`docs/database/LEGACY-D1-REMAINING-INVENTORY.md`。

每条记录至少包含：
- Worker 和业务模块；
- 文件路径、符号名和调用入口；
- D1 依赖类型；
- Neon 实现是否完整；
- 上下游调用及数据所有权；
- 分类、风险和建议处理顺序；
- 对应 PR、测试和最终状态。

### 分类规则

- **A — 可直接清理：** Neon Store 已完整实现，生产调用已具备切换条件，D1 只是遗留兼容路径。
- **B — 需补齐后清理：** Neon 只完成部分读写或部分入口，必须先补齐 Neon 实现和测试。
- **C — 暂时保留：** 尚未迁移，或真实业务仍依赖 D1。不得强行删除。
- **D — 历史/基础设施资料：** 历史 Migration、Schema 来源、数据迁移证据、回滚记录、审计文档及仍有效的基础设施标识。原则上保留。

不要将“名称中包含 D1”直接当作删除依据。尤其注意：某些名称带 D1 的 Hyperdrive 绑定可能实际连接 Neon；必须检查真实配置和运行路径后再判断。

## 5. 并行执行规则

为了加速，可以由不同工程师并行处理**互不重叠的 Worker 或功能切片**，但必须遵守：

- 每个切片指定唯一负责人。
- 开工前检查 main HEAD、开放 PR 和 changed files。
- 不得多人同时修改同一组 Runtime、公共 Store 或依赖注入文件。
- 不得覆盖其他工程师未合并的分支。
- 共享模块由单一负责人处理；下游切片等待其接口稳定。
- 若 PR #1908 或其他开放 PR 涉及目标文件，先隔离范围并协调。
- 每个切片单独分支、单独 PR、单独 CI 验证。
- 不要为追求并行而引入重复 Store、重复数据库连接或新的 Worker/Neon 资源。

优先从 A 类、风险低、Neon 实现完整、与开放 PR 不冲突的切片开始；B 类先补齐再清理；C/D 类不得误删。

## 6. 必须保护的业务与架构契约

任何清理不得破坏：
- 用户身份、认证、授权和账户隔离；
- 个人与组织/企业的数据所有权；
- 内容状态权威校验；
- 社交关系、关注、评论、点赞、收藏和通知；
- 幂等、事务边界、并发行为；
- 分页、排序、游标和缓存语义；
- Worker 间 API、事件、状态机和数据契约；
- 安全校验、审计记录和访问控制；
- 现有 API 请求/响应结构及客户端兼容性。

不得绕过业务权限检查来简化数据库调用。不得把原本由某个 Worker 拥有的数据改由其他 Worker 直接读写。不得因移除 D1 而改变业务数据的权威来源。

## 7. 上游开源系统保护

如果涉及 Payload 或其他上游开源系统：
- 优先在 LuckRead 自有 Adapter、Runtime、Repository 和依赖注入层清理。
- 不得随意修改或删除上游核心源码。
- 不得破坏上游系统数据库抽象、迁移机制或升级路径。
- 不得通过修改 vendor/第三方源码来隐藏 D1 依赖。
- 如确实发现上游核心存在必要的 D1 依赖，先单独提交审计报告，说明版本、文件、原因、升级影响和可行替代方案；未经批准不得修改。

## 8. 明确禁止的操作

本任务仅涉及代码、测试和文档。严禁：
- 删除或清空生产 D1 数据库；
- 删除 Neon 数据库、分支、表或数据；
- 修改生产 Schema 或执行生产数据迁移；
- 删除历史 Migration、Schema 来源或回滚证据；
- 修改生产 Worker 流量或执行生产部署；
- 删除 Cloudflare 资源、绑定或密钥；
- 擅自改变数据库迁移方案；
- 修改与本任务无关的项目或 PR。

如发现某个 D1 绑定可能仍在生产使用，先记录并报告，不得删除。

## 9. 单个 PR 的交付与验收

每个 PR 必须是一个边界清晰的功能切片，并满足：

- [ ] 删除的是已确认可移除的生产 D1 路径，而非仅删除字符串或文件名。
- [ ] 该模块生产读写统一使用明确注入的 Neon Store。
- [ ] 已移除该模块的 D1 fallback、双路 Resolver 和旧 Adapter（若属于本切片）。
- [ ] Neon Store 缺失时 fail closed。
- [ ] 业务写入前完成依赖检查。
- [ ] 权限、所有权、幂等、分页、排序、事务等语义保持不变。
- [ ] 单元测试、集成测试和相关契约测试通过。
- [ ] Worker 类型检查与构建通过。
- [ ] 适用的 PostgreSQL Schema Rehearsal、Security Gate、Contract Gate 通过。
- [ ] README 和 `docs/database/LEGACY-D1-CLEANUP-REGISTER.md` 已更新。
- [ ] 没有无关改动，没有与其他 PR 冲突。
- [ ] CI 全部结束且没有失败项；review 中没有未解决的阻塞意见。

CI 未完成、存在失败项或存在未解决阻塞 review 时，不得合并。不得以“mergeable=true”代替 CI 验收。
