# LuckRead GPT 防无效循环开发执行补充契约 v1.0

**Status:** ACTIVE — REQUIRED OPERATIONAL ADDENDUM  
**Date:** 2026-11-08  
**Applies to:** `wanghuinet/luckread` 的 GPT 辅助需求分析、代码实现、修复、测试、PR 与合并协助  
**Parent contract:** `docs/GPT-AUTONOMOUS-DEVELOPMENT-AND-SOFTWARE-QUALITY-GOVERNANCE-CONTRACT-v2.0.md`  
**Related standard:** `docs/DEVELOPMENT-EXECUTION-STANDARD-LUCKREAD-1.0-v1.0.md`

> 本补充契约只约束 GPT 如何恢复任务、推进开发、判断进展和停止重复尝试。它不建立第二套产品/架构/数据权威，不改变任何 Worker、D1、Queue、Service Binding、Payload、API、权限或发布边界。与现有 Blueprint、Contract、L5/L6、Evidence、Change Control、CI/Admission 规则冲突时，以现有权威规则为准，并停止冲突部分。

---

## 1. 核心目标

每轮工作必须产生可核验的工程进展，或尽早给出有证据的阻塞结论。不得用重复检查、重复描述、状态文字更新或没有新证据的重试制造“正在推进”的假象。

**唯一目标：完成当前最小可验收 Slice，然后停止。** 不以代码行数、PR 数量、测试数量或对话轮数衡量进度。

## 2. 开始工作前必须恢复仓库事实

每次新会话、用户说“继续”、准备开发或准备合并前，必须从 GitHub 当前状态恢复：

1. 仓库必须是 `wanghuinet/luckread`，核对默认分支和最新 `main` SHA。
2. 检查相关开放 PR、分支、实际 Diff、Review 线程和必要 CI/Workflow。
3. 定位当前唯一活动的 Stage / 模块 / Slice，以及最后一次有效交接。
4. 复核该 Slice 的合同、测试和 Evidence 是否仍绑定当前实现 SHA。
5. 检查是否已有合并实现或有效证据；不得因为对话上下文变化而重做。

仓库事实优先于聊天记录、历史摘要和 GPT 自身推断。任何旧的“已完成”“已通过”结论都必须在当前 SHA 上重新确认其有效性。

## 3. 单一活动工作面与切片大小

- 任一时刻只允许一个**主要活动模块 / Slice**。只允许为完成该 Slice 而修改合同明确要求的必要依赖模块。
- 每个 Slice 必须有明确目标、修改边界、不做事项、验收条件、测试和 Evidence 计划。
- 预计需要超过约 60 分钟的工作，必须拆成可独立审查、测试、提交和交接的小 Slice；不得把大量开发塞进一个长回合。
- 不把多个互不相关模块合并到一个 Slice 或 PR。发现相邻问题时登记为独立待办，除非它是当前正确性或安全阻塞。
- 当前 Slice 达到其验收条件后立即停止，不自动进入下一模块；用户明确说“继续”后才恢复下一 Slice。

## 4. GPT 执行状态与冻结规则

以下是 GPT 的**执行跟踪状态**，只用于标记当前工作，不替代项目既有状态机或 GREEN 准入：

| 执行状态 | 含义 | 允许的动作 |
|---|---|---|
| `NOT_STARTED` | 尚未开始当前 Slice | 先恢复仓库事实、明确范围 |
| `IN_PROGRESS` | 当前唯一活动 Slice 正在实施 | 只推进该 Slice |
| `ACCEPTED` | 当前 Slice 的验收条件和证据已记录 | 冻结，不再重复开发 |
| `BLOCKED` | 存在已证实且尚未解除的阻塞 | 停止实现，报告解除条件 |
| `DEFERRED` | 用户明确批准推迟 | 不自行恢复或扩大范围 |

`ACCEPTED` 仅表示该 Slice 按约定验收并冻结；只有适用的项目准入流程全部满足，才能将项目状态称为 `GREEN`。

### 4.1 已验收模块不得自行重开

进入 `ACCEPTED` 后，除以下情况外不得重新开发或反复审查：

1. 有可复现的缺陷、回归或安全问题；
2. 上游合同、批准需求或架构约束发生了明确变化；
3. 已有验收证据因代码、依赖、配置或目标环境变化而失效；
4. 用户明确授权重新打开，并给出新的目标范围。

重开必须先记录：触发原因、复现步骤或新证据、受影响 SHA、重开范围和新的验收条件，然后创建一个新的 Slice。不得仅因“想再优化一下”、上下文遗忘、代码风格偏好或重复扫描而重开。

## 5. 什么才算有效进展

每轮结束时至少产生以下一项新的、可验证结果：

- 有意义的生产代码 / 配置变更，并有对应测试；
- 新增或修复的测试，能够覆盖此前未覆盖的行为或失败路径；
- 新的 CI、集成、运行或设备验证结果，且明确绑定 SHA 和环境；
- 新的根因证据、明确的技术决策或经确认的阻塞条件；
- 已完成的 PR 审查、合并或部署事实，并有链接和 SHA。

以下内容**单独不算工程进展**：

- 只修改状态、进度百分比、文档措辞或 PR 描述；
- 只增加测试数量，却没有增加有效行为覆盖；
- 重复读取相同文件、重复搜索相同问题或重复运行同一成功检查；
- 没有新证据的“继续排查”“再次确认”；
- 把本地代码存在、文档更新、单测通过或 PR 合并描述为端到端功能完成。

文档变更只有在文档本身就是用户授权的交付目标，或为当前实现提供必需的权威/审计证据时，才算本轮交付。

## 6. 无进展止损规则

每次尝试开始前，明确写出：**当前事实 / 假设、准备采取的动作、预期新增证据或代码差异**。

出现下列任一情况，必须停止当前重复路径：

1. 相同根因或相同失败步骤连续两轮没有新增代码差异、新证据、环境变化或诊断信息；
2. 两轮连续工作没有产生任何可验证进展，也没有形成新的、明确的阻塞结论；
3. 需要的凭证、权限、用户决策或环境条件不存在，且本轮不能通过安全、获准的方式补齐；
4. 继续尝试会重复已知结果、扩大风险或绕过现有门禁。

停止后将当前 Slice 标记为 `BLOCKED`（或按用户批准标记 `DEFERRED`），说明：

- 已确认的事实与证据链接；
- 已尝试的动作及其结果；
- 为什么重复尝试不会带来新信息；
- 最小解除条件；
- 下一项**不同且可验证**的动作。

**禁止**在没有说明变化的情况下重复同一命令、同一补丁、同一测试或同一搜索。再次尝试前必须指出新增了什么信息、代码、权限或环境条件，以及为什么这次尝试能够产生不同结果。

## 7. 故障修复不得原地打转

缺陷处理必须形成闭环：

`复现 → 根因证据 → 回归测试 → 最小修复 → 受影响范围验证 → Evidence`

若无法复现，标记 `UNREPRODUCED`，不得把假设写成根因。若同一修复再次失败，必须检查测试层级、实际调用路径、多个状态来源和适配边界；不得只重复微调同一处代码。

## 8. Slice 验收与交接记录

每个 Slice 完成或阻塞时，必须输出并在适用的 PR / Evidence 中记录：

| 字段 | 必须记录的内容 |
|---|---|
| Repository | `wanghuinet/luckread` |
| Base SHA | 开始实施时的精确 `main` SHA |
| Module / Slice | 唯一主要活动模块和 Slice 标识 |
| Status | 上述 GPT 执行状态及项目真实状态 |
| Changed files | 实际变更路径与变更摘要 |
| Tests | 命令、结果、未执行项和原因 |
| CI / Review | Workflow / Job / Review 链接及 PASS、FAIL、SKIPPED、NOT RUN、UNKNOWN |
| Evidence | 证据链接、环境、执行时间和绑定 SHA |
| Blockers | 未解决问题、风险和解除条件 |
| Next action | 唯一最小下一步，不列泛化大清单 |

缺失的证据必须明确标注 `NOT RUN`、`UNKNOWN` 或 `NOT APPLICABLE`，不得推定为成功。

## 9. 用户指令解释

- **“继续”**：恢复当前唯一活动 Slice，从交接记录中的下一项最小动作继续；不重做已验收模块，不扩大范围。
- **“合并”**：只审查用户明确指定或当前任务关联的 PR；重新检查 Diff、Review、未解决线程和必要 CI。满足现有规则后才合并。
- **“合并 PR 后继续”**：按既有总契约完成 PR 审查和合并，合并后重新读取最新 `main` SHA，再恢复下一 Slice。
- **“跳过 / 暂缓”**：只作用于用户明确指定的模块或门禁；记录范围和影响，不得推广成通用豁免。

任何远程 DDL、破坏性数据操作、生产流量切换、凭证变更或其他高影响操作，仍须遵守其专属合同、环境批准和用户授权；本补充契约不提供额外授权。

## 10. 强制停止条件

当前 Slice 达到验收条件、明确阻塞、触发无进展止损规则或超出已批准边界时，立即停止。只报告真实结果、精确 SHA、证据和下一项最小动作。不得为了“保持活跃”自动寻找无关任务。

---

**执行底线：一个活动 Slice；每轮有新证据或真实变更；连续两轮无新进展即止损；验收后冻结；用户明确继续后再进入下一 Slice。**
