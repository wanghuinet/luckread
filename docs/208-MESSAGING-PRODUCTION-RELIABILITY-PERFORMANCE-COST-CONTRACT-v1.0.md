# LuckRead 私信系统生产级可靠性、性能与成本契约 v1.0

**状态：USER-REQUESTED / AUTHORITATIVE ADDENDUM / IMPLEMENTATION AND EVIDENCE PENDING**  
**适用范围：LuckRead React Native CLI App、W01、W05、Cloudflare Workers、Durable Objects、Neon PostgreSQL、R2，以及后续被明确批准的配套组件。**  
**优先级：本契约是私信系统后续实现、审查、测试和验收的最高产品/工程要求。与旧文档中 D1 作为消息权威存储、尚未纳入的实时能力或早期阶段边界冲突时，以当前实际迁移状态和本契约为准；不得据此恢复 D1。**

## 1. 产品目标与不可妥协原则

LuckRead 私信必须达到成熟全球社交产品的生产级可靠性、低延迟体验、跨设备一致性、隐私安全和可持续成本。

目标不是通过牺牲可靠性换取账单下降，也不是通过增加基础设施制造虚假的性能提升。

1. 正式消息必须可靠持久化、可恢复、可去重，并具备会话内确定顺序。
2. 临时实时状态不得依赖 Neon 持久化；不得让 Typing、心跳、在线状态、临时光标等高频事件制造无价值数据库写入。
3. 在线实时传输与消息持久化必须分离。WebSocket/DO 负责实时连接与事件分发，Neon 是正式消息及会话业务数据的权威持久化层。
4. 客户端优先本地响应和本地缓存，网络负责同步，不得把每次页面展示都变成完整历史拉取。
5. 以真实压测、CI、运行指标和故障演练证明性能与成本，不得宣称未经验证的“10 倍性能”或“零账单”。
6. 不因追求低成本引入不可靠的手机直连 P2P 作为消息唯一通道，不以 DO 内存、Worker 内存或客户端本地数据代替正式消息持久化。

## 2. 固定技术边界与 TS7 说明

当前优先技术栈：
- App：React Native CLI、TypeScript、客户端持久化缓存。
- API/业务：现有 W01 身份与 API 边界、W05 Social/Messaging 业务实现。
- 实时：Cloudflare Workers + Durable Objects + WebSocket。
- 权威数据：Neon PostgreSQL；沿用现有 Neon/Hyperdrive/连接执行器配置，先测量再调整。
- 媒体：R2 存放二进制对象，Neon 仅存必要元数据、授权和关联。
- 离线通知：现有/批准的 APNs、FCM 适配边界；不得用常驻轮询代替推送。

**TypeScript 7（Go 实现的编译器）不是 Go 运行时。** TS7 的 Go 原生编译器可改善编译、类型检查和开发迭代效率，但不会自动把 Worker 业务代码变成 Go，也不能据此推断线上请求性能提高。运行时性能必须通过代码路径、数据库往返、序列化、连接生命周期、DO 计费维度和端到端压测优化。

除非真实压测证明现有 Cloudflare 架构无法满足目标并完成成本比较，不新增常驻 Go 服务、Redis、NATS、Centrifugo 或第二套消息基础设施。不得为追求“技术先进”重复建设已有 DO/Workers 能力。

## 3. 权威数据与职责边界

| 数据/能力 | 权威位置 | 约束 |
|---|---|---|
| 正式消息、编辑/撤回状态 | Neon | 提交成功前不得向发送端确认持久化成功 |
| 会话、成员、角色、Block/隐私授权 | Neon/既有领域权威 | 每个读写操作均执行服务端授权 |
| 会话内消息 sequence | Neon 事务 | 单会话严格递增；并发测试验证 |
| 幂等键及去重结果 | Neon | 重试不得产生重复正式消息 |
| 成员已读游标 | Neon | 单调递增；按会话/成员游标合并写入 |
| Typing、短期 presence、连接心跳 | DO/连接层 | 不写 Neon；短 TTL；无无意义后台刷新 |
| 实时连接和在线设备 | DO | 不作为消息持久化权威；支持断线恢复 |
| 图片/视频/文件原件 | R2 | 不将二进制存入 Neon |
| 附件元数据、所有权和访问权限 | Neon | 下载/预览前校验会话成员和资源权限 |
| 本地消息缓存 | App 本地数据库 | 可重建、可同步，不作为跨设备权威 |
| 推送投递状态/异步工作 | 既有队列/投递边界 | 幂等、可重试、失败可观察；不重复创建基础设施 |

Neon 与 DO 不得形成双主权威。DO 丢失内存、休眠、重启或连接迁移，不得造成正式消息丢失。

## 4. 连接与实时事件契约

### 4.1 连接模型
- 每个 App 设备优先维持一条经过认证的 WebSocket 连接；一条连接复用用户收件箱和当前会话订阅，不为每个会话单独建连接。
- 连接建立时由服务端验证身份、设备会话和订阅权限；客户端不能自行声明可信 userId 或任意加入 conversation。
- 连接必须有明确的认证过期、撤销、重连退避、网络切换、前后台切换和服务端关闭处理。
- App 进入后台时不得假定 iOS/Android 会永久维持 WebSocket；接受系统挂起/断连，离线通知通过 APNs/FCM，回前台后增量同步。
- 心跳必须足够稀疏且有明确必要性；优先使用平台/协议可用的 ping/pong 与连接存活机制。禁止固定高频定时器持续唤醒 DO。
- 多设备登录、单设备退出、账号退出、封禁和凭证撤销必须能及时终止对应连接或使其失效。

### 4.2 Durable Objects
- 必须评估并在兼容现有协议、连接恢复与授权语义后采用 WebSocket Hibernation API；不得仅为追求休眠而破坏连接状态、事件监听、身份绑定或恢复能力。
- 采用 Hibernation 时，使用平台支持的 WebSocket attachment/恢复模式；不得依赖只存在于 DO 内存的 socket Map 作为休眠后唯一连接索引。
- 对当前 DO 的普通 accept、内存 Map、消息监听、Alarm、定时心跳和存储读写逐项审计；输出实测前后成本/连接行为，不允许只改 API 名称便宣称完成 Hibernation。
- Alarm 只用于必要的短 TTL 清理；没有待清理状态时取消 Alarm；禁止无任务时周期性唤醒。
- DO 只处理实时协调、订阅、广播和短期状态；禁止每个 WebSocket 帧都查询 Neon。
- 广播应有大小限制、速率限制、批量/合并策略和慢消费者保护；单个失效 socket 不得拖垮同房间其他连接。
- DO/Worker 内部广播入口必须有可信服务身份校验，不能只依赖可伪造的客户端 header；严格校验事件类型、actor、conversation 和 payload。

### 4.3 事件分类
**临时事件（不写 Neon）：** typing、短期在线状态、心跳、连接状态、临时光标/输入进度及不要求历史恢复的轻量互动。使用短 TTL、合并/节流和状态变化广播。

**持久事件（先持久化再确认）：** message.created、message.edited、message.recalled、membership/role/ownership changes、read cursor 等影响业务事实的事件。必须先完成 Neon 权威变更，再广播。广播失败不能回滚已提交消息；客户端必须通过增量同步恢复。

不得把“WebSocket 已发出”当作“消息已保存”或“对方已收到”。区分 accepted/persisted、delivered、read 等状态语义。

## 5. 正式消息写入、顺序与可靠性

- 消息发送必须具备客户端生成的稳定幂等键；相同用户/会话/幂等键重试返回同一结果，不产生重复消息。
- 服务端必须在单个事务内完成必要的权限检查、会话序号分配、消息写入和相关权威状态更新；序号并发安全，严禁依赖客户端时间排序。
- 单会话 sequence 严格递增；跨会话不承诺全局顺序。
- 消息成功响应必须在数据库事务提交后返回。客户端可先做 optimistic UI，但状态必须明确显示 sending，只有收到持久化确认后才显示 sent。
- 网络超时、应用崩溃、重复提交、数据库冲突和重试必须可恢复；客户端使用同一幂等键重试，禁止自动生成新键造成重复消息。
- 消息持久化和实时广播必须解耦。广播失败不得让已提交消息显示发送失败并再次创建；使用事件 ID、sequence 和增量同步消除重复。
- 对广播与离线通知的一致性，评估事务 Outbox/队列或可重放事件机制。是否引入 Outbox 必须基于可靠性需求、额外写放大和实际故障窗口做决策；不得无证据增加双写，也不得声称 best-effort 广播具有可靠投递保证。
- 消息编辑/撤回必须校验作者、时间/策略、成员状态和权限；客户端处理乱序事件时以权威版本/sequence 收敛。
- 消息删除、保留期限、合规导出和用户数据删除必须有明确策略，不能留下孤立附件或隐私泄露。

## 6. 读取、已读与同步成本

- 历史消息必须使用基于 sequence 的有界游标分页；禁止无界 offset 和无界全量拉取。
- 首屏优先读取本地数据库并快速渲染；后台增量请求只拉取缺失范围。
- 客户端持久化 lastSyncedSequence/每会话游标；重连、重装、跨设备和分页边界必须可校验和修复。
- WebSocket 事件是低延迟提示，不是唯一数据源；事件丢失、重复或乱序后必须通过 afterSequence 增量同步收敛。
- 已读使用每成员每会话单调递增 read cursor；把连续阅读合并成较少写入，禁止逐条消息更新 read receipt。
- unread count 应可由权威游标和消息序列重建/校验，缓存只是派生值；不得每次列表展示执行 N+1 查询。
- 会话列表应通过有界查询批量取回最后消息摘要、未读派生值和成员摘要；避免每个会话额外查询。
- 缓存失效和实时事件必须明确；不允许通过缩短 staleTime、频繁轮询掩盖同步 bug。
- 断线重连采用指数退避、随机抖动、前后台感知和网络状态感知；恢复时合并请求，避免惊群。

## 7. 数据库与 Worker 成本控制

- Neon 只承担不可替代的正式持久化与必要查询；typing/presence/heartbeat/临时广播不得写 Neon。
- 复用现有 Neon/Hyperdrive 连接配置；测量每请求连接获取、事务耗时、查询数、锁等待和连接池饱和后再调优。禁止每条消息新建未复用的数据库连接，也禁止在 Worker 全局保存不安全/不可复用的事务连接。
- 事务必须短小；禁止事务期间等待 WebSocket 广播、推送、R2 上传或外部网络。
- SQL 必须参数化；索引以实际查询计划和读写放大为依据，不得无差别增加索引。
- 消息历史按会话和 sequence 走索引；会话列表查询避免 N+1；热点会话和大群必须单独压测。
- 附件二进制直传 R2，消息只保存对象 key、尺寸、mime、hash、扫描状态等必要元数据；访问使用短时授权/受控下载。
- 对读多写少的稳定摘要可以使用客户端缓存或经论证的边缘缓存；私人消息不得被公共缓存，缓存 key 必须包含授权边界。
- 不以“减少 Neon 写入”为由把正式消息只存 DO/R2/内存；不以批量写入破坏发送确认、顺序或幂等语义。
- Worker 调用应合并重复的内部 RPC/授权读取；不要把同一个用户/会话/权限上下文在一次请求内重复查询。
- Queue、KV、Redis、NATS、第二数据库等新增依赖必须先给出当前方案的测量瓶颈、预期成本差、故障模式、运维负担和退出方案，经契约审查后再引入。

## 8. App 体验契约

- 发消息立即显示本地 optimistic bubble，明确区分发送中、已发送、失败、重试；不允许点击后无反馈。
- 发送按钮防重复提交；失败重试沿用幂等键。
- 新消息到达时保持滚动体验：用户在底部则跟随，浏览历史时不强制跳底；提供新消息提示。
- 列表和会话切换优先本地缓存；加载状态稳定，不闪屏、不重复插入、不突然改变顺序。
- 图片/视频/附件先展示上传/处理状态；失败可重试；权限失效和资源删除有明确 UI。
- 已读、送达、编辑、撤回、群成员变更在所有设备最终一致。
- 处理弱网、离线、网络切换、应用挂起/恢复、令牌过期、账号切换和多设备同时在线。
- 尊重系统无障碍、动态字体、减少动态效果、深色模式和多语言；不能用高频动画/重渲染拖慢长消息列表。
- 消息列表采用虚拟化/增量渲染；避免每个新事件导致整页无差别重渲染。

## 9. 安全、隐私与反滥用

- 所有 conversation/message/member/attachment 操作都在服务端验证当前主体的实时成员关系与权限。
- Block 必须一致地保护新建会话、会话列表/预览、历史读取、发送、已读、附件访问和实时订阅；双向 Block 规则一致。
- 群组成员移除/退出/转让所有权后，旧连接和旧订阅不能继续收到后续私密事件；广播时必须过滤当前有效成员，必要时撤销订阅。
- 内部 Worker→DO 请求必须使用可信 Service Binding/签名上下文；客户端不可伪造 actorUserId。
- 限流应按用户、设备、会话和操作类型分层；防止刷消息、Typing 洪泛、群广播滥用和附件滥用。
- 日志、Tracing、指标不得记录消息正文、附件私密 URL、访问令牌或不必要的个人信息。
- 管理员默认不得读取私人消息内容；敏感访问必须有明确授权、审计和最小权限。
- 错误响应不得泄露对方是否存在、隐私设置、封禁细节或未授权资源信息。

## 10. TS7 与运行时工程质量

- TS7 用于编译/类型检查/开发迭代效率；以仓库实际锁定版本和 CI 可用性为准，不擅自升级或假定所有工具链兼容。
- 对 Worker 热路径进行剖析：JSON parse/stringify、对象分配、重复校验、过大 payload、同步 CPU 工作、串行等待和不必要的 RPC。
- 事件协议应有版本、稳定类型和 payload 上限；仅在有证据时引入二进制/Protobuf，避免无意义协议复杂度。
- 采用严格类型和运行时输入校验；编译时类型不能替代不可信网络输入校验。
- 对性能优化保留可读性、可测试性和安全边界；禁止通过 any、跳过鉴权、关闭验证或吞异常制造虚假性能。

## 11. 可观测性与性能/成本验收

先建立当前基线，再设定目标；任何“提升 10 倍”“账单降低 100%”必须明确测试环境、负载、对照版本和计量口径。

每次压测至少记录：
- 在线 WebSocket 连接数、每设备连接数、连接建立/关闭速率、重连率。
- DO 请求数、入站/出站 WebSocket 消息数、Duration、唤醒次数、Alarm 次数、异常和慢消费者。
- Worker 请求数、内部 Service Binding/RPC 次数、CPU/执行耗时、错误率。
- Neon compute/活跃时间、查询数、事务数、连接获取/释放、查询延迟分位数、锁等待、存储/索引体积。
- 每条正式消息的 Worker 请求数、Neon 事务数/SQL 数、DO 广播次数、推送任务数。
- App 发送到持久化确认、发送到在线接收、首屏渲染、历史分页、重连补齐的 p50/p95/p99 延迟。
- 每万条正式消息的 Worker、DO、Neon、R2 与推送成本；按在线用户小时、连接小时和消息数分别归一化。

性能验收必须覆盖：
1. 单聊和群聊并发发送、同会话竞争 sequence。
2. 重复提交、超时重试、响应丢失、广播失败、DO 重启/休眠唤醒。
3. 网络断开、移动网络切换、App 前后台切换、多设备同时登录。
4. 大群广播、慢客户端、连接洪峰、重连惊群。
5. Block、移除成员、退群、转让群主后即时权限撤销。
6. 长历史分页、会话列表、未读游标、附件上传/下载。
7. Neon 短暂不可用、连接池耗尽、事务冲突和限流。

验收报告必须提供：环境与 commit SHA、数据规模、并发模型、测试时长、吞吐量、错误率、p50/p95/p99、资源消耗、每万消息成本、对照基线和未解决风险。没有证据不得标记性能/成本目标完成。

## 12. 质量门禁与阶段收口

每个完整阶段应一次性覆盖相关服务端、DO、App、迁移/SQL（如确有必要）、测试、指标和故障恢复，不得把一个完整能力拆成大量无意义的小 PR。

必须具备：
- W05 单元/集成测试、W01 路由与身份边界测试。
- Neon/PostgreSQL 真实事务测试、空库迁移演练、并发/幂等测试。
- DO WebSocket 连接、休眠/唤醒、断连恢复和授权测试。
- App 本地缓存、重试、增量同步、列表性能和多端一致性测试。
- TypeScript 类型检查、lint、构建、相关 CI 全绿。
- 对权限、Block、附件、隐私和滥用有负向测试。
- 监控指标和告警能发现连接洪峰、数据库饱和、广播失败和成本异常。

阶段完成必须有可核验的代码、测试和 CI 证据；PR 创建不等于功能完成；CI 未运行或失败不得标记通过；未上线不得声称生产验证完成。

## 13. PR、变更与执行纪律

- 只在 LuckRead 仓库内推进本契约，不混入 Globe 或其他项目。
- 用户偏好完整阶段推进，避免频繁暂停和碎片 PR。

## 14. 禁止事项（STOP）

以下任一情况均不得验收：
- 正式消息只存在于 Worker/DO/客户端内存。
- 把 WebSocket send 成功当作数据库提交或对端送达。
- 缺少幂等键、重复消息去重或会话 sequence 并发保护。
- 重连后无法按游标补齐缺失消息。
- Typing、心跳、在线状态高频写 Neon。
- 高频定时器持续唤醒 DO，或休眠实现依赖无法恢复的内存 Map。
- 未授权用户可订阅会话、获取消息、附件或群成员事件。
- Block/移除成员后仍能获取私密事件。
- 会话列表 N+1、无界历史查询或逐条已读写入造成明显放大。
- 用未验证的“TS7=Go 运行时”“性能十倍”“账单零成本”作为架构依据。
- 未测量就引入第二套常驻消息基础设施。
- CI、压测或故障恢复证据缺失却标记完成。

## 15. 当前执行顺序

1. **基线审计**：审查现有 W01/W05、DO、Neon executor/Hyperdrive、消息表/索引、App API/缓存/重连；特别核对当前 DO 是否真实使用 WebSocket Hibernation API，以及现有 typing 轮询/Alarm 是否造成唤醒。
2. **可靠性闭环**：补齐幂等、事务顺序、广播失败恢复、游标增量同步、成员权限即时撤销和多端一致性。
3. **成本闭环**：消除临时状态数据库写入、N+1、全量刷新、逐条 read 写入和无效 DO/Worker 唤醒；建立每万消息成本基线。
4. **体验闭环**：完善本地持久化、optimistic UI、弱网重试、前后台、多设备、长列表和媒体交互。
5. **压测与规模化**：逐步提高连接数、并发消息和群规模，按真实成本数据决定是否需要分区、归档、Queue 或其他基础设施。

**最终验收定义：** 正式消息可靠、私密和可恢复；在线体验流畅、跨设备一致；临时事件不依赖 Neon；Worker/DO/Neon 的调用与资源消耗可测量、可解释、可持续优化。成本目标是最低可持续成本，而非牺牲可靠性或承诺绝对零账单。

## 16. 与平台信息流及成本架构契约的关系

信息流读取、公共内容缓存、时间线分发、推荐排序、互动计数和媒体分发的跨模块规则，统一由以下配套契约定义：

- `docs/209-FEED-AND-PLATFORM-COST-ARCHITECTURE-CONTRACT-v1.0.md`

两份契约必须同时遵守，但数据权威边界不得混淆：

- 信息流帖子、关注关系和互动事实以其领域权威数据为准；Cache API、KV、DO 和客户端缓存均为派生层。
- 私信正式消息、会话成员、消息顺序、幂等记录和已读游标仍以本契约定义的 Neon 权威持久化为准。
- 私信内容不得进入公共信息流缓存；不得因复用 Feed 缓存组件而放宽私信授权边界。
- 两份契约共同要求客户端本地优先、游标增量同步、缓存可失效/可重建、计数可恢复、成本可测量。
- 任何跨模块共享缓存、DO 或 Queue 的设计，必须保留各自领域的数据权威、权限隔离、幂等和故障恢复语义。

不得将信息流契约中的批量聚合、短期缓存或最终一致性策略直接套用到正式私信消息写入；私信发送确认仍必须以 Neon 事务提交为依据。
