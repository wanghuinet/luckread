# LuckRead 1.0 Release Scope v1.0

> Status: **FROZEN SCOPE / IMPLEMENTATION TRACK**
>
> Purpose: define the minimum product scope for the first usable LuckRead 1.0 release without inventing new Feature IDs, replacing the functional Blueprint, or bypassing existing Contract/Evidence gates.
>
> Source of truth:
> - Functional scope: `docs/00-LUCKREAD-ULTIMATE-FEATURE-BLUEPRINT-v2.0.md`
> - Architecture: `docs/00-PROJECT-BLUEPRINT-v1.4.md`
> - Public API rules: existing canonical API/OpenAPI and domain Contracts
> - Completion proof: repository Evidence Registry and validating CI/runtime evidence

## 1. Release intent

LuckRead 1.0 is the first usable product release of the self-media platform. The release must provide one complete, reviewable user journey:

```text
Account
  ↓
Authenticated user
  ↓
Create content
  ↓
Publish content through the contracted lifecycle
  ↓
Public/authenticated content browse
  ↓
Video/content media where included
  ↓
Subscription/entitlement where included
  ↓
Operational administration
  ↓
Web/H5/APP client experience
```

The release is built by reusing verified platform capabilities first. A capability is not considered delivered merely because a Payload collection, CRUD route, UI mock, or unit test exists.

## 2. Frozen minimum scope

The 1.0 release train contains the following existing Feature IDs.

### 2.1 Account entry

Required:
- AUTH-001 registration
- AUTH-002 login/logout
- USER-001 profile
- USER-002 avatar/banner/bio/display name
- USER-003 locale/language/timezone

Release requirement:
- A user can create an account, authenticate, establish a session, and access their own profile.
- Existing AUTH contracts, state rules, anti-abuse controls and Evidence requirements remain authoritative.

### 2.2 Content creation and publishing

Required:
- CONTENT-001 draft
- CONTENT-007 publish/update/unpublish
- CONTENT-009 content ownership
- CONTENT-010 content lifecycle state machine
- CONTENT-012 content audit trail
- ARTICLE-001 article
- ARTICLE-002 rich text/block content
- ARTICLE-003 images/gallery
- ARTICLE-011 canonical/slug/version

Release requirement:
- A creator can create content, keep it private while drafting, publish it only through the contracted lifecycle, update/unpublish it subject to the contracted state rules, and retain server-authoritative ownership.
- Public content must be derived only from authoritative published state.

### 2.3 Content browse and discovery baseline

Required:
- API-001 canonical REST API
- API-002 OpenAPI
- API-003 API versioning
- API-004 pagination/cursor
- API-005 standard errors
- SEO-001 canonical URL
- SEO-002 stable slug

Release requirement:
- The same canonical API contract is used by Web/H5/APP clients.
- Public reads use bounded/cached read behavior defined by the relevant Contract.
- Private, draft, unpublished and deleted content must not leak into public results.

### 2.4 Basic media and video

Required:
- MEDIA-001 media asset
- MEDIA-002 upload/resumable upload
- MEDIA-004 video processing/transcoding
- MEDIA-005 short video
- MEDIA-009 thumbnail/poster/cover
- MEDIA-010 CDN/delivery metadata
- STORAGE-001 object storage abstraction
- STORAGE-002 R2 adapter
- STORAGE-004 upload validation

Release requirement:
- The product can accept valid media, associate media with content, and expose playable video through the contracted delivery path.
- Large media objects remain on object storage; authoritative content metadata and references remain on the defined metadata path.

### 2.5 Subscription and paid content

Required:
- MON-001 platform membership
- MON-003 subscription plans/tiers
- MON-005 renewal/cancel/pause/resume
- MON-006 entitlement
- MON-008 article partial paywall
- PAY-001 payment provider abstraction
- PAY-002 orders
- INT-003 payment provider

Release requirement:
- Paid access is decided through authoritative subscription/entitlement state.
- The article partial-paywall experience may expose the free portion without treating client UI state as an authorization boundary.
- Payment success is accepted only through the contracted provider/event boundary.

### 2.6 Administration

Required:
- ADMIN-001 admin console
- ADMIN-002 user management
- ADMIN-003 content management
- ADMIN-004 media management
- ADMIN-010 configuration center

Release requirement:
- Operators can manage the 1.0 user/content/media lifecycle through an auditable administrative surface.
- Administrative permissions and audit rules remain governed by existing security and authorization contracts.

### 2.7 Client delivery

Required:
- CLIENT-001 Web
- CLIENT-002 H5
- CLIENT-003 Android
- CLIENT-004 iOS

Release requirement:
- The canonical API remains the shared backend boundary.
- Client delivery is staged after the core API/content path is executable; client-specific behavior cannot silently redefine the backend contract.

## 3. Explicitly outside the minimum 1.0 scope

The following existing Blueprint capabilities remain outside the minimum 1.0 release unless a later Change Control promotes them:
- advanced creator/MCN workflows;
- passkey/WebAuthn and MFA extensions;
- OAuth/social-login expansion;
- full recommendation/ranking system;
- advanced search;
- live streaming;
- messaging/community systems;
- advertising campaign/settlement platform;
- advanced rights/DRM systems;
- developer/open-platform ecosystem;
- enterprise multi-tenant expansion;
- advanced analytics and experimentation.

These capabilities remain valid Blueprint inventory. This scope document does not delete, downgrade, or rewrite them.

## 4. Delivery order

Implementation proceeds in this order:

1. Account entry: AUTH-001/AUTH-002 and the minimum USER profile surface.
2. Content core: CONTENT/ARTICLE minimum publish-and-browse chain.
3. Media/video: MEDIA/STORAGE minimum playable path.
4. Subscription: MON/PAY/entitlement partial-paywall path.
5. Administration: ADMIN minimum operational surface.
6. Client delivery: Web/H5, then Android/iOS integration against the same canonical API.

A later stage cannot claim completion merely because an earlier stage exists; each stage requires its own Contract-aligned tests and Evidence.

## 5. Evidence and gate rule

For every 1.0 Feature ID:

- existing GREEN/PASS_VERIFIED evidence is inherited when its tested inputs remain unchanged;
- missing or stale evidence is not promoted by this document;
- implementation must remain blocked when the governing Contract/Mapping gate says implementation is not admitted;
- runtime claims require executable evidence tied to a validating commit SHA;
- external/manual execution remains an external gate and is not simulated;
- Payload CRUD existence is never sufficient proof of public API completion.

## 6. Architecture guardrails

1. Keep the final target at **12 Workers / 4 D1 domains / 25 Contract Tasks**.
2. Do not add infrastructure merely to satisfy this release scope.
3. Keep Payload Core unmodified.
4. Keep large media in object storage and metadata/state authoritative on the defined database path.
5. Prefer cache-first bounded reads and asynchronous projection where the current Contracts require them.
6. Preserve PostgreSQL/GCP portability.
7. Do not create a second custom subsystem when an already-admitted Payload-native capability satisfies the Contract.

## 7. 1.0 completion definition

LuckRead 1.0 is complete only when every Feature ID included in Section 2 has:

```text
Blueprint ID
  → Contract/API
  → Data/ownership/state
  → Authorization/security
  → Implementation
  → Unit/integration/security tests
  → CI/build validation
  → Runtime/E2E evidence where required
  → Evidence Registry provenance
```

and all applicable release gates are GREEN.

This document freezes scope. It does not itself grant implementation admission, declare any blocked feature GREEN, or replace an existing Contract/Evidence record.
