# LuckRead 1.1 Mature Creator Implementation Hardening Contract v1.0

**Status:** CHANGE-CONTROLLED / IMPLEMENTATION-GUARD / SUPPLEMENTAL CONTRACT
**Applies to:** 1.1 Mature Creator Core implementation
**Authority:** Existing canonical Blueprint + existing domain Contracts remain authoritative; this document adds implementation-grade constraints and acceptance gates.
**No new Feature IDs. No new Worker/D1 topology. No replacement of historical contracts.**

## 1. Purpose

This contract converts the existing 1.1 scope and domain contracts into a stricter implementation boundary for the first production-grade vertical slices:

```text
Account / Identity
→ Creator
→ Content Production / Article
→ Media / Short Video
```

It exists to prevent a common failure mode:

```text
UI exists ≠ business fact exists
API exists ≠ authority exists
D1 row exists ≠ lifecycle is correct
Event exists ≠ source of truth
Cache exists ≠ current authorization
```

Implementation is admitted only when the relevant authoritative contract, mapping, security boundary, runtime behavior, tests and evidence agree.

## 2. Contract Precedence

This document is supplemental.

Precedence is:

```text
Blueprint
→ Canonical Domain Contract
→ Approved Change Control
→ This Hardening Contract
→ Implementation
```

If this document conflicts with an existing canonical Contract, implementation MUST STOP and the conflict MUST be recorded as decision material. The code must not silently choose one interpretation.

Historical Evidence and historical snapshots MUST NOT be rewritten to make the current implementation appear cleaner.

## 3. Non-Negotiable Architecture Guard

The 1.1 implementation MUST remain inside:

```text
12 Workers
4 D1
25 Tasks
```

Rules:

- no new Worker;
- no new D1;
- no new database authority;
- no direct frontend-to-D1 access;
- no Payload internal model exposed as public domain schema;
- no second authority created in Creator Center, dashboard, cache, event store or projection;
- media bytes must not be routed through D1;
- derived projections remain rebuildable.

Current terminal boundaries remain governed by the Worker Binding contract. Public ingress does not transfer domain authority to W01.

## 4. Vertical Slice Rule

Implementation proceeds vertically, not by building incomplete fragments across every domain.

### Slice A — Account

Registration/login/session/profile/security/lifecycle foundations that are already contract-admitted.

### Slice B — Creator

Creator identity/profile and the minimum Creator operating boundary required by the contracted 1.1 scope.

### Slice C — Content / Article

Draft → edit → revision → preflight/review → publish → public read/update/unpublish.

### Slice D — Media / Short Video

Upload → processing → ready/failure → short-video reference → playback/delivery metadata.

A later slice may consume an earlier slice, but it may not create an alternative version of the earlier authority.

## 5. Universal Mutation Contract

Every state-changing operation MUST define:

```text
actor
authentication
account-state gate
permission/scope
target resource
ownership/delegation
precondition
idempotency
concurrency/version
mutation
event/outbox journal
audit
response
```

Minimum request controls:

- `requestId` or an equivalent trace identifier;
- `correlationId` for multi-step flows;
- `Idempotency-Key` for retryable mutations;
- `If-Match` or an equivalent optimistic-concurrency guard when a mutable version exists;
- server-side authorization;
- stable error code.

Client-supplied role, layer, capability, creator ownership or moderation result MUST NOT be treated as authoritative.

## 6. Universal Read Contract

Every protected read MUST evaluate authorization against current authoritative state.

Rules:

- private/sensitive responses MUST NOT use a shared public cache;
- cache MUST NOT override current account suspension, revocation, entitlement, visibility or rights decisions;
- public content/profile reads MAY use derived cache only when cache safety and invalidation are contractually established;
- normal public read paths MUST avoid unnecessary D1 reads;
- a cache miss MUST remain within the approved D1/read budget;
- cache keys MUST include every authorization-relevant variant where applicable.

A stale cache is a performance defect; stale authorization is a security defect.

## 7. Universal Event Contract

Domain events are propagation mechanisms, never second authorities.

Every admitted event MUST carry, where applicable:

```text
eventId
eventType
schemaVersion
producer
entity/resource id
source version
occurredAt
requestId
correlationId
causationId
idempotency/dedupe key
```

Consumers MUST tolerate:

- duplicate delivery;
- retry;
- out-of-order delivery;
- delayed delivery;
- poison messages;
- replay;
- partial downstream failure.

A consumer MUST NOT create a second authoritative fact merely because an event was received.

## 8. Universal Error Contract

External APIs MUST distinguish at least:

```text
400 VALIDATION_FAILED
401 AUTHENTICATION_FAILED
403 FORBIDDEN
404 NOT_FOUND
409 CONFLICT
412 PRECONDITION_FAILED
428 PRECONDITION_REQUIRED
429 RATE_LIMITED
422 STATE_NOT_ALLOWED
503 SERVICE_UNAVAILABLE
```

The exact error namespace may follow the existing API Contract, but error semantics MUST remain stable.

Errors MUST NOT disclose:

- passwords or credential material;
- private verification evidence;
- internal risk scores;
- moderation thresholds;
- security detection rules;
- storage internals not needed by the caller.

## 9. Account Hardening Contract

### 9.1 Authority

Account state remains owned by the Identity/Account authority.

The following must remain separate:

```text
Identity
Role
Entitlement
Subscription
Organization Membership
Account State
Resource Ownership
```

### 9.2 Lifecycle

The canonical account state machine is authoritative.

Rules:

- illegal transition → `INVALID_STATE`;
- stale version → `CONFLICT`;
- failed precondition → `PRECONDITION_FAILED`;
- token-invalidating states MUST invalidate sessions according to the lifecycle contract;
- every successful state mutation increments the state version exactly once;
- every successful state mutation emits the admitted state-change event/journal;
- audit records MUST contain before/after state and actor provenance.

### 9.3 Security

Credential and session handling MUST remain outside ordinary Creator DTOs.

No account API may:

- return passwords/password hashes;
- return raw recovery secrets;
- trust client-selected authorization layer;
- use nickname text as stable identity;
- keep a revoked session usable through cache alone.

### 9.4 Profile

Profile mutations MUST:

- use self/authorized scope;
- apply optimistic concurrency where supported;
- reject unsupported fields;
- invalidate affected derived public profile variants after a committed change;
- preserve old/new username references when username changes affect public cache keys;
- never expose private email, phone or security data through the public profile.

## 9.5 Final Account / Payload Boundary

The 1.1 implementation follows the approved account-center amendment:

```text
W02 / Better Auth
= User + Identity + Credential + Session + Account State + Authorization

W08
= Creator + Organization + Creator Qualification

W03 / Payload boundary
= Content + Article + Media + Translation + CMS workflow
```

Payload User is a local CMS/editor projection only when required by Payload relationships. It MUST bind to the canonical W02 User through `authUserId` and MUST NOT become a competing identity, session, credential, or authorization source.

All L1-L8 layer resolution MUST use the canonical authz contract:
`docs/301-L0-L8-PERMISSION-LAYER-CONTRACT-v1.0.md` + `contracts/authz/layers.json`.

Client-provided layer, role, creator flag, or permission claims are never authoritative.

## 10. Creator Hardening Contract

### 10.1 Authority

Creator System is authoritative for:

```text
creator identity
creator type
creator public profile
creator lifecycle
creator qualification
creator verification state
creator capability state
creator-side collaboration state
creator-side attribution relationship
```

It is NOT authoritative for:

```text
Organization membership
Content truth
Media processing truth
Legal rights
Social graph truth
Membership entitlement
Risk decision
Moderation decision
Money / balance / settlement
Analytics truth
```

### 10.2 Identity Binding

A Creator MUST bind to a canonical User identity.

At minimum:

```text
creatorId
userId
creatorType
handle
lifecycleState
createdAt
updatedAt
```

Rules:

- creatorId is immutable;
- userId binding is unique unless a separate approved contract explicitly permits another relation;
- handle uniqueness is server-enforced;
- normalization rules are deterministic;
- display name is not a stable identity key.

### 10.3 Qualification / Verification / Capability

These are separate facts:

```text
Verification ≠ Qualification ≠ Capability
```

Therefore:

- verified creator does not automatically mean every feature is enabled;
- capability cannot replace per-request authorization;
- qualification expiry must be represented explicitly;
- verification expiry/revocation must be explicit;
- raw verification evidence is not returned through normal Creator APIs.

### 10.4 Ownership / Delegation

Ownership and delegated access MUST be evaluated per resource.

A User owning an account does not automatically own another Creator.

An Organization/MCN member does not automatically control every Creator.

Delegation MUST have:

```text
grantor
recipient
scope
resource
issuedAt
expiresAt
revokedAt
reason
```

### 10.5 Creator Profile

Public and private projections MUST be explicitly separated.

Public profile may expose only contract-approved fields.

Business contact, verification evidence, security state, internal standing signals and sensitive location data MUST use their contracted privacy class.

## 11. Content Production Hardening Contract

### 11.1 Authority Split

```text
Production Domain
= Draft / Revision / Production Session

Content Domain
= Published Content Truth

Creator Domain
= Authorship / creator identity

Media Domain
= Media Asset / Processing Truth

Rights Domain
= Legal Rights / License Truth
```

No one domain may silently become another domain's authority.

### 11.2 Immutable Identity

Every content object MUST have:

```text
immutable contentId
contentType
ownerUserId
optional creatorId
status
visibility
canonicalVersion
createdAt
updatedAt
```

Changing title, body, cover or category MUST NOT create a new content identity unless the existing content contract explicitly defines identity rotation.

### 11.3 Revision and Publish

Published state MUST reference an explicit canonical revision/version.

Rules:

- published revisions are immutable snapshots;
- editing a draft must not silently rewrite an already-published version;
- preview MUST identify its version;
- rollback MUST restore a known version;
- publish MUST be idempotent;
- duplicate publish requests MUST not create duplicate published facts;
- scheduled publish MUST re-check authorization and lifecycle preconditions at execution time.

### 11.4 Draft Privacy

Drafts are private by default.

Draft data MUST NOT automatically enter:

- public search;
- public feeds;
- recommendation candidates;
- trending;
- public sitemap;
- public RSS.

### 11.5 Publish Preflight

Before publication, the implementation MUST respect the existing Publish Preflight boundary where applicable.

Preflight MAY reject or warn on:

- invalid structure/layout;
- invalid media references;
- contracted spam/contact patterns;
- policy violations;
- rights blockers;
- unsupported AI-generation modes under Creator policy.

Preflight is a gate, not the authority for identity, rights or moderation decisions.

### 11.6 Article Minimum Quality

Article implementation MUST preserve a structured content model capable of:

- rich text/blocks;
- images/gallery;
- canonical slug;
- version;
- series/collection references;
- category/tag/topic references;
- related-content references;
- featured/pinned references;
- preview/paywall markers where contractually admitted.

The implementation MUST NOT collapse all article semantics into one opaque HTML string if the admitted Article contract requires structured fields.

### 11.7 Cache Invalidation

A successful content mutation that changes public visibility or list membership MUST advance or invalidate the applicable cache generation.

The invalidation contract MUST cover at least:

```text
content detail
default list
creator filtered list
type filtered list
cursor variants
public profile/work aggregation where affected
```

Authenticated/private list responses MUST remain non-shared.

## 12. Media / Short Video Hardening Contract

### 12.1 Authority

```text
Media Domain
= Asset / Processing / Derived Media State

R2/Object Storage
= binary objects

Content/Video
= work identity and publication semantics

Rights
= legal authorization

Analytics
= playback/engagement derived metrics
```

R2 object existence MUST NOT be interpreted as business readiness.

### 12.2 Upload Contract

Upload flow MUST distinguish:

```text
upload intent
→ authorized upload
→ completed upload
→ validation
→ processing
→ ready / failed
```

Upload completion is not equivalent to playable/usable media.

### 12.3 Processing

Processing state MUST be durable and explicit.

At minimum:

```text
PENDING
PROCESSING
READY
FAILED
QUARANTINED
```

Exact enum names may follow the canonical media contract.

Processing MUST support:

- idempotent task identity;
- retry;
- timeout;
- DLQ/quarantine where required;
- replay;
- derived-output verification;
- failure recovery.

Incomplete outputs MUST NOT become public-ready assets.

### 12.4 Object Storage

Rules:

- video bytes do not enter D1 as primary storage;
- D1 stores authoritative metadata/references/state within the admitted domain;
- derived media objects are addressable through stable references;
- object deletion follows the media retention/deletion contract;
- public delivery does not expose private object paths without authorization.

### 12.5 Short Video

Short Video MUST reference Media rather than duplicate Media processing facts.

At minimum the implementation needs explicit references for:

```text
video/work identity
mediaId
poster/cover reference
processing state reference
publication state
visibility
rights/safety eligibility
playback/delivery metadata
```

Playback MUST re-check applicable:

```text
visibility
account restriction
moderation
rights
region policy
entitlement
```

before issuing or exposing a playback path where required.

### 12.6 Telemetry

Playback telemetry is asynchronous/derived.

The implementation MUST NOT:

- synchronously write one primary D1 transaction per playback heartbeat;
- use raw telemetry as authoritative recommendation or finance facts;
- allow telemetry retry to create duplicate financial facts.

## 13. Frontend / Backend Boundary

Frontend code may orchestrate interaction, but the backend/domain boundary remains authoritative.

Frontend MUST NOT decide:

- role;
- permission;
- creator ownership;
- account state;
- content publication eligibility;
- media readiness;
- rights clearance;
- moderation result;
- entitlement.

The frontend may pre-check for UX only; server-side checks remain mandatory.

## 14. Observability Contract

Every important mutation/read path MUST provide enough telemetry to answer:

```text
Who
→ did what
→ to which resource
→ under which authorization context
→ at which version
→ with which request/correlation
→ what was committed
→ which event was emitted
→ what failed downstream
```

Logs MUST be structured and redacted.

Do not log secrets, credential material, raw verification evidence or internal security signals.

## 15. Test Contract

Each vertical slice MUST contain:

### Unit

- valid state transitions;
- invalid transitions;
- authorization;
- normalization;
- idempotency;
- optimistic concurrency;
- cache key/invalidation rules.

### Integration

- public boundary;
- owning Worker;
- authoritative D1 path;
- event/outbox journal;
- failure rollback.

### Runtime / E2E

At least one real runtime path for every capability promoted toward GREEN, including:

```text
happy path
unauthorized path
stale version
duplicate/replay
failure recovery
visibility/security boundary
```

A static test that only checks source text MUST NOT be treated as the sole proof of runtime completion when runtime evidence is required.

## 16. Evidence Contract

Every promoted capability MUST produce evidence bound to the exact tested commit.

Minimum evidence:

```text
featureId
checkId
testedCommitSha
environment
operation/capability
testId or command
input/reference
observed result
timestamp
status
```

Evidence status MUST distinguish:

```text
PLANNED
RUN
PASS
FAIL
BLOCKED
VERIFIED
```

Only actually executed and provenance-bound evidence may support GREEN.

A 1.1 vertical slice is complete only when all applicable gates pass:

## 18. Release Admission Levels

### READY-FOR-CODE

All applicable design/contract/mapping gates are satisfied and implementation may start.

### IMPLEMENTED

Code exists and the local/static tests pass.

### RUNTIME-VERIFIED

Real runtime evidence has passed at the tested commit.

### GREEN

Feature-level reconciliation confirms the complete chain required by the authoritative Contract.

These states MUST NOT be conflated.

## 19. STOP Conditions

Immediately stop implementation when any of the following occurs:

- a new authority is being invented;
- a contract conflict is discovered;
- a duplicate operationId/entity owner appears;
- a new Worker/D1 is being introduced without approved Change Control;
- client input controls privilege;
- private data is shared-cached;
- stale cache can override authorization;
- concurrent update can silently overwrite;
- retry can duplicate an authoritative fact;
- published content can be rewritten without version semantics;
- unready media can become playable;
- media bytes are moved into D1 as primary storage;
- rights/moderation/risk decisions are recreated in another domain;
- evidence is missing, stale or bound to another commit.

## 20. Change Rule

Any requirement that cannot be implemented within existing contracts MUST follow:

```text
GAP
→ Decision Material
→ Change Control
→ Contract/Mapping amendment
→ Reconciliation
→ Implementation
```

Code MUST NOT be used to smuggle an architecture or authority decision into the project.

## 21. Final Principle

The 1.1 platform should feel simple to the user while remaining strict internally:

```text
Simple UX
+
Single Authority
+
Explicit Lifecycle
+
Safe Concurrency
+
Fail-Closed Security
+
Async Derived Data
+
Rebuildable Cache
+
Commit-Bound Evidence
```

The implementation should add the minimum code necessary to satisfy these guarantees and should not add infrastructure merely to make the implementation easier.
